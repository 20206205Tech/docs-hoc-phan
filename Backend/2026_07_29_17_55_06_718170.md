Dưới đây là bộ câu hỏi phỏng vấn về **OOP và các Design Pattern: Adapter, Builder, Singleton, Decorator, Factory, Mediator, Command**, phù hợp với vị trí **Lập trình viên Fresher/Junior Backend hoặc Fullstack**.

# I. Kiến thức nền tảng về OOP và Design Pattern

## 1. Design Pattern là gì?

**Trả lời:**

Design Pattern là mẫu thiết kế tổng quát dùng để giải quyết các vấn đề thường gặp trong thiết kế phần mềm.

Design Pattern không phải là đoạn mã hoàn chỉnh, mà là cách tổ chức class và object sao cho:

* Dễ mở rộng.
* Dễ bảo trì.
* Giảm phụ thuộc.
* Tăng khả năng tái sử dụng.

---

## 2. Design Pattern có phải luôn nên dùng không?

**Trả lời:**

Không.

Chỉ nên dùng khi bài toán thực sự phù hợp. Nếu áp dụng không cần thiết, hệ thống có thể:

* Tăng số lượng class.
* Khó đọc.
* Khó debug.
* Bị over-engineering.

---

## 3. Có những nhóm Design Pattern chính nào?

**Trả lời:**

Ba nhóm chính:

* **Creational Patterns:** Liên quan đến tạo object.
* **Structural Patterns:** Liên quan đến cấu trúc class và object.
* **Behavioral Patterns:** Liên quan đến giao tiếp và hành vi giữa object.

Các pattern trong câu hỏi được phân loại như sau:

* Builder, Singleton, Factory: Creational.
* Adapter, Decorator: Structural.
* Mediator, Command: Behavioral.

---

## 4. Design Pattern khác nguyên tắc SOLID như thế nào?

**Trả lời:**

SOLID là tập hợp các nguyên tắc thiết kế.

Design Pattern là các giải pháp thiết kế cụ thể.

Ví dụ:

* Dependency Inversion giúp giảm phụ thuộc.
* Factory có thể được dùng để tạo object thông qua abstraction.
* Decorator hỗ trợ Open/Closed Principle.

---

# II. Adapter Pattern

## 5. Adapter Pattern là gì?

**Trả lời:**

Adapter chuyển đổi interface của một class thành interface mà Client mong muốn.

Nó giúp hai thành phần không tương thích có thể làm việc với nhau.

Ví dụ:

```text
Client
  ↓
PaymentGateway interface
  ↓
MomoAdapter
  ↓
Momo SDK
```

---

## 6. Khi nào nên dùng Adapter?

**Trả lời:**

Dùng khi:

* Tích hợp thư viện bên thứ ba.
* API bên ngoài có interface khác hệ thống.
* Cần thay thế implementation mà không sửa Client.
* Cần tương thích với mã cũ.

---

## 7. Ví dụ Adapter trong hệ thống thanh toán?

**Trả lời:**

Giả sử hệ thống dùng interface chung:

```typescript
interface PaymentGateway {
  pay(amount: number): Promise<void>;
}
```

SDK MoMo có method khác:

```typescript
class MomoSdk {
  createPayment(totalAmount: number): Promise<void> {
    return Promise.resolve();
  }
}
```

Adapter:

```typescript
class MomoAdapter implements PaymentGateway {
  constructor(private readonly momoSdk: MomoSdk) {}

  pay(amount: number): Promise<void> {
    return this.momoSdk.createPayment(amount);
  }
}
```

Client chỉ phụ thuộc vào `PaymentGateway`, không phụ thuộc trực tiếp vào SDK MoMo.

---

## 8. Adapter và Facade khác nhau thế nào?

**Trả lời:**

Adapter chuyển đổi interface để tương thích.

Facade cung cấp một interface đơn giản hơn cho một hệ thống phức tạp.

* Adapter giải quyết vấn đề không tương thích.
* Facade giải quyết vấn đề phức tạp khi sử dụng.

---

## 9. Adapter và Decorator khác nhau thế nào?

**Trả lời:**

* Adapter thay đổi interface.
* Decorator giữ nguyên interface nhưng bổ sung hành vi.

Ví dụ:

```text
Adapter:
Momo SDK → PaymentGateway

Decorator:
PaymentGateway → LoggingPaymentGateway
```

---

## 10. Ưu và nhược điểm của Adapter?

**Trả lời:**

Ưu điểm:

* Giảm phụ thuộc vào hệ thống bên ngoài.
* Dễ thay thế nhà cung cấp.
* Giữ code Client ổn định.
* Dễ mock khi test.

Nhược điểm:

* Tăng số lượng class.
* Có thể tạo nhiều lớp chuyển đổi.
* Nếu API ngoài thay đổi nhiều, Adapter cũng phải cập nhật.

---

# III. Builder Pattern

## 11. Builder Pattern là gì?

**Trả lời:**

Builder dùng để tạo object phức tạp theo từng bước.

Nó giúp tránh constructor có quá nhiều tham số.

---

## 12. Khi nào nên dùng Builder?

**Trả lời:**

Dùng khi:

* Object có nhiều thuộc tính.
* Nhiều thuộc tính là tùy chọn.
* Có nhiều cách tạo cùng một object.
* Muốn object dễ đọc khi khởi tạo.
* Muốn tạo immutable object.

---

## 13. Constructor quá nhiều tham số gây vấn đề gì?

**Trả lời:**

Ví dụ:

```java
new User(
    "Nghia",
    "nghia@example.com",
    "0123456789",
    "Hanoi",
    true,
    "ADMIN"
);
```

Các vấn đề:

* Khó nhớ thứ tự.
* Dễ truyền nhầm.
* Khó đọc.
* Khó thêm thuộc tính mới.

---

## 14. Ví dụ Builder trong Java?

```java
public class User {
    private final String name;
    private final String email;
    private final String phone;

    private User(Builder builder) {
        this.name = builder.name;
        this.email = builder.email;
        this.phone = builder.phone;
    }

    public static class Builder {
        private String name;
        private String email;
        private String phone;

        public Builder name(String name) {
            this.name = name;
            return this;
        }

        public Builder email(String email) {
            this.email = email;
            return this;
        }

        public Builder phone(String phone) {
            this.phone = phone;
            return this;
        }

        public User build() {
            return new User(this);
        }
    }
}
```

Sử dụng:

```java
User user = new User.Builder()
    .name("Nghia")
    .email("nghia@example.com")
    .phone("0123456789")
    .build();
```

---

## 15. Builder khác Factory như thế nào?

**Trả lời:**

Factory tập trung vào việc chọn và tạo loại object phù hợp.

Builder tập trung vào quá trình tạo một object phức tạp theo từng bước.

Ví dụ:

* Factory chọn tạo `EmailNotification` hay `SmsNotification`.
* Builder cấu hình chi tiết một `NotificationRequest`.

---

## 16. Builder có giúp tạo immutable object không?

**Trả lời:**

Có.

Object chính có thể:

* Dùng field `final`.
* Không có setter.
* Chỉ nhận dữ liệu từ Builder trong constructor.

Sau khi tạo, object không thể thay đổi.

---

## 17. Nhược điểm của Builder?

**Trả lời:**

* Tăng số lượng mã.
* Có thêm Builder class.
* Không cần thiết với object đơn giản.
* Có thể khó đồng bộ validation giữa Builder và object.

---

# IV. Singleton Pattern

## 18. Singleton Pattern là gì?

**Trả lời:**

Singleton đảm bảo một class chỉ có một instance và cung cấp điểm truy cập chung đến instance đó.

Ví dụ:

* Configuration manager.
* Logger.
* Cache manager.
* Connection pool manager.

---

## 19. Ví dụ Singleton trong Java?

```java
public final class AppConfig {
    private static final AppConfig INSTANCE = new AppConfig();

    private AppConfig() {
    }

    public static AppConfig getInstance() {
        return INSTANCE;
    }
}
```

---

## 20. Vì sao constructor của Singleton phải là private?

**Trả lời:**

Để ngăn code bên ngoài tự tạo object bằng:

```java
new AppConfig();
```

Class phải tự kiểm soát việc tạo instance.

---

## 21. Singleton có vấn đề gì trong môi trường đa luồng?

**Trả lời:**

Nếu lazy initialization không được đồng bộ đúng, nhiều thread có thể tạo nhiều instance cùng lúc.

Ví dụ không an toàn:

```java
if (instance == null) {
    instance = new Singleton();
}
```

Cần dùng:

* Eager initialization.
* `synchronized`.
* Double-checked locking đúng cách.
* Enum Singleton trong Java.

---

## 22. Enum Singleton trong Java là gì?

```java
public enum AppConfig {
    INSTANCE;
}
```

Ưu điểm:

* Thread-safe.
* Chống tạo lại qua serialization.
* Cách viết ngắn gọn.

---

## 23. Singleton khác static class như thế nào?

**Trả lời:**

Singleton là một object thực sự nên có thể:

* Implement interface.
* Truyền qua Dependency Injection.
* Mock trong test.
* Quản lý vòng đời.

Static class thường khó thay thế và khó test hơn.

---

## 24. Vì sao Singleton thường bị xem là Global State?

**Trả lời:**

Vì nhiều thành phần có thể truy cập và thay đổi cùng một instance toàn cục.

Điều này có thể gây:

* Coupling cao.
* Khó test.
* Khó kiểm soát trạng thái.
* Race condition.

---

## 25. Có nên tự viết Singleton trong NestJS không?

**Trả lời:**

Thường không cần.

Provider của NestJS mặc định có scope singleton trong phạm vi ứng dụng.

```typescript
@Injectable()
export class UsersService {}
```

NestJS Dependency Injection Container sẽ quản lý một instance của provider theo scope mặc định.

---

## 26. Khi nào không nên dùng Singleton?

**Trả lời:**

Không nên dùng khi:

* Object chứa trạng thái thay đổi theo request.
* Cần nhiều configuration khác nhau.
* Cần test độc lập.
* Cần scale trên nhiều process hoặc server.

Singleton chỉ đảm bảo một instance trong một process, không đảm bảo toàn hệ thống phân tán chỉ có một instance.

---

# V. Decorator Pattern

## 27. Decorator Pattern là gì?

**Trả lời:**

Decorator bổ sung hành vi cho object bằng cách bọc object đó mà không sửa class gốc.

Decorator giữ cùng interface với object được bọc.

---

## 28. Khi nào dùng Decorator?

**Trả lời:**

Dùng khi cần thêm chức năng như:

* Logging.
* Caching.
* Retry.
* Authorization.
* Metrics.
* Compression.
* Encryption.

---

## 29. Ví dụ Decorator?

```typescript
interface DataService {
  getData(): Promise<string>;
}

class ApiDataService implements DataService {
  async getData(): Promise<string> {
    return "data";
  }
}

class LoggingDataService implements DataService {
  constructor(private readonly inner: DataService) {}

  async getData(): Promise<string> {
    console.log("Start");
    const result = await this.inner.getData();
    console.log("End");
    return result;
  }
}
```

Sử dụng:

```typescript
const service = new LoggingDataService(
  new ApiDataService()
);
```

---

## 30. Decorator Pattern và Decorator Syntax có giống nhau không?

**Trả lời:**

Không hoàn toàn.

Decorator Pattern là mẫu thiết kế hướng đối tượng.

Decorator Syntax như `@Injectable()` hoặc `@Controller()` trong TypeScript là tính năng ngôn ngữ hoặc metadata.

Chúng có mục đích liên quan đến bổ sung hành vi hoặc metadata, nhưng không đồng nghĩa hoàn toàn với Decorator Pattern cổ điển.

---

## 31. Decorator và Inheritance khác nhau thế nào?

**Trả lời:**

Inheritance thêm hành vi bằng kế thừa class.

Decorator thêm hành vi bằng composition.

Decorator linh hoạt hơn vì có thể kết hợp nhiều lớp bọc tại runtime:

```text
Caching
  ↓
Logging
  ↓
Retry
  ↓
ApiService
```

---

## 32. Decorator hỗ trợ nguyên tắc SOLID nào?

**Trả lời:**

Decorator hỗ trợ Open/Closed Principle:

* Mở để mở rộng.
* Đóng để sửa đổi.

Có thể bổ sung hành vi mà không sửa class gốc.

---

## 33. Nhược điểm của Decorator?

**Trả lời:**

* Tạo nhiều object lồng nhau.
* Khó debug luồng gọi.
* Thứ tự các Decorator có thể ảnh hưởng kết quả.
* Có thể tăng độ phức tạp cấu hình.

---

# VI. Factory Pattern

## 34. Factory Pattern là gì?

**Trả lời:**

Factory đóng gói logic tạo object, giúp Client không cần biết class cụ thể được khởi tạo như thế nào.

---

## 35. Khi nào dùng Factory?

**Trả lời:**

Dùng khi:

* Có nhiều implementation cùng interface.
* Loại object phụ thuộc vào cấu hình hoặc input.
* Việc tạo object phức tạp.
* Muốn giảm phụ thuộc vào class cụ thể.

---

## 36. Ví dụ Simple Factory?

```typescript
interface NotificationSender {
  send(message: string): void;
}

class EmailSender implements NotificationSender {
  send(message: string): void {
    console.log(`Email: ${message}`);
  }
}

class SmsSender implements NotificationSender {
  send(message: string): void {
    console.log(`SMS: ${message}`);
  }
}

class NotificationFactory {
  static create(type: string): NotificationSender {
    if (type === "email") {
      return new EmailSender();
    }

    if (type === "sms") {
      return new SmsSender();
    }

    throw new Error("Unsupported notification type");
  }
}
```

---

## 37. Factory Method là gì?

**Trả lời:**

Factory Method định nghĩa method tạo object trong class cha hoặc interface, còn class con quyết định object cụ thể được tạo.

Mục tiêu là cho phép mở rộng loại object mà không sửa Client.

---

## 38. Abstract Factory là gì?

**Trả lời:**

Abstract Factory tạo ra một họ object có liên quan.

Ví dụ giao diện theo theme:

```text
LightThemeFactory
  ├── LightButton
  └── LightDialog

DarkThemeFactory
  ├── DarkButton
  └── DarkDialog
```

---

## 39. Simple Factory, Factory Method và Abstract Factory khác nhau?

**Trả lời:**

* **Simple Factory:** Một class hoặc method lựa chọn class cụ thể.
* **Factory Method:** Class con quyết định object được tạo.
* **Abstract Factory:** Tạo một nhóm object liên quan.

---

## 40. Factory hỗ trợ Dependency Inversion như thế nào?

**Trả lời:**

Client phụ thuộc vào interface thay vì class cụ thể.

```text
Client
  ↓
NotificationSender
  ↑
EmailSender / SmsSender
```

Factory chịu trách nhiệm chọn implementation phù hợp.

---

## 41. Nhược điểm của Factory?

**Trả lời:**

* Tăng số lượng class.
* Logic Factory có thể trở nên lớn.
* Nếu dùng `if/else` liên tục, Factory có thể vi phạm Open/Closed.
* Có thể cần Registry hoặc Dependency Injection Container để mở rộng tốt hơn.

---

# VII. Mediator Pattern

## 42. Mediator Pattern là gì?

**Trả lời:**

Mediator tạo một đối tượng trung gian để điều phối giao tiếp giữa nhiều object.

Các object không gọi trực tiếp nhau mà giao tiếp qua Mediator.

---

## 43. Vì sao cần Mediator?

**Trả lời:**

Nếu nhiều object gọi chéo nhau:

```text
A ↔ B
A ↔ C
B ↔ C
C ↔ D
```

Hệ thống có coupling cao.

Mediator chuyển thành:

```text
A
B
C
D
 ↓
Mediator
```

---

## 44. Ví dụ Mediator trong giao diện?

**Trả lời:**

Một form có:

* Checkbox.
* Textbox.
* Submit button.

Khi Checkbox thay đổi, Mediator quyết định:

* Bật Textbox.
* Bật hoặc tắt Submit button.

Các component không cần biết trực tiếp nhau.

---

## 45. Ví dụ Mediator trong Backend?

**Trả lời:**

CQRS Mediator có thể nhận command và chuyển đến đúng handler:

```text
Controller
  ↓
Mediator
  ↓
CreateOrderHandler
```

Controller không cần phụ thuộc trực tiếp vào từng Service hoặc Handler cụ thể.

---

## 46. Mediator và Event Bus khác nhau thế nào?

**Trả lời:**

Mediator thường điều phối giao tiếp trong phạm vi ứng dụng hoặc process.

Event Bus thường dùng mô hình publish/subscribe, có thể có nhiều subscriber và giao tiếp bất đồng bộ.

Mediator thường biết cách định tuyến tới handler phù hợp; Event Bus phân phối event đến các subscriber.

---

## 47. Mediator có nhược điểm gì?

**Trả lời:**

Mediator có thể trở thành “God Object” nếu chứa quá nhiều logic.

Khi đó:

* Khó bảo trì.
* Khó test.
* Tập trung quá nhiều trách nhiệm.
* Mọi luồng đều phụ thuộc vào một nơi.

Mediator chỉ nên điều phối, không nên chứa toàn bộ nghiệp vụ.

---

# VIII. Command Pattern

## 48. Command Pattern là gì?

**Trả lời:**

Command đóng gói một yêu cầu thành một object.

Command object có thể chứa:

* Hành động.
* Tham số.
* Người thực thi.
* Thời điểm thực hiện.
* Trạng thái.

---

## 49. Khi nào dùng Command Pattern?

**Trả lời:**

Dùng khi cần:

* Queue tác vụ.
* Undo/Redo.
* Logging hành động.
* Retry.
* Scheduling.
* Tách người gửi yêu cầu khỏi người thực hiện.

---

## 50. Ví dụ Command Pattern?

```typescript
interface Command {
  execute(): void;
}

class Light {
  turnOn(): void {
    console.log("Light on");
  }
}

class TurnOnLightCommand implements Command {
  constructor(private readonly light: Light) {}

  execute(): void {
    this.light.turnOn();
  }
}
```

Invoker:

```typescript
class RemoteControl {
  execute(command: Command): void {
    command.execute();
  }
}
```

---

## 51. Các thành phần của Command Pattern?

**Trả lời:**

* **Command:** Interface hành động.
* **Concrete Command:** Cài đặt hành động.
* **Receiver:** Object thực hiện công việc thật.
* **Invoker:** Kích hoạt Command.
* **Client:** Tạo và cấu hình Command.

---

## 52. Command Pattern hỗ trợ Undo như thế nào?

**Trả lời:**

Command có thể cung cấp method:

```typescript
interface Command {
  execute(): void;
  undo(): void;
}
```

Ví dụ:

* `execute()` bật đèn.
* `undo()` tắt đèn.

Invoker lưu lịch sử Command để thực hiện Undo.

---

## 53. Command Pattern khác Strategy Pattern thế nào?

**Trả lời:**

Strategy đóng gói một thuật toán có thể thay thế.

Command đóng gói một yêu cầu hoặc hành động.

Ví dụ:

* Strategy: Chọn thuật toán tính phí.
* Command: Thực hiện thao tác thanh toán.

---

## 54. Command Pattern khác Event như thế nào?

**Trả lời:**

Command yêu cầu một hành động xảy ra:

```text
CreateOrder
```

Event thông báo một hành động đã xảy ra:

```text
OrderCreated
```

Command có thể thất bại hoặc bị từ chối. Event mô tả sự thật trong quá khứ.

---

## 55. Command Pattern có liên quan đến Message Queue không?

**Trả lời:**

Có.

Command có thể được serialize thành message và đưa vào Queue:

```text
API
  ↓ ProcessDocumentCommand
RabbitMQ
  ↓
Document Worker
```

Worker nhận Command và thực thi.

Cần thêm:

* Idempotency.
* Retry.
* DLQ.
* Correlation ID.
* Validation.

---

| --------- | ------------------------------------ |
| Adapter   | Chuyển đổi interface                 |
| Builder   | Tạo object phức tạp từng bước        |
| Singleton | Giới hạn một instance                |
| Decorator | Bổ sung hành vi bằng cách bọc object |
| Factory   | Đóng gói việc tạo object             |
| Mediator  | Điều phối giao tiếp giữa các object  |
| Command   | Đóng gói một yêu cầu thành object    |

# X. Câu hỏi tình huống phỏng vấn

## Tình huống 1: Tích hợp nhiều cổng thanh toán

**Hỏi:** Hệ thống hỗ trợ MoMo, VNPay và Stripe, mỗi SDK có API khác nhau. Dùng Pattern nào?

**Trả lời:**

Dùng Adapter để chuyển từng SDK về một interface chung:

```text
PaymentGateway
  ├── MomoAdapter
  ├── VnPayAdapter
  └── StripeAdapter
```

Có thể dùng Factory để chọn Adapter dựa trên loại thanh toán.

---

## Tình huống 2: Tạo object cấu hình AI có nhiều tham số

**Hỏi:** Object có model, temperature, max tokens, tools, timeout và retry. Dùng Pattern nào?

**Trả lời:**

Dùng Builder vì object có nhiều tham số, phần lớn là tùy chọn.

```text
AgentConfigBuilder
  .model(...)
  .temperature(...)
  .tools(...)
  .timeout(...)
  .build()
```

---

## Tình huống 3: Thêm logging và caching vào Repository

**Hỏi:** Không muốn sửa Repository hiện tại. Dùng Pattern nào?

**Trả lời:**

Dùng Decorator:

```text
CachingRepository
  ↓
LoggingRepository
  ↓
DatabaseRepository
```

Các Decorator cùng triển khai một Repository interface.

---

## Tình huống 4: Chọn cách gửi thông báo

**Hỏi:** Tùy cấu hình mà tạo EmailSender, SmsSender hoặc PushSender. Dùng Pattern nào?

**Trả lời:**

Dùng Factory để tạo đúng implementation dựa trên loại thông báo.

---

## Tình huống 5: Nhiều component gọi chéo nhau

**Hỏi:** Form có nhiều component phụ thuộc lẫn nhau. Dùng Pattern nào?

**Trả lời:**

Dùng Mediator để gom logic điều phối vào một thành phần trung gian, giảm coupling giữa các component.

---

## Tình huống 6: Xây dựng chức năng Undo/Redo

**Hỏi:** Dùng Pattern nào?

**Trả lời:**

Dùng Command Pattern.

Mỗi hành động được đóng gói thành Command có:

* `execute()`.
* `undo()`.

Hệ thống lưu Command vào Stack để Undo hoặc Redo.

---

## Tình huống 7: Một Service trong NestJS chỉ nên có một instance

**Hỏi:** Có cần tự viết Singleton không?

**Trả lời:**

Thông thường không.

NestJS Provider mặc định đã có singleton scope. Nên để Dependency Injection Container quản lý thay vì tự tạo Global Singleton.

# XI. Các câu hỏi nâng cao

## 1. Có thể kết hợp Adapter và Factory không?

**Trả lời:**

Có.

Factory chọn Adapter phù hợp:

```text
PaymentAdapterFactory
  ├── MomoAdapter
  ├── VnPayAdapter
  └── StripeAdapter
```

Client chỉ yêu cầu một `PaymentGateway`.

---

## 2. Có thể kết hợp Builder và Factory không?

**Trả lời:**

Có.

Factory chọn loại object, Builder cấu hình chi tiết object đó.

Ví dụ Factory chọn loại Agent, Builder cấu hình model, tool và timeout.

---

## 3. Decorator có thể bọc nhiều lớp không?

**Trả lời:**

Có.

```text
MetricsDecorator
  ↓
RetryDecorator
  ↓
CachingDecorator
  ↓
ApiClient
```

Cần chú ý thứ tự vì kết quả có thể khác nhau.

Ví dụ cache bên ngoài retry khác với retry bên ngoài cache.

---

## 4. Singleton có hoạt động trên nhiều Pod Kubernetes không?

**Trả lời:**

Không.

Mỗi Pod hoặc process có một instance Singleton riêng.

Nếu cần trạng thái duy nhất toàn hệ thống, có thể cần:

* Database lock.
* Distributed lock.
* Leader election.
* Redis.
* Kubernetes Lease.

---

## 5. Factory có thể được thay thế bằng Dependency Injection không?

**Trả lời:**

Trong nhiều trường hợp, Dependency Injection Container có thể thay Factory bằng cách đăng ký implementation.

Tuy nhiên, Factory vẫn hữu ích khi implementation phải được lựa chọn động tại runtime dựa trên dữ liệu đầu vào.

---

## 6. Mediator có làm mất tính rõ ràng của luồng không?

**Trả lời:**

Có thể.

Nếu mọi hành động đều đi qua Mediator, việc theo dõi luồng sẽ khó hơn.

Cần:

* Tên Command và Handler rõ ràng.
* Logging.
* Tracing.
* Không đặt nghiệp vụ chính trong Mediator.
* Tránh dùng Mediator cho những lời gọi đơn giản không cần thiết.

---

# XII. Câu trả lời ngắn cần ghi nhớ

**Adapter là gì?**

> Adapter chuyển interface không tương thích thành interface mà hệ thống mong muốn.

**Builder là gì?**

> Builder tạo object phức tạp theo từng bước và tránh constructor có quá nhiều tham số.

**Singleton là gì?**

> Singleton đảm bảo một class chỉ có một instance trong phạm vi một process.

**Decorator là gì?**

> Decorator bổ sung hành vi cho object bằng cách bọc object và giữ nguyên interface.

**Factory là gì?**

> Factory đóng gói logic tạo object và giúp Client không phụ thuộc vào class cụ thể.

**Mediator là gì?**

> Mediator điều phối giao tiếp giữa nhiều object để giảm phụ thuộc trực tiếp.

**Command là gì?**

> Command đóng gói một yêu cầu thành object, hỗ trợ queue, retry, logging và undo/redo.

**Ví dụ kết hợp thực tế:**

```text
PaymentFactory
   ↓
MomoAdapter
   ↓
LoggingDecorator
   ↓
RetryDecorator
   ↓
Momo SDK
```
