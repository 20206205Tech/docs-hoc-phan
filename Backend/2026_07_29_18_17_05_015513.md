Dưới đây là bộ câu hỏi phỏng vấn về **HashiCorp Vault và Terraform**, phù hợp với vị trí **Lập trình viên Fresher/Junior Backend, DevOps, Cloud hoặc Microservices**.

# I. Tổng quan HashiCorp

## 1. HashiCorp là gì?

**Trả lời:**

HashiCorp phát triển nhiều công cụ hỗ trợ xây dựng và vận hành hạ tầng, trong đó:

* **Terraform:** Khai báo và quản lý hạ tầng bằng mã nguồn.
* **Vault:** Quản lý secret, khóa mã hóa và thông tin xác thực.
* **Consul:** Service discovery và service networking.
* **Nomad:** Điều phối workload.

Trong phạm vi phỏng vấn này, Terraform quản lý **hạ tầng**, còn Vault quản lý **thông tin bí mật và quyền truy cập**.

---

## 2. Vault và Terraform giải quyết hai vấn đề gì?

**Trả lời:**

```text
Terraform
→ Tạo và quản lý hạ tầng

Vault
→ Bảo vệ, cấp phát và thu hồi secret
```

Ví dụ:

```text
Terraform
→ Tạo PostgreSQL, Kubernetes, DNS

Vault
→ Cấp tài khoản PostgreSQL tạm thời cho ứng dụng
```

Terraform là công cụ Infrastructure as Code; Vault là hệ thống quản lý secret và mã hóa dựa trên danh tính. ([HashiCorp Developer][1])

# II. HashiCorp Vault

## 3. HashiCorp Vault là gì?

**Trả lời:**

Vault là hệ thống quản lý:

* Secret.
* API key.
* Mật khẩu.
* Certificate.
* Khóa mã hóa.
* Database credential.
* Token.

Vault có thể tập trung hóa secret, tạo credential theo yêu cầu, xoay vòng credential và ghi nhận hoạt động truy cập để phục vụ audit. ([HashiCorp Developer][2])

---

## 4. Vì sao không nên lưu secret trực tiếp trong source code?

**Trả lời:**

Vì secret có thể bị lộ qua:

* Git history.
* Repository công khai.
* Log CI/CD.
* Docker Image.
* File cấu hình.
* Máy của lập trình viên.

Khi dùng Vault, ứng dụng xác thực với Vault rồi lấy secret phù hợp với quyền được cấp.

---

## 5. Static Secret là gì?

**Trả lời:**

Static Secret là secret được tạo trước và lưu trong Vault.

Ví dụ:

```text
API_KEY=abc123
JWT_SECRET=...
SMTP_PASSWORD=...
```

Secret chỉ thay đổi khi quản trị viên hoặc hệ thống chủ động cập nhật.

---

## 6. Dynamic Secret là gì?

**Trả lời:**

Dynamic Secret được Vault tạo tại thời điểm ứng dụng yêu cầu.

Ví dụ ứng dụng cần truy cập PostgreSQL:

```text
Application
→ Vault
→ Vault tạo username/password tạm thời
→ Application kết nối Database
```

Credential có TTL và có thể tự động bị thu hồi khi hết hạn. Vault Database Secrets Engine có thể tạo thông tin đăng nhập Database động theo role được cấu hình. ([HashiCorp Developer][3])

---

## 7. Static Secret và Dynamic Secret khác nhau thế nào?

| Static Secret                    | Dynamic Secret                     |
| -------------------------------- | ---------------------------------- |
| Được tạo trước                   | Tạo khi có yêu cầu                 |
| Thường dùng lâu hơn              | Có TTL ngắn                        |
| Nhiều ứng dụng có thể dùng chung | Có thể cấp riêng cho từng ứng dụng |
| Rotation phức tạp hơn            | Thu hồi và xoay vòng dễ hơn        |
| Khó truy vết cá nhân             | Dễ xác định credential thuộc ai    |

Dynamic Secret giúp giảm rủi ro khi credential bị lộ.

---

## 8. Secrets Engine là gì?

**Trả lời:**

Secrets Engine là thành phần Vault chịu trách nhiệm lưu, tạo hoặc chuyển đổi secret.

Ví dụ:

* KV Secrets Engine.
* Database Secrets Engine.
* PKI Secrets Engine.
* Transit Secrets Engine.
* Cloud Secrets Engine.

Mỗi Secrets Engine được mount tại một path.

---

## 9. KV Secrets Engine là gì?

**Trả lời:**

KV Secrets Engine lưu secret dạng key-value.

Ví dụ:

```text
secret/data/payment
├── api_key
├── api_secret
└── callback_secret
```

Phù hợp với secret tĩnh như API key hoặc cấu hình nhạy cảm.

---

## 10. KV Version 1 và Version 2 khác nhau thế nào?

**Trả lời:**

KV Version 1 lưu phiên bản hiện tại của secret.

KV Version 2 hỗ trợ versioning, cho phép:

* Xem phiên bản cũ.
* Khôi phục phiên bản.
* Soft delete.
* Quản lý metadata.

KV v2 phù hợp khi cần lịch sử thay đổi secret.

---

## 11. Database Secrets Engine hoạt động như thế nào?

**Trả lời:**

1. Vault được cấu hình tài khoản quản trị Database.
2. Quản trị viên tạo role trong Vault.
3. Ứng dụng xác thực với Vault.
4. Ứng dụng yêu cầu credential cho role.
5. Vault tạo tài khoản Database tạm thời.
6. Vault trả username, password và TTL.
7. Khi lease hết hạn, Vault thu hồi tài khoản.

Cơ chế này giúp ứng dụng không cần giữ mật khẩu Database cố định. ([HashiCorp Developer][4])

---

## 12. Transit Secrets Engine là gì?

**Trả lời:**

Transit Secrets Engine cung cấp dịch vụ mã hóa mà Vault không cần lưu dữ liệu nghiệp vụ gốc.

Luồng:

```text
Application
→ gửi plaintext cho Vault
→ Vault trả ciphertext
→ Application lưu ciphertext vào Database
```

Khi cần đọc:

```text
Application
→ gửi ciphertext
→ Vault giải mã
```

Vault quản lý khóa mã hóa, còn ứng dụng quản lý dữ liệu.

---

## 13. PKI Secrets Engine là gì?

**Trả lời:**

PKI Secrets Engine giúp:

* Phát hành certificate.
* Quản lý Certificate Authority.
* Tạo certificate có TTL ngắn.
* Thu hồi certificate.
* Hỗ trợ mTLS.

Nó có thể được dùng để cấp certificate cho Microservice, máy chủ hoặc người dùng.

---

## 14. Auth Method trong Vault là gì?

**Trả lời:**

Auth Method xác thực người dùng hoặc ứng dụng và ánh xạ danh tính đó với một tập policy.

Ví dụ:

* Token.
* Username/password.
* Kubernetes.
* AppRole.
* AWS.
* Azure.
* GitHub.
* OIDC.

Sau khi xác thực thành công, Vault thường trả về Vault Token mang các policy tương ứng. ([HashiCorp Developer][5])

---

## 15. Vault Token là gì?

**Trả lời:**

Vault Token là credential được dùng để gửi các request tiếp theo tới Vault.

Token gắn với:

* Policy.
* TTL.
* Khả năng gia hạn.
* Quan hệ cha–con.
* Metadata.

Không nên dựa vào cấu trúc nội bộ của Vault Token vì token được xem là giá trị opaque. ([HashiCorp Developer][6])

---

## 16. AppRole Auth Method là gì?

**Trả lời:**

AppRole thường dùng cho ứng dụng hoặc máy tự động.

Hai thành phần phổ biến:

* `role_id`: Định danh role.
* `secret_id`: Thông tin bí mật.

Ứng dụng dùng chúng để đăng nhập và nhận Vault Token.

Không nên lưu cố định cả `role_id` và `secret_id` trong cùng một repository hoặc file cấu hình.

---

## 17. Kubernetes Auth Method hoạt động thế nào?

**Trả lời:**

Luồng cơ bản:

```text
Pod
→ gửi Kubernetes ServiceAccount JWT cho Vault
→ Vault xác minh JWT với Kubernetes
→ Vault kiểm tra role
→ Vault trả Vault Token
```

Nhờ đó Pod không cần lưu Vault Token tĩnh trong Kubernetes Secret.

---

## 18. Policy trong Vault là gì?

**Trả lời:**

Policy xác định một danh tính được phép thực hiện hành động nào trên path nào.

Vault sử dụng mô hình path-based và mặc định từ chối quyền nếu policy không cấp phép. ([HashiCorp Developer][7])

Ví dụ:

```hcl
path "secret/data/payment/*" {
  capabilities = ["read"]
}
```

Policy trên chỉ cho phép đọc secret thuộc `payment`.

---

## 19. Các capability phổ biến trong Vault là gì?

**Trả lời:**

Một số capability:

* `create`
* `read`
* `update`
* `delete`
* `list`
* `sudo`
* `deny`

Nên áp dụng nguyên tắc **least privilege**: chỉ cấp quyền tối thiểu cần thiết.

---

## 20. Lease trong Vault là gì?

**Trả lời:**

Lease là metadata gắn với Dynamic Secret hoặc một số token, gồm:

* TTL.
* Có thể gia hạn hay không.
* Thời điểm hết hạn.
* Khả năng thu hồi.

Khi lease hết hạn, Vault có thể tự động thu hồi credential. ([HashiCorp Developer][3])

---

## 21. TTL là gì?

**Trả lời:**

TTL là thời gian secret hoặc token còn hiệu lực.

Ví dụ:

```text
TTL = 1 giờ
```

Sau một giờ, ứng dụng phải:

* Gia hạn lease.
* Hoặc lấy credential mới.

HashiCorp khuyến nghị điều chỉnh TTL ngắn nhất có thể mà vẫn đáp ứng nghiệp vụ. ([HashiCorp Developer][8])

---

## 22. Renew và Revoke khác nhau thế nào?

**Trả lời:**

* **Renew:** Gia hạn thời gian hiệu lực của lease hoặc token.
* **Revoke:** Thu hồi secret hoặc token trước khi hết hạn.

Ví dụ khi một Pod bị xóa, hệ thống có thể thu hồi credential Database mà Pod đã sử dụng.

---

## 23. Seal và Unseal trong Vault là gì?

**Trả lời:**

Khi Vault ở trạng thái **sealed**, Vault không thể truy cập dữ liệu đã mã hóa trong storage.

Unseal là quá trình cung cấp vật liệu khóa cần thiết để Vault giải mã khóa bảo vệ dữ liệu và bắt đầu phục vụ request.

---

## 24. Auto Unseal là gì?

**Trả lời:**

Auto Unseal dùng một hệ thống quản lý khóa bên ngoài để mở Vault tự động.

Ví dụ:

* Cloud KMS.
* HSM.
* Một Vault khác.

Điều này giúp tránh phải nhập thủ công các unseal key mỗi lần Vault khởi động lại.

---

## 25. Root Token là gì?

**Trả lời:**

Root Token có quyền rất cao trong Vault.

Nó chỉ nên được sử dụng cho:

* Khởi tạo hệ thống.
* Phục hồi khẩn cấp.
* Một số thao tác quản trị đặc biệt.

Không nên:

* Dùng Root Token cho ứng dụng.
* Đặt trong CI/CD.
* Lưu trong source code.
* Dùng cho công việc hằng ngày.

---

## 26. Audit Device trong Vault dùng để làm gì?

**Trả lời:**

Audit Device ghi nhận các request và response liên quan đến Vault.

Nó giúp trả lời:

* Ai truy cập secret?
* Truy cập lúc nào?
* Truy cập path nào?
* Request thành công hay thất bại?

Audit log rất quan trọng cho điều tra sự cố và tuân thủ bảo mật.

---

## 27. Vault Agent là gì?

**Trả lời:**

Vault Agent chạy cạnh ứng dụng và có thể hỗ trợ:

* Tự động xác thực.
* Gia hạn token.
* Lấy secret.
* Render secret vào file từ template.
* Giảm logic tích hợp Vault trong ứng dụng.

Ví dụ trong Kubernetes, Vault Agent có thể chạy như sidecar.

---

## 28. Secret Zero Problem là gì?

**Trả lời:**

Secret Zero là vấn đề: để lấy secret từ Vault, ứng dụng ban đầu phải có thông tin nào đó để chứng minh danh tính.

Cách giảm rủi ro:

* Kubernetes Service Account.
* Cloud IAM identity.
* Workload Identity.
* AppRole với cơ chế phân phối Secret ID an toàn.
* Certificate hoặc machine identity.

Mục tiêu là tránh một credential gốc cố định được nhúng trong source code.

---

## 29. Vault có phải là Database lưu dữ liệu nghiệp vụ không?

**Trả lời:**

Không.

Vault phù hợp lưu:

* Secret.
* Key.
* Credential.
* Certificate.
* Chính sách bảo mật.

Không nên dùng Vault để lưu:

* Đơn hàng.
* Hồ sơ sản phẩm.
* Log nghiệp vụ.
* Nội dung tài liệu lớn.

---

## 30. Nếu Vault không hoạt động thì ứng dụng có chạy được không?

**Trả lời:**

Tùy thiết kế.

Ứng dụng có thể tiếp tục dùng credential đã lấy nếu:

* Secret chưa hết hạn.
* Token còn hiệu lực.
* Credential vẫn được hệ thống đích chấp nhận.

Tuy nhiên, ứng dụng có thể không:

* Lấy secret mới.
* Renew lease.
* Giải mã dữ liệu qua Transit.
* Cấp certificate mới.

Vì vậy Vault production cần HA, monitoring và kế hoạch phục hồi.

# III. Terraform

## 31. Terraform là gì?

**Trả lời:**

Terraform là công cụ Infrastructure as Code cho phép khai báo, thay đổi và quản lý phiên bản hạ tầng bằng cấu hình.

Terraform có thể quản lý:

* Máy ảo.
* Network.
* Database.
* DNS.
* Kubernetes.
* SaaS resources.
* Cloud services.

([HashiCorp Developer][1])

---

## 32. Infrastructure as Code là gì?

**Trả lời:**

Infrastructure as Code, viết tắt IaC, là việc mô tả hạ tầng bằng file mã nguồn thay vì cấu hình thủ công.

Lợi ích:

* Có version control.
* Có code review.
* Tái sử dụng.
* Tạo môi trường nhất quán.
* Dễ audit.
* Giảm sai sót thủ công.

---

## 33. Terraform dùng ngôn ngữ gì?

**Trả lời:**

Terraform chủ yếu sử dụng **HashiCorp Configuration Language — HCL**.

Ví dụ:

```hcl
resource "aws_s3_bucket" "documents" {
  bucket = "company-documents"
}
```

Terraform cũng có thể nhận cấu hình JSON, nhưng HCL thường dễ đọc hơn.

---

## 34. Terraform là declarative hay imperative?

**Trả lời:**

Terraform chủ yếu là **declarative**.

Người dùng mô tả trạng thái mong muốn:

```text
Tôi muốn có 3 server.
```

Terraform tự xác định cần:

* Tạo thêm.
* Cập nhật.
* Hay xóa resource.

Không cần mô tả chi tiết từng câu lệnh thực thi như một script imperative.

---

## 35. Provider trong Terraform là gì?

**Trả lời:**

Provider là plugin cho phép Terraform giao tiếp với một API hoặc nền tảng cụ thể.

Ví dụ:

* AWS Provider.
* Azure Provider.
* Google Cloud Provider.
* Kubernetes Provider.
* Supabase Provider.
* MongoDB Atlas Provider.

Provider định nghĩa các loại `resource` và `data source` mà Terraform có thể sử dụng.

---

## 36. Resource trong Terraform là gì?

**Trả lời:**

Resource là đối tượng hạ tầng do Terraform quản lý.

Ví dụ:

```hcl
resource "aws_instance" "api" {
  ami           = "ami-123"
  instance_type = "t3.micro"
}
```

Resource trên biểu diễn một máy ảo AWS. ([HashiCorp Developer][9])

---

## 37. Data Source trong Terraform là gì?

**Trả lời:**

Data Source dùng để đọc thông tin đã tồn tại mà Terraform không nhất thiết tạo hoặc sở hữu.

Ví dụ:

```hcl
data "aws_vpc" "existing" {
  id = "vpc-123"
}
```

Sau đó cấu hình khác có thể sử dụng thông tin từ VPC này.

---

## 38. `terraform init` làm gì?

**Trả lời:**

`terraform init` khởi tạo thư mục Terraform:

* Tải Provider.
* Tải Module.
* Khởi tạo Backend.
* Chuẩn bị working directory.

Cần chạy lại khi:

* Đổi Backend.
* Thêm Provider.
* Thay Module source.
* Clone dự án Terraform mới.

---

## 39. `terraform fmt` làm gì?

**Trả lời:**

`terraform fmt` định dạng file Terraform theo style chuẩn.

Ví dụ:

```bash
terraform fmt -recursive
```

Nó thường được chạy trong pre-commit hoặc CI.

---

## 40. `terraform validate` làm gì?

**Trả lời:**

`terraform validate` kiểm tra cấu hình về:

* Cú pháp.
* Kiểu dữ liệu.
* Tham chiếu.
* Cấu trúc cấu hình.

Nó không xác nhận rằng credential cloud hợp lệ hoặc resource chắc chắn tạo được.

---

## 41. `terraform plan` làm gì?

**Trả lời:**

`terraform plan` tạo execution plan, cho biết Terraform dự định:

* Tạo resource nào.
* Thay đổi resource nào.
* Xóa resource nào.

Nó giúp review thay đổi trước khi thực thi. ([HashiCorp Developer][10])

---

## 42. `terraform apply` làm gì?

**Trả lời:**

`terraform apply` thực thi các thay đổi cần thiết để đưa hạ tầng về trạng thái đã khai báo.

Quy trình an toàn trong CI/CD thường là:

```text
terraform plan -out=tfplan
→ Review/Approve
→ terraform apply tfplan
```

---

## 43. `terraform destroy` làm gì?

**Trả lời:**

`terraform destroy` tạo và thực thi kế hoạch xóa các resource Terraform đang quản lý.

Đây là lệnh nguy hiểm, đặc biệt trong production. Nên có:

* Phê duyệt.
* Backup.
* Policy bảo vệ.
* `prevent_destroy` cho resource quan trọng.

---

## 44. Terraform State là gì?

**Trả lời:**

State là dữ liệu Terraform dùng để ánh xạ:

```text
Resource trong code
↔ Resource thật trên Cloud
```

State còn lưu metadata giúp Terraform xác định thay đổi cần thực hiện và cải thiện hiệu năng. ([HashiCorp Developer][11])

---

## 45. Vì sao Terraform cần State?

**Trả lời:**

Terraform cần biết:

* Resource thật nào tương ứng với resource trong code.
* ID của resource.
* Thuộc tính hiện tại.
* Quan hệ giữa các resource.
* Resource nào cần tạo, sửa hoặc xóa.

Không có state, Terraform khó quản lý vòng đời resource một cách đáng tin cậy.

---

## 46. Có nên commit file `terraform.tfstate` vào Git không?

**Trả lời:**

Không nên.

State có thể chứa:

* ID hạ tầng.
* Địa chỉ resource.
* Cấu hình nhạy cảm.
* Giá trị secret.
* Metadata nội bộ.

Nên lưu state trong Remote Backend có kiểm soát truy cập, mã hóa và locking.

---

## 47. Remote Backend là gì?

**Trả lời:**

Remote Backend lưu state ở hệ thống dùng chung thay vì trên máy cá nhân.

Lợi ích:

* Nhóm dùng chung state.
* Backup.
* Quản lý quyền.
* State locking.
* Tránh thất lạc state.
* Hỗ trợ quy trình CI/CD.

Remote state là giải pháp được khuyến nghị khi làm việc nhóm. ([HashiCorp Developer][12])

---

## 48. State Locking là gì?

**Trả lời:**

State Locking ngăn hai người hoặc hai pipeline cùng sửa state tại một thời điểm.

Nếu không có locking:

```text
Pipeline A apply
Pipeline B apply đồng thời
→ State có nguy cơ bị hỏng hoặc ghi đè
```

Terraform tự động lock state cho các thao tác có khả năng ghi nếu Backend hỗ trợ. ([HashiCorp Developer][13])

---

## 49. Có nên dùng `-lock=false` không?

**Trả lời:**

Thông thường không.

Tắt lock có thể khiến nhiều tiến trình cùng thay đổi state và gây hỏng dữ liệu. HashiCorp cảnh báo không nên vô hiệu hóa state locking trong những tình huống có thể chạy đồng thời. ([HashiCorp Developer][13])

---

## 50. Input Variable là gì?

**Trả lời:**

Input Variable cho phép truyền cấu hình vào module.

```hcl
variable "environment" {
  type        = string
  description = "Deployment environment"
}
```

Sử dụng:

```hcl
name = "api-${var.environment}"
```

## 51. Local Value là gì?

**Trả lời:**

Local Value lưu một biểu thức tái sử dụng trong module.

```hcl
locals {
  common_tags = {
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}
```

Local không phải input từ bên ngoài và không phải output.

## 52. Output Value là gì?

**Trả lời:**

Output Value công bố dữ liệu từ module.

```hcl
output "database_host" {
  value = aws_db_instance.main.address
}
```

Output có thể được dùng bởi:

* Người vận hành.
* Module cha.
* Cấu hình Terraform khác.
* Pipeline.

([HashiCorp Developer][14])

## 53. Terraform Module là gì?

**Trả lời:**

Module là tập hợp cấu hình Terraform có thể tái sử dụng.

Ví dụ:

```text
modules/
├── network/
├── kubernetes/
├── database/
└── monitoring/
```

Root Module gọi Child Module:

```hcl
module "database" {
  source      = "./modules/database"
  environment = "production"
}
```

Variables, locals và outputs giúp module linh hoạt và có thể kết hợp. ([HashiCorp Developer][15])

---

## 54. Lợi ích của Module là gì?

**Trả lời:**

* Giảm lặp code.
* Chuẩn hóa hạ tầng.
* Dễ tạo nhiều môi trường.
* Dễ review.
* Che giấu chi tiết triển khai.
* Có thể version hóa.

Không nên tạo module chỉ chứa một resource đơn giản nếu không mang lại khả năng tái sử dụng hoặc abstraction có ý nghĩa.

## 55. `count` và `for_each` khác nhau thế nào?

**Trả lời:**

`count` tạo resource theo số lượng và xác định instance bằng chỉ số:

```hcl
count = 3
```

Địa chỉ:

```text
aws_instance.api[0]
aws_instance.api[1]
```

`for_each` tạo resource theo key:

```hcl
for_each = {
  api    = "t3.micro"
  worker = "t3.small"
}
```

Địa chỉ ổn định hơn:

```text
aws_instance.service["api"]
```

Với tập resource có danh tính riêng, `for_each` thường an toàn hơn khi thêm hoặc xóa phần tử.

---

## 56. Terraform tự xác định dependency như thế nào?

**Trả lời:**

Terraform tạo dependency graph từ các tham chiếu.

Ví dụ:

```hcl
subnet_id = aws_subnet.private.id
```

Terraform hiểu instance phụ thuộc vào subnet và tạo subnet trước.

---

## 57. Khi nào dùng `depends_on`?

**Trả lời:**

Dùng khi tồn tại dependency ẩn mà Terraform không thể suy ra từ tham chiếu dữ liệu.

```hcl
depends_on = [
  aws_iam_role_policy.api
]
```

Không nên lạm dụng vì có thể tạo kế hoạch bảo thủ và làm giảm khả năng chạy song song. HashiCorp khuyến nghị chỉ khai báo khi dependency không thể được suy luận tự động. ([HashiCorp Developer][16])

---

## 58. Lifecycle Block là gì?

**Trả lời:**

Lifecycle Block tùy chỉnh cách Terraform quản lý vòng đời resource.

Ví dụ:

```hcl
lifecycle {
  prevent_destroy = true
}
```

Một số tùy chọn:

* `create_before_destroy`
* `prevent_destroy`
* `ignore_changes`
* `replace_triggered_by`

([HashiCorp Developer][17])

---

## 59. `create_before_destroy` dùng khi nào?

**Trả lời:**

Nó yêu cầu Terraform tạo resource mới trước khi xóa resource cũ.

Phù hợp khi muốn giảm downtime:

```hcl
lifecycle {
  create_before_destroy = true
}
```

Tuy nhiên, nhà cung cấp phải cho phép hai resource tồn tại đồng thời.

---

## 60. `prevent_destroy` dùng để làm gì?

**Trả lời:**

Nó làm Terraform từ chối kế hoạch xóa resource.

Phù hợp với:

* Production Database.
* Storage quan trọng.
* DNS zone.
* Resource chứa dữ liệu.

```hcl
lifecycle {
  prevent_destroy = true
}
```

Đây không thay thế backup hoặc phân quyền nhưng giúp ngăn thao tác nhầm. ([HashiCorp Developer][18])

---

## 61. `ignore_changes` dùng khi nào?

**Trả lời:**

Dùng khi một thuộc tính được quản lý bởi hệ thống khác và Terraform không nên liên tục hoàn tác thay đổi đó.

Ví dụ:

```hcl
lifecycle {
  ignore_changes = [
    desired_capacity
  ]
}
```

Có thể dùng khi Auto Scaling tự thay đổi số lượng instance.

Không nên dùng để che giấu drift chưa hiểu rõ.

---

## 62. Infrastructure Drift là gì?

**Trả lời:**

Drift xảy ra khi hạ tầng thật khác với cấu hình hoặc state Terraform.

Ví dụ:

```text
Terraform: 3 replicas
Người quản trị sửa thủ công: 5 replicas
```

Terraform `plan` hoặc `apply` thường refresh trạng thái thực tế để phát hiện chênh lệch. ([HashiCorp Developer][19])

---

## 63. Xử lý Drift như thế nào?

**Trả lời:**

Có hai hướng:

1. **Không chấp nhận thay đổi thủ công:** Chạy plan/apply để đưa hạ tầng về lại cấu hình.
2. **Chấp nhận thay đổi:** Cập nhật code Terraform để phản ánh trạng thái mới.

Không nên chỉ sửa state mà không hiểu nguyên nhân drift.

---

## 64. `terraform import` dùng để làm gì?

**Trả lời:**

`terraform import` đưa resource đã tồn tại vào Terraform State.

Ví dụ:

```bash
terraform import aws_s3_bucket.documents company-documents
```

Sau import, cần có cấu hình Terraform tương ứng để quản lý resource lâu dài.

Terraform hiện cũng hỗ trợ import block theo workflow plan/apply, giúp preview thay đổi và phù hợp hơn với CI/CD. ([HashiCorp Developer][20])

---

## 65. Import có tự động tạo đầy đủ Terraform code không?

**Trả lời:**

Không phải lúc nào cũng hoàn chỉnh.

Import chủ yếu tạo liên kết giữa resource thật và state. Với configuration-driven import, Terraform có thể hỗ trợ sinh cấu hình ban đầu, nhưng vẫn cần review và chuẩn hóa code. ([HashiCorp Developer][21])

---

## 66. `terraform state rm` làm gì?

**Trả lời:**

Lệnh này xóa liên kết giữa Terraform State và resource thật.

```bash
terraform state rm aws_s3_bucket.documents
```

Resource thật không bị xóa ngay, nhưng Terraform “quên” rằng nó đang quản lý resource đó. ([HashiCorp Developer][22])

---

## 67. Workspace trong Terraform là gì?

**Trả lời:**

CLI Workspace cho phép một cấu hình sử dụng nhiều state riêng biệt.

Ví dụ:

```text

development
staging
production
```

Tuy nhiên, với môi trường production phức tạp, nhiều nhóm ưu tiên tách thư mục hoặc cấu hình riêng để ranh giới rõ hơn.

---

## 68. Có nên dùng Workspace để quản lý mọi môi trường không?

**Trả lời:**

Không phải lúc nào cũng nên.

Workspace phù hợp khi các môi trường gần như giống nhau.

Không lý tưởng nếu:

* Production khác dev rất nhiều.
* Cần Backend hoặc credential khác.
* Cần quyền truy cập khác.
* Dễ apply nhầm workspace.

## 69. Sensitive Variable có bảo vệ hoàn toàn secret không?

**Trả lời:**

Không.

```hcl
variable "database_password" {
  type      = string
  sensitive = true

```

`sensitive = true` chủ yếu che giá trị khỏi một số output trên CLI.

Giá trị vẫn có thể:

Vì vậy state và plan phải được bảo vệ.

## 70. Có nên đưa secret vào file `.tfvars` rồi commit Git không?

**Trả lời:**

Không.

Nên sử dụng:

# IV. Kết hợp Vault và Terraform

## 71. Terraform có thể đọc secret từ Vault không?

**Trả lời:**

Có thể thông qua Vault Provider hoặc cơ chế xác thực phù hợp.

Ví dụ:

```text
Terraform
→ xác thực với Vault
→ đọc credential cần thiết
→ tạo resource Cloud
```

Tuy nhiên, cần nhớ giá trị được Terraform sử dụng có thể đi vào state hoặc plan tùy resource và Provider.

---

## 72. Có nên dùng Terraform để ghi mọi secret vào Vault không?

**Trả lời:**

Có thể dùng Terraform để:

* Enable Secrets Engine.
* Tạo policy.
* Cấu hình Auth Method.
* Cấu hình role.
* Tạo path hoặc metadata cần thiết.

Nhưng cần thận trọng khi truyền giá trị secret thực vào Terraform vì secret có thể xuất hiện trong state.

Một nguyên tắc tốt:

```text
Terraform quản lý cấu hình Vault
Vault quản lý giá trị secret
```

---

## 73. Terraform State có thể chứa secret từ Vault không?

**Trả lời:**

Có thể.

Dù output được đánh dấu sensitive, Provider hoặc resource vẫn có thể lưu giá trị trong state.

Do đó:

* State phải được mã hóa.
* Giới hạn quyền truy cập.
* Không commit Git.
* Có audit.
* Hạn chế đọc secret không cần thiết qua Terraform.

---

## 74. Terraform nên xác thực với Vault như thế nào trong CI/CD?

**Trả lời:**

Nên ưu tiên credential ngắn hạn và danh tính workload:

* OIDC/JWT.
* Cloud IAM.
* Kubernetes Auth.
* AppRole với Secret ID được phân phối an toàn.

Không nên lưu Vault Root Token hoặc token dài hạn trong pipeline.

---

## 75. Terraform và Vault có thay thế nhau không?

**Trả lời:**

Không.

* Terraform quản lý trạng thái hạ tầng.
* Vault quản lý secret, identity-based access và encryption.

Chúng thường được sử dụng cùng nhau.

# V. Câu hỏi tình huống phỏng vấn

## Tình huống 1: Secret bị commit lên Git

**Hỏi:** Bạn xử lý thế nào?

**Trả lời:**

1. Thu hồi hoặc rotate secret ngay.
2. Xóa secret khỏi code.
3. Chuyển secret vào Vault.
4. Kiểm tra Git history và log.
5. Xác định secret đã bị sử dụng trái phép chưa.
6. Bổ sung `.gitignore`, secret scanning và pre-commit hook.

Chỉ xóa dòng secret trong commit mới không làm secret biến mất khỏi lịch sử.

---

## Tình huống 2: Pod Kubernetes cần mật khẩu Database

**Hỏi:** Thiết kế bằng Vault thế nào?

**Trả lời:**

```text
Pod
→ Kubernetes Auth
→ Vault
→ Dynamic Database Credential
→ PostgreSQL
```

Vault cấp username/password có TTL cho Pod. Khi lease hết hạn hoặc Pod không còn cần dùng, credential được thu hồi.

---

## Tình huống 3: Vault Token của ứng dụng bị lộ

**Trả lời:**

Tôi sẽ:

1. Revoke token.
2. Revoke các token con và lease liên quan nếu cần.
3. Rotate secret mà token đã truy cập.
4. Kiểm tra audit log.
5. Giảm TTL và quyền policy.
6. Xác định nguyên nhân token bị lộ.
7. Chuyển sang authentication theo workload nếu đang dùng token tĩnh.

---

## Tình huống 4: Hai pipeline chạy `terraform apply` cùng lúc

**Hỏi:** Có rủi ro gì?

**Trả lời:**

Có thể:

* Ghi đè state.
* Tạo thay đổi xung đột.
* Xóa hoặc cập nhật resource sai.
* Làm state không khớp hạ tầng.

Cần Remote Backend hỗ trợ State Locking và giới hạn concurrency của pipeline.

---

## Tình huống 5: Terraform định xóa Production Database

**Hỏi:** Bạn làm gì?

**Trả lời:**

Không apply ngay.

Tôi sẽ:

1. Kiểm tra `terraform plan`.
2. Xác định thay đổi code hoặc state gây ra việc replace/delete.
3. Kiểm tra resource address có bị đổi không.
4. Kiểm tra Provider upgrade.
5. Cân nhắc dùng `moved` block nếu chỉ refactor.
6. Bảo vệ bằng `prevent_destroy`.
7. Backup Database.
8. Chỉ apply sau khi hiểu rõ tác động.

---

## Tình huống 6: Resource đã được tạo thủ công trên Cloud

**Hỏi:** Làm sao đưa vào Terraform?

**Trả lời:**

1. Viết hoặc sinh cấu hình Terraform.
2. Dùng `import` block hoặc `terraform import`.
3. Chạy `terraform plan`.
4. Điều chỉnh code đến khi plan không tạo thay đổi ngoài ý muốn.
5. Đưa code vào version control.

---

## Tình huống 7: Đổi tên resource trong code khiến Terraform muốn xóa và tạo lại

**Hỏi:** Xử lý thế nào?

**Trả lời:**

Terraform nhận diện resource bằng địa chỉ trong state. Khi đổi tên, Terraform có thể nghĩ resource cũ bị xóa và resource mới cần được tạo.

Nên dùng `moved` block hoặc lệnh state phù hợp để chuyển địa chỉ mà không phá hủy resource thật.

---

## Tình huống 8: Người quản trị sửa hạ tầng thủ công

**Hỏi:** Terraform sẽ làm gì?

**Trả lời:**

Terraform sẽ phát hiện drift khi refresh và lập kế hoạch:

* Hoàn tác thay đổi để khớp code.
* Hoặc yêu cầu cập nhật code nếu tổ chức muốn giữ thay đổi.

Không nên apply mà chưa review vì Terraform có thể ghi đè thay đổi thủ công. ([HashiCorp Developer][23])

---

## Tình huống 9: Pipeline cần dùng Cloud Credential để chạy Terraform

**Trả lời:**

Nên ưu tiên:

* OIDC.
* Workload Identity.
* Credential ngắn hạn.
* Vault Dynamic Cloud Credentials.

Không nên dùng access key dài hạn được lưu cố định trong repository hoặc biến môi trường không kiểm soát.

---

## Tình huống 10: `terraform apply` thất bại giữa chừng

**Hỏi:** Có rollback toàn bộ tự động không?

**Trả lời:**

Không nên giả định Terraform rollback toàn bộ.

Một số resource có thể đã được tạo hoặc cập nhật.

Cần:

1. Đọc lỗi.
2. Kiểm tra state.
3. Kiểm tra hạ tầng thật.
4. Sửa cấu hình hoặc quyền.
5. Chạy lại `terraform plan`.
6. Apply tiếp để đưa hệ thống về trạng thái mong muốn.

# VI. Câu hỏi nâng cao

## 76. Terraform có phải công cụ cấu hình bên trong Server không?

**Trả lời:**

Terraform mạnh nhất trong provisioning và quản lý resource hạ tầng.

Nó có thể chạy một số provisioner, nhưng không nên dùng provisioner làm phương pháp chính để cấu hình toàn bộ hệ điều hành.

Có thể kết hợp:

* Terraform tạo Server.
* Cloud-init, Ansible hoặc image được chuẩn bị sẵn cấu hình Server.

---

## 77. Vì sao hạn chế dùng `local-exec` và `remote-exec`?

**Trả lời:**

Vì chúng:

* Khó đảm bảo idempotent.
* Khó theo dõi trong state.
* Phụ thuộc môi trường chạy Terraform.
* Khó xử lý lỗi và rollback.
* Có thể làm cấu hình trở nên imperative.

Chỉ nên dùng khi không có resource hoặc Provider phù hợp.

---

## 78. Provider Version Locking là gì?

**Trả lời:**

Nên giới hạn version Provider:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
```

Terraform tạo file `.terraform.lock.hcl` để khóa phiên bản Provider được chọn.

Nên commit lock file để CI và máy lập trình viên dùng cùng phiên bản.

---

## 79. Terraform Plan File có nhạy cảm không?

**Trả lời:**

Có thể.

Saved plan có thể chứa:

* Dữ liệu cấu hình.
* Giá trị nhạy cảm.
* Thông tin Backend.
* Credential ngắn hạn trong một số trường hợp.

HashiCorp lưu ý rằng khi apply một saved plan, Terraform dùng cấu hình Backend được lưu trong plan; credential ngắn hạn có thể hết hạn giữa plan và apply. ([HashiCorp Developer][24])

---

## 80. Least Privilege nên áp dụng thế nào cho Vault và Terraform?

**Trả lời:**

### Với Vault

* Mỗi ứng dụng có policy riêng.
* Chỉ cho phép đúng path cần thiết.
* Token có TTL ngắn.
* Không dùng Root Token.

### Với Terraform

* Pipeline chỉ có quyền quản lý resource cần thiết.
* Tách quyền dev và production.
* State Backend có quyền riêng.
* Production apply cần phê duyệt.
* Không dùng Cloud Admin credential nếu không cần.

# VII. Câu trả lời ngắn nên ghi nhớ

**Vault là gì?**

> Vault là hệ thống quản lý secret và mã hóa dựa trên danh tính, hỗ trợ secret tĩnh, dynamic credential, lease, rotation và audit.

**Terraform là gì?**

> Terraform là công cụ Infrastructure as Code dùng để khai báo và quản lý hạ tầng bằng cấu hình.

**Dynamic Secret là gì?**

> Dynamic Secret được Vault tạo theo yêu cầu, có TTL và có thể tự động bị thu hồi.

**Policy trong Vault là gì?**

> Policy xác định danh tính được phép thực hiện capability nào trên những path nào.

**Terraform State là gì?**

> State ánh xạ resource trong code với resource thật và giúp Terraform xác định thay đổi cần thực hiện.

**Remote Backend để làm gì?**

> Remote Backend lưu state dùng chung, hỗ trợ kiểm soát truy cập, backup và state locking.

**`plan` khác `apply` thế nào?**

> `plan` xem trước thay đổi; `apply` thực thi thay đổi.

**Terraform có nên lưu secret không?**

> Nên hạn chế vì secret có thể xuất hiện trong state; dùng Vault hoặc Secret Manager để quản lý giá trị bí mật.
