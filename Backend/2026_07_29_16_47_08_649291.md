Dưới đây là bộ câu hỏi phỏng vấn về **Git** mà rất nhiều công ty sử dụng khi tuyển **Fresher/Junior Backend, Frontend, Fullstack**. Mình tập trung vào các **tình huống thực tế** thay vì chỉ hỏi lệnh Git.

---

# 1. Git là gì?

**Trả lời**

Git là một hệ thống quản lý phiên bản phân tán (Distributed Version Control System).

Git giúp:

* Quản lý lịch sử source code
* Làm việc nhóm
* Theo dõi thay đổi
* Khôi phục phiên bản cũ
* Hỗ trợ merge code

---

# 2. Git khác GitHub như thế nào?

**Trả lời**

Git là công cụ quản lý phiên bản.

GitHub là dịch vụ lưu trữ Git Repository trên cloud.

Ngoài GitHub còn có:

* GitLab
* Bitbucket
* Azure DevOps

---

# 3. Repository là gì?

Là nơi chứa toàn bộ source code và lịch sử commit.

Có hai loại:

* Local Repository
* Remote Repository

---

# 4. Clone và Fork khác nhau?

### Clone

Tải Repository về máy.

```
git clone https://...
```

---

### Fork

Tạo bản sao Repository trên tài khoản GitHub của mình.

Thường dùng khi đóng góp mã nguồn mở.

---

# 5. Commit là gì?

Lưu lại một phiên bản của source code.

Ví dụ:

```
git commit -m "Add login API"
```

---

# 6. HEAD là gì?

HEAD là con trỏ đang chỉ tới commit hiện tại.

Ví dụ:

```
HEAD
 ↓
commit A
```

---

# 7. Branch là gì?

Là một nhánh phát triển độc lập.

Ví dụ:

```
main

develop

feature/login

bugfix/auth
```

---

# 8. Vì sao phải tạo branch?

Để:

* Không ảnh hưởng main
* Làm nhiều tính năng song song
* Dễ review code

---

# 9. Khi nào dùng Merge?

Khi hoàn thành feature và muốn gộp vào branch chính.

Ví dụ:

```
feature/login

↓

develop
```

---

# 10. Merge khác Rebase?

### Merge

Giữ nguyên lịch sử.

Sinh Merge Commit.

```
A-B-C
     \
      D-E

↓

Merge
```

---

### Rebase

Viết lại lịch sử commit.

Lịch sử đẹp hơn.

```
A-B-C-D-E
```

---

# 11. Khi nào nên dùng Rebase?

Thường dùng:

```
git pull --rebase
```

để tránh tạo nhiều Merge Commit không cần thiết.

---

# 12. Pull là gì?

```
git pull
```

=

```
git fetch

+

git merge
```

---

# 13. Fetch khác Pull?

### Fetch

Chỉ tải commit mới.

Không merge.

---

### Pull

Tải và merge luôn.

---

# 14. Push là gì?

Đẩy commit từ Local lên Remote.

---

# 15. Nếu Push bị từ chối?

Ví dụ:

```
non-fast-forward
```

Nguyên nhân:

Có người khác đã push trước.

Cách xử lý:

```
git pull

resolve conflict

git push
```

---

# 16. Conflict là gì?

Hai người sửa cùng một dòng code.

Git không biết chọn ai.

Ví dụ:

```
<<<<<<< HEAD

A

=======

B

>>>>>>> feature
```

---

# 17. Bạn xử lý Conflict như thế nào?

1. Mở file.
2. Chọn nội dung đúng.
3. Xóa marker.
4. Add.
5. Commit.

```

# 19. Nếu quên thêm file vào commit?

git commit --amend

```

```

---

# 24. reset và revert khác nhau?

### reset

Quay về commit cũ.

Viết lại lịch sử.

---

### revert

Tạo commit mới để hoàn tác.

Không thay đổi lịch sử.

Thường dùng trên branch dùng chung.

---

# 25. Khi nào dùng revert?

Ví dụ:

Đã push lên main.

Không nên reset.

Nên:

```
git revert
```

---

# 26. stash là gì?

Lưu tạm thay đổi chưa commit.

```

```

Sau đó:

```
git stash pop
```

---

# 27. Khi nào dùng stash?

Ví dụ:

Đang code.

```

...

```

```

# 31. Vì sao không nên commit file .env?

Vì chứa:

* API Key
* Database Password
* JWT Secret
* Token

Nếu commit sẽ gây rò rỉ thông tin.

---

# 32. Nếu lỡ commit file .env thì làm gì?

* Xóa khỏi Git.
* Thay đổi (rotate) toàn bộ khóa bí mật đã lộ.
* Nếu đã đẩy lên remote, cần xóa lịch sử bằng công cụ phù hợp (ví dụ `git filter-repo` hoặc BFG) nếu cần, đồng thời cập nhật lại secret trên hệ thống.

# 33. Git Flow là gì?

# 35. Nếu push nhầm branch main?

Nếu chưa Merge:

Có thể:

```

```

Hoặc reset (nếu được phép và chưa có ai sử dụng commit đó).

---

# 36. Nếu checkout branch bị báo "Your local changes would be overwritten"?

Nguyên nhân:

Có thay đổi chưa commit.

Cách xử lý:

* Commit
* Hoặc stash
* Hoặc restore nếu không cần giữ

---

# 37. Detached HEAD là gì?

HEAD đang trỏ trực tiếp tới commit.

Không ở branch nào.

Nếu muốn giữ thay đổi:

```
git switch -c new-branch
```

---

# 38. Fast-forward Merge là gì?

Nếu branch chính chưa có commit mới kể từ khi tạo nhánh, Git chỉ cần di chuyển con trỏ branch lên commit mới mà không tạo Merge Commit.

---

# 39. Nếu xóa nhầm branch thì sao?

Nếu commit vẫn còn trong lịch sử:

```
git reflog
```

Tìm commit.

Sau đó:

```
git checkout -b recover <commit>
```

---

# 40. Git reflog dùng để làm gì?

Hiển thị lịch sử di chuyển của HEAD.

Có thể cứu:

* Commit
* Branch
* Reset nhầm

---

# 41. Bạn thường làm việc Git theo quy trình nào?

**Trả lời mẫu**

1. Pull code mới nhất từ `develop`.
2. Tạo branch `feature/...`.
3. Code và commit với message rõ ràng.
4. Push branch lên remote.
5. Tạo Pull Request.
6. Code Review.
7. Sửa theo góp ý nếu có.
8. Merge vào `develop`.

---

# 42. Nếu Pull Request có Conflict?

**Trả lời**

1. Cập nhật branch đích (`develop` hoặc `main`).
2. Merge hoặc rebase branch đích vào branch của mình.
3. Giải quyết conflict.
4. Test lại toàn bộ.
5. Push lên remote để cập nhật Pull Request.

**Ví dụ**

```

```

---

# 44. Nếu đã push commit lên remote nhưng phát hiện bug?

**Trả lời**

* Nếu chưa merge: sửa và push thêm commit hoặc dùng `git commit --amend` + `git push --force-with-lease` (chỉ khi được phép và không ảnh hưởng người khác).
* Nếu đã merge vào branch dùng chung: tạo commit sửa hoặc `git revert` nếu cần hoàn tác tính năng.

---

# 45. Vì sao hạn chế dùng `git push --force`?

**Trả lời**

Vì có thể ghi đè lịch sử commit trên remote và làm mất commit của người khác.

Nếu buộc phải ghi đè lịch sử branch cá nhân, nên ưu tiên:

```
git push --force-with-lease
```

vì lệnh này kiểm tra remote chưa bị người khác cập nhật trước khi ghi đè.

## 5 câu tình huống phỏng vấn rất hay gặp

### Tình huống 1

**Hỏi:** Bạn đang code dở, chưa commit nhưng cần chuyển sang sửa bug gấp ở branch khác. Bạn làm gì?

**Đáp:** Dùng `git stash`, chuyển branch, sửa bug, sau đó quay lại và `git stash pop`.

---

### Tình huống 2

**Hỏi:** Bạn vừa `git reset --hard` nhầm. Có cách cứu không?

**Đáp:** Kiểm tra `git reflog`, tìm commit cũ và tạo lại branch hoặc reset về commit đó nếu commit vẫn còn được Git lưu.

---

### Tình huống 3

**Hỏi:** Hai người cùng sửa một file và bị conflict. Bạn xử lý thế nào?

**Đáp:** Đọc phần conflict, chọn hoặc kết hợp nội dung đúng, xóa các marker (`<<<<<<<`, `=======`, `>>>>>>>`), sau đó `git add`, `git commit` (hoặc tiếp tục `git rebase` nếu đang rebase).

---

### Tình huống 4

**Hỏi:** Bạn lỡ commit file `.env` chứa API Key lên GitHub. Bạn làm gì?

**Đáp:** Xóa file khỏi repository, thay đổi toàn bộ API Key/Secret đã lộ, cân nhắc xóa lịch sử chứa secret nếu cần và cập nhật `.gitignore` để tránh lặp lại.

---

### Tình huống 5

**Hỏi:** Khi nào nên dùng `merge`, khi nào nên dùng `rebase`?

**Đáp:** Dùng `merge` khi muốn giữ nguyên lịch sử commit và phù hợp với làm việc nhóm. Dùng `rebase` để cập nhật branch cá nhân hoặc làm sạch lịch sử trước khi merge, tránh rebase các commit đã được nhiều người cùng sử dụng trên remote.
