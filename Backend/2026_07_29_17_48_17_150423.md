Dưới đây là bộ câu hỏi phỏng vấn về **SQL, MySQL, PostgreSQL, MongoDB và Vector Database**, phù hợp với vị trí **Lập trình viên Fresher/Junior Backend, AI hoặc Microservices**.

# I. Tổng quan Database

## 1. Database là gì?

**Trả lời:**

Database là hệ thống dùng để lưu trữ, quản lý và truy vấn dữ liệu.

Các nhóm phổ biến:

* Cơ sở dữ liệu quan hệ: MySQL, PostgreSQL.
* Cơ sở dữ liệu NoSQL: MongoDB.
* Vector Database: Pinecone, Qdrant, Milvus.

---

## 2. DBMS là gì?

**Trả lời:**

DBMS là hệ quản trị cơ sở dữ liệu, cung cấp các chức năng:

* Lưu dữ liệu.
* Truy vấn dữ liệu.
* Quản lý transaction.
* Phân quyền.
* Sao lưu và phục hồi.
* Kiểm soát truy cập đồng thời.

MySQL, PostgreSQL và MongoDB đều là các hệ quản trị cơ sở dữ liệu.

---

## 3. SQL và NoSQL khác nhau như thế nào?

| SQL                     | NoSQL                                   |
| ----------------------- | --------------------------------------- |
| Dữ liệu dạng bảng       | Nhiều mô hình dữ liệu                   |
| Schema thường chặt chẽ  | Schema linh hoạt hơn                    |
| Hỗ trợ JOIN mạnh        | Thường hạn chế JOIN                     |
| Transaction mạnh        | Tùy loại NoSQL                          |
| Phù hợp dữ liệu quan hệ | Phù hợp dữ liệu linh hoạt hoặc phân tán |

Không nên hiểu NoSQL là không có cấu trúc. NoSQL vẫn cần thiết kế dữ liệu cẩn thận.

---

## 4. Khi nào nên dùng SQL?

**Trả lời:**

SQL phù hợp khi:

* Dữ liệu có quan hệ rõ ràng.
* Cần transaction mạnh.
* Cần JOIN và truy vấn phức tạp.
* Cần đảm bảo tính toàn vẹn dữ liệu.
* Dữ liệu có cấu trúc ổn định.

Ví dụ:

* Thanh toán.
* Đơn hàng.
* Ngân hàng.
* Quản lý người dùng.

---

## 5. Khi nào nên dùng NoSQL?

**Trả lời:**

NoSQL phù hợp khi:

* Cấu trúc dữ liệu thay đổi thường xuyên.
* Dữ liệu dạng document tự nhiên.
* Cần scale ngang.
* Dữ liệu lồng nhau nhiều.
* Cần phát triển nhanh và không cần nhiều JOIN.

Ví dụ:

* Catalog sản phẩm.
* Nội dung bài viết.
* Log.
* Metadata.
* Session.

---

# II. SQL và cơ sở dữ liệu quan hệ

## 6. Primary Key là gì?

**Trả lời:**

Primary Key là cột hoặc nhóm cột dùng để định danh duy nhất một bản ghi.

Đặc điểm:

* Không trùng.
* Không được `NULL`.
* Một bảng chỉ có một Primary Key, nhưng có thể là khóa ghép.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    email VARCHAR(255) NOT NULL
);
```

---

## 7. Foreign Key là gì?

**Trả lời:**

Foreign Key tạo quan hệ giữa hai bảng và giúp đảm bảo tính toàn vẹn tham chiếu.

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Không thể tạo đơn hàng cho người dùng không tồn tại nếu ràng buộc được thực thi.

---

## 8. Unique Constraint khác Primary Key như thế nào?

**Trả lời:**

Primary Key:

* Dùng làm định danh chính.
* Không cho phép `NULL`.
* Một bảng có một Primary Key.

Unique Constraint:

* Đảm bảo giá trị không trùng.
* Một bảng có thể có nhiều Unique Constraint.
* Cách xử lý `NULL` có thể khác nhau giữa các DBMS.

---

## 9. Index là gì?

**Trả lời:**

Index là cấu trúc dữ liệu giúp Database tìm bản ghi nhanh hơn mà không phải quét toàn bộ bảng.

Ví dụ:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Index thường hữu ích cho các cột xuất hiện trong:

* `WHERE`.
* `JOIN`.
* `ORDER BY`.
* `GROUP BY`.

---

## 10. Nhược điểm của Index là gì?

**Trả lời:**

Index:

* Tốn dung lượng lưu trữ.
* Làm `INSERT`, `UPDATE`, `DELETE` chậm hơn.
* Tăng chi phí bảo trì.
* Có thể không được sử dụng nếu truy vấn viết không phù hợp.

Không nên tạo Index trên mọi cột.

---

## 11. Composite Index là gì?

**Trả lời:**

Composite Index là Index gồm nhiều cột.

```sql
CREATE INDEX idx_orders_user_created
ON orders(user_id, created_at);
```

Index này phù hợp với truy vấn:

```sql
SELECT *
FROM orders
WHERE user_id = 10
ORDER BY created_at DESC;
```

Thứ tự các cột trong Index rất quan trọng.

---

## 12. Leftmost Prefix Rule là gì?

**Trả lời:**

Với Index:

```text
(user_id, status, created_at)
```

Database thường có thể tận dụng tốt cho:

```text
user_id
user_id + status
user_id + status + created_at
```

Nhưng thường không tối ưu cho truy vấn chỉ có:

```text
status
created_at
```

vì thiếu cột đầu tiên của Index.

---

## 13. Clustered Index và Non-Clustered Index khác nhau thế nào?

**Trả lời:**

Clustered Index ảnh hưởng đến cách dữ liệu bảng được tổ chức hoặc lưu trữ vật lý, tùy DBMS.

Non-Clustered Index là cấu trúc riêng, chứa khóa và thông tin để tìm bản ghi.

Khái niệm này có cách triển khai khác nhau giữa MySQL, PostgreSQL và SQL Server nên không nên áp dụng máy móc.

---

## 14. Covering Index là gì?

**Trả lời:**

Covering Index chứa đủ các cột cần thiết để Database trả kết quả mà không phải đọc thêm dữ liệu từ bảng.

Ví dụ truy vấn:

```sql
SELECT user_id, created_at
FROM orders
WHERE user_id = 10;
```

Index:

```sql
CREATE INDEX idx_orders_user_created
ON orders(user_id, created_at);
```

có thể bao phủ truy vấn này.

---

## 15. Execution Plan là gì?

**Trả lời:**

Execution Plan mô tả cách Database thực thi truy vấn.

Có thể xem bằng:

```sql
EXPLAIN
SELECT *
FROM users
WHERE email = 'test@example.com';
```

Cần kiểm tra:

* Có dùng Index không.
* Có Full Table Scan không.
* Thứ tự JOIN.
* Số dòng dự kiến.
* Loại thuật toán JOIN.

---

## 16. Full Table Scan là gì?

**Trả lời:**

Full Table Scan là việc Database đọc toàn bộ bảng để tìm kết quả.

Nó không phải lúc nào cũng xấu. Với bảng nhỏ hoặc truy vấn trả phần lớn dữ liệu, quét toàn bảng có thể hợp lý.

---

## 17. INNER JOIN và LEFT JOIN khác nhau thế nào?

**Trả lời:**

`INNER JOIN` chỉ trả các bản ghi khớp ở cả hai bảng.

`LEFT JOIN` trả toàn bộ bản ghi bảng trái, kể cả khi bảng phải không có dữ liệu tương ứng.

```sql
SELECT users.id, orders.id
FROM users
LEFT JOIN orders ON orders.user_id = users.id;
```

Người dùng chưa có đơn hàng vẫn xuất hiện với dữ liệu `orders` bằng `NULL`.

---

## 18. WHERE và HAVING khác nhau thế nào?

**Trả lời:**

`WHERE` lọc dữ liệu trước khi nhóm.

`HAVING` lọc kết quả sau `GROUP BY`.

```sql
SELECT user_id, COUNT(*) AS total_orders
FROM orders
WHERE status = 'COMPLETED'
GROUP BY user_id
HAVING COUNT(*) >= 5;
```

---

## 19. UNION và UNION ALL khác nhau thế nào?

**Trả lời:**

`UNION` kết hợp dữ liệu và loại bỏ bản ghi trùng.

`UNION ALL` giữ nguyên bản ghi trùng và thường nhanh hơn.

---

## 20. Subquery và JOIN nên chọn cách nào?

**Trả lời:**

Không có lựa chọn luôn tốt hơn.

Nên xét:

* Khả năng đọc hiểu.
* Execution Plan.
* Kích thước dữ liệu.
* Index.
* Loại truy vấn.

Database hiện đại có thể tối ưu Subquery thành kế hoạch tương đương JOIN trong nhiều trường hợp.

---

# III. Transaction và đồng thời

## 21. Transaction là gì?

**Trả lời:**

Transaction là nhóm thao tác được thực hiện như một đơn vị.

Ví dụ chuyển tiền:

1. Trừ tiền tài khoản A.
2. Cộng tiền tài khoản B.

Nếu một bước lỗi, cần rollback toàn bộ.

---

## 22. ACID là gì?

**Trả lời:**

ACID gồm:

* **Atomicity:** Tất cả hoặc không thao tác nào được thực hiện.
* **Consistency:** Dữ liệu luôn tuân thủ quy tắc.
* **Isolation:** Transaction đồng thời không gây kết quả sai.
* **Durability:** Dữ liệu đã commit không bị mất khi hệ thống gặp sự cố.

---

## 23. Isolation Level là gì?

**Trả lời:**

Isolation Level xác định mức độ một Transaction nhìn thấy thay đổi của Transaction khác.

Các mức phổ biến:

* Read Uncommitted.
* Read Committed.
* Repeatable Read.
* Serializable.

Isolation càng cao thường càng an toàn nhưng có thể làm giảm khả năng xử lý đồng thời.

---

## 24. Dirty Read là gì?

**Trả lời:**

Dirty Read xảy ra khi một Transaction đọc dữ liệu chưa commit của Transaction khác.

Nếu Transaction kia rollback, dữ liệu đã đọc trở thành không hợp lệ.

---

## 25. Non-repeatable Read là gì?

**Trả lời:**

Một Transaction đọc cùng một bản ghi hai lần nhưng nhận hai giá trị khác nhau vì Transaction khác đã cập nhật và commit giữa hai lần đọc.

---

## 26. Phantom Read là gì?

**Trả lời:**

Một Transaction chạy cùng điều kiện truy vấn hai lần nhưng lần sau xuất hiện thêm hoặc mất các dòng do Transaction khác đã thêm hoặc xóa dữ liệu.

---

## 27. Deadlock là gì?

**Trả lời:**

Deadlock xảy ra khi hai Transaction giữ khóa mà Transaction kia cần.

Ví dụ:

```text
Transaction A giữ Row 1, chờ Row 2
Transaction B giữ Row 2, chờ Row 1
```

Database thường phát hiện và hủy một Transaction.

Cách hạn chế:

* Khóa tài nguyên theo cùng thứ tự.
* Transaction ngắn.
* Có Index phù hợp.
* Tránh giữ khóa trong lúc gọi mạng.

---

## 28. Optimistic Locking là gì?

**Trả lời:**

Optimistic Locking giả định xung đột ít xảy ra.

Thường dùng cột `version`:

```sql
UPDATE products
SET stock = 9,
    version = version + 1
WHERE id = 10
  AND version = 5;
```

Nếu không có dòng nào được cập nhật, dữ liệu đã bị thay đổi bởi Transaction khác.

---

## 29. Pessimistic Locking là gì?

**Trả lời:**

Pessimistic Locking khóa dữ liệu trước khi cập nhật.

Ví dụ:

```sql
SELECT *
FROM products
WHERE id = 10
FOR UPDATE;
```

Phù hợp khi xung đột cao nhưng có thể làm tăng thời gian chờ và nguy cơ deadlock.

---

# IV. MySQL

## 30. MySQL là gì?

**Trả lời:**

MySQL là hệ quản trị cơ sở dữ liệu quan hệ phổ biến, thường được sử dụng cho ứng dụng web, hệ thống CRUD và hệ thống giao dịch.

---

## 31. InnoDB là gì?

**Trả lời:**

InnoDB là Storage Engine phổ biến của MySQL, hỗ trợ:

* Transaction.
* Foreign Key.
* Row-level locking.
* Crash recovery.
* MVCC.

---

## 32. MySQL sử dụng MVCC để làm gì?

**Trả lời:**

MVCC giúp nhiều Transaction đọc và ghi đồng thời với ít xung đột hơn bằng cách duy trì các phiên bản dữ liệu.

Nó giúp các truy vấn đọc không phải lúc nào cũng chặn truy vấn ghi.

---

## 33. `AUTO_INCREMENT` dùng để làm gì?

**Trả lời:**

`AUTO_INCREMENT` tự sinh giá trị số tăng dần cho cột.

```sql
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL
);
```

Trong hệ thống phân tán, có thể cân nhắc UUID hoặc ID generator khác nếu nhiều nguồn cùng tạo ID.

---

## 34. `CHAR` và `VARCHAR` khác nhau thế nào?

**Trả lời:**

`CHAR` có độ dài cố định.

`VARCHAR` có độ dài thay đổi.

Ví dụ:

* Mã quốc gia có thể dùng `CHAR(2)`.
* Tên người dùng thường dùng `VARCHAR`.

---

## 35. Khi nào MySQL Index có thể không được sử dụng?

**Trả lời:**

Một số nguyên nhân:

* Dùng hàm trên cột Index.
* Ép kiểu không phù hợp.
* Điều kiện trả quá nhiều dòng.
* Sai thứ tự Composite Index.
* Dùng wildcard đầu chuỗi như `LIKE '%abc'`.
* Statistics khiến Optimizer chọn kế hoạch khác.

---

# V. PostgreSQL

## 36. PostgreSQL có điểm mạnh gì?

**Trả lời:**

PostgreSQL mạnh ở:

* Chuẩn SQL phong phú.
* Transaction và tính toàn vẹn dữ liệu.
* Truy vấn phức tạp.
* Kiểu dữ liệu đa dạng.
* JSON/JSONB.
* Extension.
* Window Function.
* Full-text search.
* Khả năng mở rộng.

---

## 37. JSON và JSONB trong PostgreSQL khác nhau thế nào?

**Trả lời:**

`JSON` lưu nội dung gần với chuỗi JSON ban đầu.

`JSONB` lưu dạng nhị phân đã phân tích, phù hợp hơn cho truy vấn và đánh Index.

Thông thường, nếu cần truy vấn field bên trong, nên cân nhắc `JSONB`.

```sql
CREATE TABLE events (
    id BIGSERIAL PRIMARY KEY,
    payload JSONB NOT NULL
);
```

---

## 38. GIN Index là gì?

**Trả lời:**

GIN Index phù hợp với dữ liệu chứa nhiều phần tử như:

* `JSONB`.
* Array.
* Full-text search.

Ví dụ:

```sql
CREATE INDEX idx_events_payload
ON events USING GIN(payload);
```

---

## 39. PostgreSQL Sequence là gì?

**Trả lời:**

Sequence là đối tượng sinh số tăng dần, thường được dùng cho Primary Key.

Các kiểu như `SERIAL` trước đây thường sử dụng Sequence bên dưới. Trong thiết kế mới, có thể dùng cột Identity.

---

## 40. `VACUUM` trong PostgreSQL dùng để làm gì?

**Trả lời:**

Do PostgreSQL sử dụng MVCC, các phiên bản dòng cũ không được xóa ngay.

`VACUUM` giúp:

* Thu hồi hoặc tái sử dụng không gian.
* Dọn dead tuples.
* Duy trì hiệu năng.
* Hỗ trợ tránh vấn đề transaction ID wraparound.

---

## 41. Window Function là gì?

**Trả lời:**

Window Function tính toán trên một nhóm dòng nhưng không gộp chúng thành một dòng như `GROUP BY`.

Ví dụ:

```sql
SELECT
    user_id,
    amount,
    ROW_NUMBER() OVER (
        PARTITION BY user_id
        ORDER BY created_at DESC
    ) AS row_number
FROM payments;
```

---

## 42. CTE là gì?

**Trả lời:**

CTE tạo kết quả tạm thời có tên trong một truy vấn.

```sql
WITH completed_orders AS (
    SELECT *
    FROM orders
    WHERE status = 'COMPLETED'
)
SELECT user_id, COUNT(*)
FROM completed_orders
GROUP BY user_id;
```

CTE giúp truy vấn dễ đọc và có thể dùng cho truy vấn đệ quy.

---

## 43. MySQL và PostgreSQL nên chọn hệ nào?

**Trả lời:**

MySQL phù hợp khi:

* Ứng dụng web thông thường.
* Đội ngũ đã quen MySQL.
* CRUD và transaction tiêu chuẩn.
* Hệ sinh thái đang phụ thuộc MySQL.

PostgreSQL phù hợp khi:

* Truy vấn phức tạp.
* Cần nhiều kiểu dữ liệu và Extension.
* Dùng `JSONB`, GIS hoặc full-text search.
* Cần tính năng SQL nâng cao.

Không nên chọn chỉ dựa vào việc hệ nào “nhanh hơn” vì hiệu năng phụ thuộc thiết kế và workload.

---

# VI. MongoDB

## 44. MongoDB là gì?

**Trả lời:**

MongoDB là Document Database, lưu dữ liệu dưới dạng document gần giống JSON, thực tế sử dụng định dạng BSON.

Ví dụ:

```json
{
  "_id": "user-1",
  "name": "Nghia",
  "skills": ["Python", "NestJS"],
  "address": {
    "city": "Hanoi"
  }
}
```

---

## 45. Collection và Document là gì?

**Trả lời:**

* Collection tương tự bảng.
* Document tương tự một bản ghi.
* Field tương tự cột.

Tuy nhiên, các Document trong cùng Collection không nhất thiết có cấu trúc hoàn toàn giống nhau.

---

## 46. BSON là gì?

**Trả lời:**

BSON là định dạng nhị phân dùng để lưu Document trong MongoDB.

BSON hỗ trợ nhiều kiểu dữ liệu hơn JSON, ví dụ:

* Date.
* Binary.
* ObjectId.
* Decimal.

---

## 47. ObjectId là gì?

**Trả lời:**

ObjectId là kiểu ID thường được MongoDB tự động tạo cho trường `_id`.

Nó được thiết kế để có xác suất trùng rất thấp trong môi trường phân tán.

---

## 48. Embedding và Referencing khác nhau thế nào?

**Trả lời:**

Embedding lưu dữ liệu liên quan bên trong cùng Document.

```json
{
  "_id": 1,
  "items": [
    {"productId": 10, "quantity": 2}
  ]
}
```

Referencing lưu ID trỏ đến Document khác.

```json
{
  "_id": 1,
  "userId": 100
}
```

Embedding phù hợp khi dữ liệu thường được đọc cùng nhau và kích thước có giới hạn.

Referencing phù hợp khi dữ liệu lớn, được dùng chung hoặc thay đổi độc lập.

---

## 49. MongoDB có hỗ trợ JOIN không?

**Trả lời:**

MongoDB có thể kết hợp Collection bằng Aggregation Stage như `$lookup`.

Tuy nhiên, nếu hệ thống phụ thuộc nhiều vào JOIN phức tạp, SQL Database có thể phù hợp hơn.

---

## 50. Aggregation Pipeline là gì?

**Trả lời:**

Aggregation Pipeline xử lý Document qua nhiều giai đoạn.

Ví dụ:

```javascript
db.orders.aggregate([
  {
    $match: {
      status: "COMPLETED"
    }
  },
  {
    $group: {
      _id: "$userId",
      total: {
        $sum: "$amount"
      }
    }
  }
]);
```

Các stage phổ biến:

* `$match`.
* `$project`.
* `$group`.
* `$sort`.
* `$lookup`.
* `$unwind`.

---

## 51. MongoDB Index hoạt động như thế nào?

**Trả lời:**

MongoDB hỗ trợ nhiều loại Index:

* Single-field Index.
* Compound Index.
* Multikey Index.
* Text Index.
* TTL Index.
* Geospatial Index.

Index giúp truy vấn nhanh nhưng cũng làm thao tác ghi tốn chi phí hơn.

---

## 52. Multikey Index là gì?

**Trả lời:**

Multikey Index được MongoDB tạo khi đánh Index lên field dạng Array.

Ví dụ:

```javascript
db.users.createIndex({
  skills: 1
});
```

---

## 53. TTL Index là gì?

**Trả lời:**

TTL Index cho phép tự động xóa Document sau một thời gian.

Phù hợp với:

* Session.
* Token tạm thời.
* Log ngắn hạn.
* Dữ liệu cache.

---

## 54. Replica Set trong MongoDB là gì?

**Trả lời:**

Replica Set là nhóm MongoDB Server giữ các bản sao dữ liệu.

Thông thường gồm:

* Primary nhận ghi.
* Secondary sao chép dữ liệu.
* Có thể bầu Primary mới khi Primary cũ lỗi.

---

## 55. Sharding trong MongoDB là gì?

**Trả lời:**

Sharding chia dữ liệu trên nhiều máy dựa vào Shard Key.

Nó giúp scale ngang khi dữ liệu hoặc throughput lớn.

Việc chọn Shard Key rất quan trọng để tránh:

* Hot shard.
* Phân phối dữ liệu không đều.
* Truy vấn phải quét nhiều shard.

---

## 56. MongoDB có hỗ trợ Transaction không?

**Trả lời:**

Có.

MongoDB hỗ trợ Transaction trên nhiều Document trong các cấu hình phù hợp.

Tuy nhiên, nếu thường xuyên cần Transaction phức tạp trên nhiều Collection, cần xem lại mô hình dữ liệu hoặc cân nhắc SQL Database.

---

# VII. Vector Database

## 57. Vector Database là gì?

**Trả lời:**

Vector Database là hệ thống được tối ưu để lưu trữ và tìm kiếm Vector Embedding.

Vector thường biểu diễn ý nghĩa của:

* Văn bản.
* Hình ảnh.
* Âm thanh.
* Sản phẩm.
* Người dùng.

---

## 58. Embedding là gì?

**Trả lời:**

Embedding là một mảng số biểu diễn đặc trưng hoặc ngữ nghĩa của dữ liệu.

Ví dụ:

```text
"Thanh toán đơn hàng"
→ [0.12, -0.31, 0.84, ...]
```

Các nội dung có ý nghĩa gần nhau thường có Vector gần nhau trong không gian Vector.

---

## 59. Vector Dimension là gì?

**Trả lời:**

Dimension là số phần tử trong một Vector.

Ví dụ:

```text
[0.1, 0.2, 0.3]
```

có 3 chiều.

Dimension của dữ liệu lưu trong Collection hoặc Index phải phù hợp với mô hình Embedding được sử dụng.

---

## 60. Similarity Search là gì?

**Trả lời:**

Similarity Search tìm các Vector gần nhất với Vector truy vấn.

Quy trình:

```text
Câu hỏi người dùng
→ Embedding model
→ Query vector
→ Vector Database
→ Top-k vector gần nhất
```

---

## 61. Cosine Similarity là gì?

**Trả lời:**

Cosine Similarity đo độ tương đồng về hướng giữa hai Vector.

Nó thường được dùng khi quan tâm đến ngữ nghĩa hơn độ lớn tuyệt đối của Vector.

Giá trị càng lớn thường biểu thị mức độ tương đồng càng cao, tùy cách hệ thống định nghĩa score.

---

## 62. Euclidean Distance là gì?

**Trả lời:**

Euclidean Distance đo khoảng cách đường thẳng giữa hai Vector.

Khoảng cách càng nhỏ thì hai Vector càng gần nhau.

---

## 63. Dot Product là gì?

**Trả lời:**

Dot Product nhân các phần tử tương ứng rồi cộng lại.

Nó có thể được sử dụng làm độ đo tương đồng, đặc biệt khi mô hình Embedding được huấn luyện phù hợp với metric này.

---

## 64. Vector Database khác Database thông thường thế nào?

**Trả lời:**

Database thông thường tối ưu cho:

* Tra cứu chính xác.
* Điều kiện bằng nhau.
* Range query.
* JOIN.
* Transaction.

Vector Database tối ưu cho:

* Nearest-neighbor search.
* Tìm kiếm theo ngữ nghĩa.
* Truy vấn Vector nhiều chiều.
* Approximate similarity search.

Hai loại Database thường được dùng kết hợp, không nhất thiết thay thế nhau.

---

## 65. ANN là gì?

**Trả lời:**

ANN là Approximate Nearest Neighbor.

Thay vì tìm chính xác tất cả Vector gần nhất bằng cách quét toàn bộ dữ liệu, ANN sử dụng Index để trả kết quả gần đúng nhanh hơn.

Đây là sự đánh đổi giữa:

* Tốc độ.
* Bộ nhớ.
* Độ chính xác hoặc recall.

---

## 66. HNSW là gì?

**Trả lời:**

HNSW là một thuật toán Index dạng đồ thị nhiều tầng dùng cho tìm kiếm Vector gần nhất.

Ưu điểm:

* Tốc độ truy vấn tốt.
* Recall cao.

Nhược điểm:

* Dùng nhiều bộ nhớ.
* Xây dựng Index có thể tốn chi phí.

---

## 67. IVF là gì?

**Trả lời:**

IVF chia Vector thành nhiều cụm.

Khi truy vấn, hệ thống chỉ tìm trong một số cụm gần Query Vector thay vì quét toàn bộ dữ liệu.

Tham số cấu hình ảnh hưởng đến tốc độ và recall.

---

## 68. Top-k là gì?

**Trả lời:**

Top-k là số lượng kết quả gần nhất cần lấy.

Ví dụ:

```text
top_k = 5
```

Vector Database trả về năm Vector gần Query Vector nhất.

Top-k quá nhỏ có thể bỏ sót thông tin; quá lớn có thể đưa nhiều nhiễu vào hệ thống.

---

## 69. Metadata Filtering là gì?

**Trả lời:**

Metadata Filtering lọc kết quả Vector theo điều kiện có cấu trúc.

Ví dụ chỉ tìm tài liệu:

* Thuộc lĩnh vực pháp luật.
* Có trạng thái published.
* Thuộc người dùng hiện tại.
* Được tạo sau một ngày cụ thể.

```json
{
  "category": "legal",
  "status": "published"
}
```

---

## 70. Hybrid Search là gì?

**Trả lời:**

Hybrid Search kết hợp:

* Vector Search.
* Keyword hoặc lexical search.

Vector Search tốt cho ngữ nghĩa.

Keyword Search tốt cho:

* Tên riêng.
* Mã văn bản.
* Thuật ngữ chính xác.
* Số hiệu.

Hybrid Search thường cho kết quả tốt hơn trong hệ thống RAG.

---

# VIII. Pinecone, Qdrant và Milvus

## 71. Pinecone là gì?

**Trả lời:**

Pinecone là dịch vụ Vector Database được quản lý.

Phù hợp khi:

* Muốn giảm công việc vận hành.
* Cần triển khai nhanh.
* Muốn sử dụng API quản lý sẵn.
* Không muốn tự quản lý Cluster Vector Database.

Đổi lại, hệ thống phụ thuộc nhiều hơn vào dịch vụ bên ngoài và mô hình chi phí của nhà cung cấp.

---

## 72. Qdrant là gì?

**Trả lời:**

Qdrant là Vector Database tập trung vào Vector Search và Payload Filtering.

Qdrant có thể được:

* Tự triển khai.
* Chạy bằng Docker hoặc Kubernetes.
* Sử dụng dưới dạng dịch vụ quản lý.

Qdrant phù hợp khi cần kiểm soát hạ tầng và filter metadata linh hoạt.

---

## 73. Milvus là gì?

**Trả lời:**

Milvus là Vector Database mã nguồn mở hướng đến workload Vector Search lớn.

Milvus phù hợp khi:

* Dữ liệu Vector lớn.
* Cần kiến trúc phân tán.
* Có đội ngũ vận hành hạ tầng.
* Cần tùy chỉnh Index và khả năng mở rộng.

---

## 74. Pinecone, Qdrant và Milvus khác nhau cơ bản thế nào?

| Pinecone                     | Qdrant                          | Milvus                            |
| ---------------------------- | ------------------------------- | --------------------------------- |
| Dịch vụ quản lý là trọng tâm | Mã nguồn mở và có Cloud         | Mã nguồn mở, hướng đến quy mô lớn |
| Vận hành đơn giản            | Triển khai tương đối thuận tiện | Kiến trúc có thể phức tạp hơn     |
| Ít kiểm soát hạ tầng hơn     | Kiểm soát tốt                   | Tùy chỉnh và scale mạnh           |
| Phù hợp triển khai nhanh     | Phù hợp nhiều hệ thống RAG      | Phù hợp dữ liệu rất lớn           |

Lựa chọn phụ thuộc vào quy mô, ngân sách, yêu cầu tự quản lý và năng lực vận hành.

---

## 75. Collection, Index và Namespace trong VectorDB là gì?

**Trả lời:**

Tên gọi phụ thuộc sản phẩm, nhưng thường dùng để phân tách hoặc tổ chức Vector.

Ví dụ có thể tách theo:

* Môi trường `dev`, `test`, `prod`.
* Tenant.
* Loại tài liệu.
* Mô hình Embedding.

Không nên trộn Vector từ các mô hình có dimension hoặc cách biểu diễn khác nhau trong cùng một Index không tương thích.

---

# IX. Vector Database và RAG

## 76. RAG là gì?

**Trả lời:**

RAG là Retrieval-Augmented Generation.

Quy trình:

```text
Tài liệu
→ Chia đoạn
→ Tạo Embedding
→ Lưu Vector Database

Câu hỏi
→ Tạo Query Embedding
→ Tìm đoạn liên quan
→ Đưa context vào LLM
→ Sinh câu trả lời
```

---

## 77. Chunking là gì?

**Trả lời:**

Chunking là chia tài liệu thành các đoạn nhỏ trước khi tạo Embedding.

Chunk quá lớn:

* Chứa nhiều nội dung không liên quan.
* Tốn token.
* Khó tìm chính xác.

Chunk quá nhỏ:

* Mất ngữ cảnh.
* Tạo quá nhiều Vector.
* Có thể làm kết quả rời rạc.

---

## 78. Chunk overlap để làm gì?

**Trả lời:**

Overlap giữ lại một phần nội dung giữa hai Chunk liên tiếp để tránh mất ngữ cảnh tại ranh giới.

Ví dụ:

```text
Chunk 1: từ 1 đến 500
Chunk 2: từ 450 đến 950
```

50 đơn vị cuối của Chunk 1 xuất hiện lại trong Chunk 2.

---

## 79. Reranking là gì?

**Trả lời:**

Reranking là bước sắp xếp lại các kết quả do Vector Database trả về bằng một mô hình chính xác hơn.

Ví dụ:

1. VectorDB lấy Top 20.
2. Reranker chấm điểm lại.
3. Chọn Top 5 đưa vào LLM.

Điều này có thể tăng chất lượng truy xuất nhưng làm tăng độ trễ và chi phí.

---

## 80. Vector Search trả kết quả không liên quan, bạn kiểm tra gì?

**Trả lời:**

Tôi sẽ kiểm tra:

1. Mô hình Embedding có phù hợp ngôn ngữ và lĩnh vực không.
2. Chunk size và overlap.
3. Có dùng đúng metric không.
4. Query và document có dùng cùng mô hình không.
5. Metadata Filter có đúng không.
6. Top-k có quá nhỏ hoặc quá lớn không.
7. Dữ liệu có được làm sạch không.
8. Có cần Hybrid Search hoặc Reranking không.

---

# X. Câu hỏi tình huống phỏng vấn

## Tình huống 1: Truy vấn SQL chậm

**Hỏi:** Bảng có hàng triệu bản ghi, truy vấn theo `email` bị chậm. Bạn làm gì?

**Trả lời:**

Tôi sẽ:

1. Chạy `EXPLAIN`.
2. Kiểm tra Index trên `email`.
3. Kiểm tra kiểu dữ liệu có khớp không.
4. Kiểm tra truy vấn có dùng hàm trên `email` không.
5. Kiểm tra số bản ghi trả về.
6. Kiểm tra Statistics và Execution Plan.

Không nên thêm Index trước khi xác định nguyên nhân.

---

## Tình huống 2: Lưu Product Catalog

**Hỏi:** Sản phẩm có thuộc tính khác nhau giữa từng loại. Chọn SQL hay MongoDB?

**Trả lời:**

MongoDB có thể phù hợp nếu mỗi nhóm sản phẩm có cấu trúc thuộc tính khác nhau và dữ liệu thường được đọc theo Document.

Tuy nhiên, nếu hệ thống có quan hệ phức tạp, transaction và báo cáo SQL mạnh, có thể dùng PostgreSQL với bảng quan hệ hoặc `JSONB`.

---

## Tình huống 3: Lưu đơn hàng và thanh toán

**Hỏi:** Chọn MongoDB hay PostgreSQL?

**Trả lời:**

Tôi ưu tiên PostgreSQL hoặc MySQL vì:

* Cần transaction.
* Cần tính toàn vẹn.
* Có nhiều quan hệ.
* Dữ liệu tài chính cần nhất quán.

MongoDB vẫn có thể dùng, nhưng SQL Database thường tự nhiên hơn cho bài toán này.

---

## Tình huống 4: MongoDB Document tăng quá lớn

**Hỏi:** Một User Document chứa toàn bộ lịch sử hoạt động và liên tục tăng. Bạn xử lý thế nào?

**Trả lời:**

Không nên nhúng danh sách không giới hạn.

Tôi sẽ tách lịch sử thành Collection riêng:

```text
users
user_activities
```

Document User chỉ giữ thông tin tóm tắt hoặc hoạt động gần nhất nếu cần.

---

## Tình huống 5: Thay đổi Embedding Model

**Hỏi:** Hệ thống đổi sang mô hình Embedding có dimension khác. Bạn làm gì?

**Trả lời:**

Tôi sẽ:

1. Tạo Collection hoặc Index mới.
2. Tạo lại Embedding cho toàn bộ dữ liệu.
3. Chạy song song hệ thống cũ và mới nếu cần.
4. Kiểm tra chất lượng truy xuất.
5. Chuyển traffic sang Index mới.
6. Chỉ xóa Index cũ khi đã xác nhận ổn định.

Không thể chỉ đưa Vector dimension mới vào Index cũ không tương thích.

---

## Tình huống 6: Cần phân quyền dữ liệu RAG theo người dùng

**Hỏi:** Làm sao ngăn User A tìm thấy tài liệu của User B?

**Trả lời:**

Lưu metadata:

```json
{
  "owner_id": "user-a",
  "document_id": "doc-100"
}
```

Khi truy vấn, luôn thêm filter theo `owner_id` hoặc tenant.

Ngoài ra cần kiểm tra quyền ở Application Layer; không chỉ dựa vào dữ liệu Client gửi.

---

## Tình huống 7: VectorDB bị mất dữ liệu gốc

**Hỏi:** Có thể khôi phục tài liệu từ Vector không?

**Trả lời:**

Không nên coi Vector là bản sao đầy đủ của dữ liệu gốc.

Nên lưu:

* File gốc trong Object Storage.
* Metadata trong SQL/NoSQL Database.
* Nội dung Chunk hoặc tham chiếu Chunk.
* Vector trong VectorDB.

VectorDB chủ yếu phục vụ tìm kiếm, không thay thế hệ thống lưu trữ nguồn.

---

## Tình huống 8: SQL và VectorDB bị lệch dữ liệu

**Hỏi:** Document đã bị xóa trong SQL nhưng Vector vẫn còn. Xử lý thế nào?

**Trả lời:**

Có thể:

* Sử dụng Outbox Pattern để phát sự kiện xóa.
* Consumer xóa Vector theo `document_id`.
* Thực hiện tác vụ đối soát định kỳ.
* Dùng Soft Delete và metadata filter trong thời gian chờ đồng bộ.
* Thiết kế thao tác idempotent.

# XI. Câu hỏi nâng cao

## 1. Có nên lưu Vector trực tiếp trong PostgreSQL không?

**Trả lời:**

Có thể dùng PostgreSQL cùng Extension hỗ trợ Vector khi:

* Dữ liệu chưa quá lớn.
* Muốn giữ metadata và Vector cùng một Database.
* Muốn giảm độ phức tạp vận hành.
* Cần transaction và filter SQL.

Vector Database chuyên dụng phù hợp hơn khi:

* Quy mô Vector rất lớn.
* Cần throughput truy vấn cao.
* Cần scale độc lập.
* Cần nhiều tùy chọn ANN chuyên sâu.

---

## 2. Normalization và Denormalization khác nhau thế nào?

**Trả lời:**

Normalization giảm dữ liệu trùng và tăng tính nhất quán bằng cách tách bảng.

Denormalization chủ động lặp một số dữ liệu để giảm JOIN và tăng tốc đọc.

SQL thường thiên về chuẩn hóa; MongoDB thường chấp nhận phi chuẩn hóa nhiều hơn dựa trên access pattern.

---

## 3. Database per Service trong Microservices là gì?

**Trả lời:**

Mỗi Microservice sở hữu dữ liệu của mình.

Ví dụ:

```text
User Service → PostgreSQL
Document Service → MongoDB
Search Service → Qdrant
```

Service khác không truy cập trực tiếp Database của nhau mà giao tiếp qua API hoặc Event.

---

## 4. Polyglot Persistence là gì?

**Trả lời:**

Polyglot Persistence là việc sử dụng nhiều loại Database trong cùng hệ thống theo nhu cầu.

Ví dụ:

* PostgreSQL cho Transaction.
* MongoDB cho Document.
* Redis cho Cache.
* Qdrant cho Vector Search.

Không nên dùng nhiều Database chỉ vì công nghệ mới; mỗi loại làm tăng chi phí vận hành.

---

## 5. CAP Theorem có áp dụng cho Database không?

**Trả lời:**

Có, với hệ thống dữ liệu phân tán.

Khi xảy ra Network Partition, hệ thống phải đánh đổi giữa:

* Consistency.
* Availability.

Partition Tolerance thường là điều không thể bỏ qua trong hệ thống phân tán thực tế.

# XII. Câu trả lời ngắn cần ghi nhớ

**MySQL là gì?**

> MySQL là cơ sở dữ liệu quan hệ phổ biến, phù hợp ứng dụng web, CRUD và các hệ thống transaction thông thường.

**PostgreSQL mạnh ở đâu?**

> PostgreSQL mạnh về SQL nâng cao, tính toàn vẹn dữ liệu, JSONB, Extension và truy vấn phức tạp.

**MongoDB là gì?**

> MongoDB là Document Database lưu dữ liệu dưới dạng BSON, phù hợp với dữ liệu lồng nhau và schema linh hoạt.

**Vector Database là gì?**

> Vector Database lưu Embedding và tìm dữ liệu gần nhau theo độ tương đồng thay vì chỉ tìm kiếm chính xác.

**Pinecone phù hợp khi nào?**

> Khi muốn dịch vụ được quản lý và giảm công việc vận hành.

**Qdrant phù hợp khi nào?**

> Khi cần Vector Search, metadata filtering và khả năng tự triển khai tương đối thuận tiện.

**Milvus phù hợp khi nào?**

> Khi cần xử lý dữ liệu Vector lớn, kiến trúc phân tán và có năng lực vận hành hệ thống.

**Thiết kế dữ liệu RAG phổ biến:**

```text
File gốc
  ↓
Object Storage

Metadata và trạng thái
  ↓
PostgreSQL/MongoDB

Chunks và Embeddings
  ↓
Pinecone/Qdrant/Milvus

User Query
  ↓
Embedding
  ↓
Vector Search + Filter
  ↓
Reranking
  ↓
LLM
```
