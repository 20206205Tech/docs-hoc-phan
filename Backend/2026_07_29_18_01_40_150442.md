Dưới đây là bộ câu hỏi phỏng vấn về **Model–View–Controller (MVC) và Microservices Architecture (MSA)**, phù hợp với vị trí **Lập trình viên Fresher/Junior Backend hoặc Fullstack**.

# I. Model–View–Controller

## 1. MVC là gì?

**Trả lời:**

MVC là mẫu kiến trúc chia ứng dụng thành ba thành phần:

* **Model:** Quản lý dữ liệu và nghiệp vụ.
* **View:** Hiển thị giao diện cho người dùng.
* **Controller:** Nhận request, điều phối xử lý và chọn dữ liệu trả về.

```text
User
  ↓
Controller
  ↓
Model
  ↓
Controller
  ↓
View
  ↓
User
```

---

## 2. Mục đích của MVC là gì?

**Trả lời:**

MVC giúp tách biệt:

* Giao diện.
* Xử lý request.
* Dữ liệu và nghiệp vụ.

Nhờ đó, mã nguồn dễ:

* Đọc.
* Kiểm thử.
* Bảo trì.
* Phân chia công việc.
* Thay đổi từng phần độc lập.

---

## 3. Model trong MVC là gì?

**Trả lời:**

Model đại diện cho dữ liệu và các quy tắc liên quan đến dữ liệu.

Ví dụ:

```text
User
Order
Product
Payment
```

Model có thể bao gồm:

* Entity.
* Validation nghiệp vụ.
* Truy cập Database.
* Domain logic.

Tùy framework, phần truy cập Database có thể được tách riêng thành Repository.

---

## 4. View trong MVC là gì?

**Trả lời:**

View chịu trách nhiệm hiển thị dữ liệu cho người dùng.

Ví dụ:

* HTML.
* Template.
* Trang danh sách sản phẩm.
* Trang chi tiết người dùng.

Trong REST API thuần túy, JSON response đôi khi được xem như phần biểu diễn dữ liệu thay cho HTML View.

---

## 5. Controller trong MVC là gì?

**Trả lời:**

Controller nhận request từ Client, gọi thành phần nghiệp vụ và trả response.

Ví dụ:

```typescript
@Controller("users")
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get(":id")
  getUser(@Param("id") id: string) {
    return this.usersService.findById(id);
  }
}
```

Controller không nên chứa quá nhiều Business Logic.

---

## 6. Luồng xử lý một request trong MVC diễn ra thế nào?

**Trả lời:**

Ví dụ người dùng truy cập `/products/10`:

1. Router chuyển request đến `ProductController`.
2. Controller lấy ID sản phẩm.
3. Controller gọi Model hoặc Service.
4. Service lấy dữ liệu từ Database.
5. Controller truyền dữ liệu sang View.
6. View hiển thị kết quả.

Với REST API, bước cuối thường là trả JSON.

---

## 7. MVC có phải là kiến trúc ba tầng không?

**Trả lời:**

Không hoàn toàn.

MVC chia trách nhiệm theo giao diện và điều khiển:

```text
Model – View – Controller
```

Kiến trúc ba tầng thường chia thành:

```text
Presentation Layer
Business Layer
Data Access Layer
```

Hai cách tổ chức có thể được sử dụng cùng nhau nhưng không đồng nghĩa hoàn toàn.

---

## 8. Controller có nên gọi trực tiếp Database không?

**Trả lời:**

Không nên trong phần lớn dự án.

Thiết kế tốt hơn:

```text
Controller
→ Service
→ Repository
→ Database
```

Điều này giúp:

* Controller đơn giản.
* Nghiệp vụ dễ tái sử dụng.
* Dễ unit test.
* Giảm phụ thuộc vào Database.

---

## 9. Service Layer có thuộc MVC truyền thống không?

**Trả lời:**

MVC nguyên bản chỉ mô tả Model, View và Controller.

Trong ứng dụng thực tế, người ta thường bổ sung Service Layer để chứa nghiệp vụ:

```text
Controller
→ Service
→ Repository
→ Database
```

Service Layer giúp tránh Controller và Model trở nên quá lớn.

---

## 10. Repository có vai trò gì trong ứng dụng MVC?

**Trả lời:**

Repository đóng gói logic truy cập dữ liệu.

Ví dụ:

```typescript
interface UserRepository {
  findById(id: string): Promise<User | null>;
  save(user: User): Promise<void>;
}
```

Service sử dụng Repository thay vì viết trực tiếp câu SQL.

---

## 11. Fat Controller là gì?

**Trả lời:**

Fat Controller là Controller chứa quá nhiều:

* Business Logic.
* Validation nghiệp vụ.
* Truy vấn Database.
* Xử lý dữ liệu.
* Gọi nhiều hệ thống bên ngoài.

Ví dụ không tốt:

```text
Controller
├── Kiểm tra quyền
├── Tính giá
├── Tạo đơn hàng
├── Trừ tồn kho
├── Gửi email
└── Ghi Database
```

Nên chuyển nghiệp vụ sang Service hoặc Domain Layer.

---

## 12. Fat Model là gì?

**Trả lời:**

Fat Model là Model chứa quá nhiều trách nhiệm, chẳng hạn:

* Truy cập Database.
* Gọi API ngoài.
* Format giao diện.
* Gửi email.
* Xử lý mọi nghiệp vụ.

Model nên chứa hành vi phù hợp với dữ liệu của nó, nhưng không nên trở thành một đối tượng làm tất cả mọi việc.

---

## 13. Ưu điểm của MVC là gì?

**Trả lời:**

* Tách biệt trách nhiệm.
* Dễ phát triển ứng dụng CRUD.
* Dễ học và áp dụng.
* Nhiều framework hỗ trợ.
* Controller và View có thể phát triển tương đối độc lập.
* Dễ tổ chức dự án nhỏ và vừa.

---

## 14. Nhược điểm của MVC là gì?

**Trả lời:**

* Controller dễ trở nên quá lớn.
* Business Logic có thể bị rải rác.
* Model có thể phụ thuộc ORM.
* Với hệ thống lớn, cấu trúc theo loại file khó thể hiện ranh giới nghiệp vụ.
* Không giải quyết trực tiếp vấn đề hệ thống phân tán.

---

## 15. MVC phù hợp với loại ứng dụng nào?

**Trả lời:**

MVC phù hợp với:

* Web application.
* CRUD application.
* Admin dashboard.
* Monolithic application.
* Backend API nhỏ và vừa.
* Ứng dụng server-rendered HTML.

---

## 16. MVC có dùng được trong REST API không?

**Trả lời:**

Có.

Trong REST API:

* Controller nhận HTTP request.
* Model hoặc Service xử lý nghiệp vụ.
* Response JSON đóng vai trò biểu diễn dữ liệu.

```text
HTTP Request
→ Controller
→ Service/Model
→ JSON Response
```

---

## 17. MVC trong NestJS được thể hiện như thế nào?

**Trả lời:**

Một cách tổ chức phổ biến:

```text
Controller
→ Service
→ Repository
→ Database
```

Trong đó:

* Controller xử lý HTTP.
* Service xử lý nghiệp vụ.
* Repository truy cập dữ liệu.
* DTO kiểm tra dữ liệu vào và ra.

NestJS không bắt buộc phải triển khai MVC cổ điển có HTML View.

---

## 18. MVC trong Spring Boot được thể hiện như thế nào?

**Trả lời:**

Spring MVC thường gồm:

```text
@RestController
→ @Service
→ @Repository
→ Database
```

Nếu ứng dụng server-rendered, Controller có thể trả về template như Thymeleaf.

Nếu là REST API, Controller thường trả JSON.

---

## 19. ViewModel hoặc DTO dùng để làm gì?

**Trả lời:**

DTO hoặc ViewModel giúp tách dữ liệu giao tiếp khỏi Domain Model hoặc Database Model.

Ví dụ không nên trả trực tiếp:

```json
{
  "id": 1,
  "email": "user@example.com",
  "passwordHash": "...",
  "internalNote": "..."
}
```

Nên dùng Response DTO:

```json
{
  "id": 1,
  "email": "user@example.com"
}
```

---

## 20. MVC có liên quan đến Design Pattern không?

**Trả lời:**

MVC là một mẫu kiến trúc cấp cao. Bên trong MVC vẫn có thể sử dụng nhiều Design Pattern khác:

* Factory.
* Repository.
* Strategy.
* Observer.
* Adapter.
* Dependency Injection.

# II. Microservices Architecture

## 21. Microservices Architecture là gì?

**Trả lời:**

Microservices Architecture, viết tắt là MSA, chia hệ thống thành nhiều dịch vụ nhỏ, độc lập theo miền nghiệp vụ.

Ví dụ:

```text
Client
  ↓
API Gateway
  ├── User Service
  ├── Order Service
  ├── Payment Service
  └── Notification Service
```

Mỗi Service có thể được phát triển, triển khai và mở rộng độc lập.

---

## 22. Microservice nên được chia theo tiêu chí nào?

**Trả lời:**

Nên chia theo:

* Nghiệp vụ.
* Bounded Context.
* Quyền sở hữu dữ liệu.
* Nhịp độ thay đổi.
* Yêu cầu scale.
* Trách nhiệm của đội phát triển.

Không nên chỉ chia theo bảng Database hoặc lớp kỹ thuật.

---

## 23. Microservices khác Monolith như thế nào?

| Monolith                      | Microservices                    |
| ----------------------------- | -------------------------------- |
| Một ứng dụng triển khai chung | Nhiều Service triển khai độc lập |
| Gọi hàm trong cùng tiến trình | Giao tiếp qua mạng               |
| Dễ bắt đầu                    | Phức tạp hơn                     |
| Transaction đơn giản hơn      | Transaction phân tán khó hơn     |
| Scale toàn ứng dụng           | Scale từng Service               |
| Debug tập trung               | Cần distributed tracing          |

---

## 24. Modular Monolith là gì?

**Trả lời:**

Modular Monolith là một ứng dụng triển khai thành một khối nhưng bên trong được chia thành các module nghiệp vụ rõ ràng.

```text
Single Application
├── User Module
├── Order Module
├── Payment Module
└── Notification Module
```

Đây thường là lựa chọn tốt trước khi chuyển sang Microservices.

---

## 25. Ưu điểm của Microservices là gì?

**Trả lời:**

* Deploy độc lập.
* Scale độc lập.
* Giới hạn phạm vi thay đổi.
* Đội ngũ có thể làm việc độc lập.
* Có thể sử dụng công nghệ khác nhau.
* Lỗi có thể được cô lập nếu thiết kế tốt.
* Phù hợp hệ thống lớn, nhiều miền nghiệp vụ.

---

## 26. Nhược điểm của Microservices là gì?

**Trả lời:**

* Giao tiếp mạng có thể lỗi.
* Độ trễ cao hơn gọi hàm nội bộ.
* Khó quản lý dữ liệu nhất quán.
* Triển khai phức tạp.
* Khó debug.
* Cần logging, tracing và monitoring.
* Cần quản lý API contract.
* Tốn nhiều tài nguyên vận hành.

---

## 27. Mỗi Microservice có nên có Database riêng không?

**Trả lời:**

Thông thường mỗi Service nên sở hữu dữ liệu của mình.

```text
User Service → User Database
Order Service → Order Database
Payment Service → Payment Database
```

Service khác không nên đọc trực tiếp Database đó mà phải gọi API hoặc sử dụng Event.

---

## 28. Tại sao không nên dùng chung Database giữa các Microservice?

**Trả lời:**

Database dùng chung tạo coupling:

* Một Service thay đổi schema có thể làm Service khác lỗi.
* Khó deploy độc lập.
* Khó xác định Service sở hữu dữ liệu.
* Service có thể truy cập và sửa dữ liệu không thuộc trách nhiệm.
* Khó scale độc lập.

---

## 29. Microservice giao tiếp với nhau bằng cách nào?

**Trả lời:**

Hai cách chính:

### Đồng bộ

* REST.
* gRPC.

### Bất đồng bộ

* RabbitMQ.
* Kafka.
* Event Bus.

Không có phương thức phù hợp cho mọi trường hợp.

---

## 30. Khi nào dùng giao tiếp đồng bộ?

**Trả lời:**

Dùng khi Service cần kết quả ngay để tiếp tục xử lý.

Ví dụ:

```text
Order Service
→ kiểm tra giá
→ Product Service
```

Cần có:

* Timeout.
* Retry có giới hạn.
* Circuit Breaker.
* Fallback nếu phù hợp.

---

## 31. Khi nào dùng giao tiếp bất đồng bộ?

**Trả lời:**

Dùng khi không cần kết quả ngay:

* Gửi email.
* Phân tích dữ liệu.
* Xử lý tài liệu.
* Cập nhật hệ thống khác.
* Phát Domain Event.
* Chạy tác vụ nền.

```text
Order Service
→ OrderCreated
→ Message Broker
→ Notification Service
```

---

## 32. API Gateway có vai trò gì trong MSA?

**Trả lời:**

API Gateway là điểm vào chung của hệ thống.

Nó có thể đảm nhiệm:

* Routing.
* Authentication.
* Rate limiting.
* CORS.
* Logging.
* Request transformation.
* TLS termination.

Ví dụ:

```text
Client
  ↓
Kong API Gateway
  ├── User Service
  ├── Document Service
  └── Payment Service
```

---

## 33. Service Discovery là gì?

**Trả lời:**

Service Discovery giúp Service tìm được địa chỉ của nhau mà không cần cấu hình IP cố định.

Ví dụ:

* Kubernetes Service và DNS.
* Consul.
* Eureka.

Trong Kubernetes, Service có thể được gọi bằng DNS nội bộ:

```text
payment-service.default.svc.cluster.local
```

---

## 34. Load Balancing trong Microservices là gì?

**Trả lời:**

Load Balancer phân phối request giữa nhiều instance của một Service.

```text
Order Service
    ↓
Load Balancer
    ├── Payment Instance 1
    ├── Payment Instance 2
    └── Payment Instance 3
```

---

## 35. Stateless Service là gì?

**Trả lời:**

Stateless Service không lưu trạng thái người dùng trong bộ nhớ cục bộ giữa các request.

Thông tin có thể được lưu trong:

* Database.
* Redis.
* Token.
* Shared Storage.

Stateless Service dễ scale ngang hơn vì request có thể được gửi đến bất kỳ instance nào.

---

## 36. Circuit Breaker là gì?

**Trả lời:**

Circuit Breaker tạm thời ngừng gọi một Service đang lỗi liên tục.

Các trạng thái thường có:

* Closed.
* Open.
* Half-open.

Mục đích là ngăn lỗi lan truyền và giảm tải cho Service đang gặp sự cố.

---

## 37. Retry trong Microservices cần lưu ý gì?

**Trả lời:**

Không nên retry mọi lỗi.

Retry nên:

* Chỉ áp dụng lỗi tạm thời.
* Có giới hạn số lần.
* Sử dụng exponential backoff.
* Có jitter.
* Tôn trọng timeout hoặc deadline.
* Chỉ retry thao tác idempotent hoặc có idempotency key.

---

## 38. Distributed Transaction là gì?

**Trả lời:**

Distributed Transaction là giao dịch liên quan đến nhiều Service hoặc Database.

Ví dụ:

```text
Order Service tạo đơn
Payment Service trừ tiền
Inventory Service trừ kho
```

Nếu một bước thất bại, không thể dùng transaction Database đơn giản trên toàn hệ thống.

---

## 39. Saga Pattern là gì?

**Trả lời:**

Saga chia giao dịch phân tán thành chuỗi các transaction cục bộ.

Nếu một bước lỗi, hệ thống thực hiện hành động bù.

Ví dụ:

```text
Tạo đơn hàng
→ Trừ tiền
→ Trừ kho
→ Giao hàng
```

Nếu trừ kho thất bại:

```text
Hoàn tiền
→ Hủy đơn hàng
```

---

## 40. Saga Choreography và Orchestration khác nhau thế nào?

**Trả lời:**

### Choreography

Các Service phản ứng với Event:

```text
OrderCreated
→ Payment xử lý
→ PaymentCompleted
→ Inventory xử lý
```

Ưu điểm là giảm thành phần điều phối trung tâm, nhưng luồng tổng thể có thể khó theo dõi.

### Orchestration

Có Saga Orchestrator điều phối:

```text
Orchestrator
├── Gọi Payment
├── Gọi Inventory
└── Gọi Shipping
```

Dễ nhìn luồng hơn nhưng Orchestrator có thể trở nên phức tạp.

---

## 41. Eventual Consistency là gì?

**Trả lời:**

Eventual Consistency nghĩa là dữ liệu giữa các Service có thể chưa đồng nhất ngay lập tức nhưng sẽ đồng bộ sau một khoảng thời gian.

Ví dụ:

* Payment đã hoàn thành.
* Order vài giây sau mới chuyển sang `PAID`.

---

## 42. Outbox Pattern là gì?

**Trả lời:**

Outbox Pattern giải quyết trường hợp lưu Database thành công nhưng gửi Event thất bại.

Các bước:

1. Lưu dữ liệu nghiệp vụ.
2. Lưu Event vào bảng Outbox trong cùng transaction.
3. Worker đọc Outbox.
4. Publish Event lên Broker.
5. Đánh dấu Event đã gửi.

---

## 43. Idempotency trong Microservices là gì?

**Trả lời:**

Idempotency giúp xử lý cùng request hoặc message nhiều lần mà không tạo kết quả trùng.

Ví dụ Client gửi lại yêu cầu thanh toán do timeout.

Server sử dụng:

```text
Idempotency-Key: payment-123
```

Nếu key đã được xử lý, Server trả kết quả cũ thay vì thanh toán lần nữa.

---

## 44. Dead Letter Queue là gì?

**Trả lời:**

Dead Letter Queue lưu những message không thể xử lý thành công sau số lần retry cho phép.

Nó giúp:

* Tránh retry vô hạn.
* Cô lập Poison Message.
* Cho phép phân tích và xử lý lại.
* Tạo cảnh báo vận hành.

---

## 45. Observability trong MSA gồm những gì?

**Trả lời:**

Ba nhóm thường được nhắc đến:

* Logs.
* Metrics.
* Traces.

Ngoài ra cần:

* Correlation ID.
* Request ID.
* Alerting.
* Dashboard.
* Theo dõi dependency.

---

## 46. Distributed Tracing là gì?

**Trả lời:**

Distributed Tracing theo dõi một request đi qua nhiều Service.

```text
Client
→ Gateway
→ Order Service
→ Payment Service
→ Database
```

Mỗi request có Trace ID chung và mỗi bước có Span riêng.

---

## 47. Health Check trong Microservices là gì?

**Trả lời:**

Health Check giúp hệ thống biết Service có đang hoạt động và sẵn sàng nhận request không.

Trong Kubernetes:

* Liveness Probe: Có cần restart Container không?
* Readiness Probe: Pod có sẵn sàng nhận traffic không?
* Startup Probe: Ứng dụng đã khởi động xong chưa?

---

## 48. API Contract là gì?

**Trả lời:**

API Contract mô tả giao diện giữa các Service:

* Endpoint hoặc RPC method.
* Request schema.
* Response schema.
* Error.
* Event schema.
* Quy tắc phiên bản.

Có thể dùng:

* OpenAPI.
* Protobuf.
* AsyncAPI.
* JSON Schema.
* Avro.

---

## 49. Làm thế nào thay đổi API mà không làm hỏng Consumer?

**Trả lời:**

* Ưu tiên thay đổi tương thích ngược.
* Thêm field tùy chọn.
* Không xóa field ngay.
* Không đổi ý nghĩa field cũ.
* Quản lý version.
* Dùng contract test.
* Cho Client thời gian chuyển phiên bản.

---

## 50. Contract Testing là gì?

**Trả lời:**

Contract Testing kiểm tra Producer và Consumer có tuân thủ cùng một hợp đồng hay không.

Nó giúp phát hiện lỗi tích hợp trước khi triển khai toàn hệ thống.

# III. So sánh MVC và Microservices

## 51. MVC và MSA có phải cùng cấp kiến trúc không?

**Trả lời:**

Không hoàn toàn.

* MVC tổ chức thành phần bên trong một ứng dụng.
* MSA tổ chức toàn hệ thống thành nhiều Service.

Một Microservice có thể sử dụng MVC bên trong:

```text
Microservices System
├── User Service
│   └── MVC
├── Order Service
│   └── MVC
└── Payment Service
    └── Hexagonal Architecture
```

---

## 52. MVC có thay thế Microservices không?

**Trả lời:**

Không.

MVC giải quyết việc tách Model, View và Controller trong một ứng dụng.

Microservices giải quyết việc phân chia toàn hệ thống thành các dịch vụ độc lập.

Hai kiến trúc có thể được sử dụng cùng nhau.

---

## 53. Có thể xây dựng Monolith bằng MVC không?

**Trả lời:**

Có.

Đây là thiết kế phổ biến:

```text
Single Application
├── Controllers
├── Models
├── Views
├── Services
└── Repositories
```

Ứng dụng được triển khai như một đơn vị.

---

## 54. Có thể xây dựng mỗi Microservice theo MVC không?

**Trả lời:**

Có.

Ví dụ một User Service:

```text
User Service
├── UserController
├── UserService
├── UserRepository
└── UserModel
```

Tuy nhiên, với nghiệp vụ phức tạp có thể cân nhắc DDD, Hexagonal hoặc Clean Architecture.

---

## 55. MVC hay Microservices phù hợp hơn cho dự án nhỏ?

**Trả lời:**

Đây không phải lựa chọn loại trừ trực tiếp.

Với dự án nhỏ, thường nên bắt đầu bằng Monolith hoặc Modular Monolith có tổ chức MVC/layered rõ ràng.

Microservices có thể gây thêm chi phí vận hành không cần thiết.

---

## 56. Khi nào nên chuyển từ Monolith sang Microservices?

**Trả lời:**

Có thể cân nhắc khi:

* Một số module cần scale độc lập.
* Các đội cần deploy độc lập.
* Chu kỳ phát hành giữa các miền khác nhau.
* Monolith quá lớn và khó thay đổi.
* Ranh giới nghiệp vụ đã rõ.
* Một lỗi nhỏ thường ảnh hưởng toàn hệ thống.
* Có đủ năng lực DevOps và observability.

---

## 57. Có nên bắt đầu dự án mới bằng Microservices không?

**Trả lời:**

Không phải lúc nào cũng nên.

Nếu:

* Nghiệp vụ chưa rõ.
* Đội nhỏ.
* Sản phẩm đang thử nghiệm.
* Lưu lượng chưa lớn.
* Chưa có nền tảng DevOps.

Modular Monolith thường đơn giản và an toàn hơn.

---

## 58. MVC có điểm yếu gì khi hệ thống lớn?

**Trả lời:**

Nếu chỉ tổ chức thư mục toàn hệ thống theo:

```text
controllers/
models/
services/
repositories/
```

thì các chức năng cùng nghiệp vụ bị phân tán.

Có thể cải thiện bằng cách tổ chức theo feature hoặc module:

```text
modules/
├── users/
│   ├── user.controller
│   ├── user.service
│   └── user.repository
└── orders/
    ├── order.controller
    ├── order.service
    └── order.repository
```

---

## 59. Microservices có tự động làm hệ thống dễ bảo trì hơn không?

**Trả lời:**

Không.

Nếu chia Service sai:

* Quá nhiều giao tiếp mạng.
* Service phụ thuộc vòng tròn.
* Transaction rất khó.
* Thay đổi một chức năng phải sửa nhiều Service.
* Deploy độc lập nhưng không thực sự độc lập.

Ranh giới nghiệp vụ quan trọng hơn số lượng Service.

---

## 60. Distributed Monolith là gì?

**Trả lời:**

Distributed Monolith là hệ thống được chia thành nhiều Service nhưng vẫn phụ thuộc chặt chẽ.

Dấu hiệu:

* Phải deploy nhiều Service cùng lúc.
* Dùng chung Database.
* Gọi đồng bộ theo chuỗi dài.
* Một Service lỗi làm toàn hệ thống lỗi.
* Các Service chia sẻ Domain Model.
* Thay đổi một API gây ảnh hưởng hàng loạt.

Hệ thống có độ phức tạp của Microservices nhưng không nhận được lợi ích độc lập.

# IV. Câu hỏi tình huống phỏng vấn

## Tình huống 1: Controller chứa logic tạo đơn hàng

**Hỏi:** Controller kiểm tra tồn kho, tính giá, thanh toán và gửi email. Bạn cải tiến thế nào?

**Trả lời:**

Tôi sẽ:

1. Giữ Controller chỉ nhận request và trả response.
2. Chuyển quy trình tạo đơn sang Application Service.
3. Chuyển quy tắc tính giá vào Domain Service hoặc Strategy.
4. Dùng Repository để truy cập dữ liệu.
5. Gửi email bất đồng bộ qua Message Queue.
6. Dùng transaction cho dữ liệu cần nhất quán.

---

## Tình huống 2: Một hệ thống mới chỉ có ba lập trình viên

**Hỏi:** Có nên dùng Microservices không?

**Trả lời:**

Tôi ưu tiên Modular Monolith nếu nghiệp vụ và lưu lượng chưa đủ phức tạp.

Lý do:

* Phát triển nhanh hơn.
* Debug đơn giản.
* Transaction dễ quản lý.
* Ít chi phí triển khai.
* Có thể tách Service sau nếu module được thiết kế rõ.

---

## Tình huống 3: Payment Service tạm thời không hoạt động

**Hỏi:** Order Service nên xử lý thế nào?

**Trả lời:**

Tùy yêu cầu nghiệp vụ:

* Đặt timeout.
* Retry có giới hạn với backoff.
* Dùng Circuit Breaker.
* Giữ Order ở trạng thái `PAYMENT_PENDING`.
* Gửi Command qua Message Queue nếu xử lý bất đồng bộ.
* Cho phép thử thanh toán lại.
* Không đánh dấu Order là đã thanh toán khi chưa xác nhận.

---

## Tình huống 4: Hai Microservice cùng cần dữ liệu người dùng

**Hỏi:** Có nên dùng chung bảng `users` không?

**Trả lời:**

Không nên truy cập chung bảng trực tiếp.

Các Service có thể:

* Gọi User Service khi cần dữ liệu mới nhất.
* Nhận Event và lưu bản sao dữ liệu cần thiết.
* Chỉ lưu `user_id` nếu đủ.
* Sử dụng cache phù hợp.

Mỗi Service chỉ nên lưu dữ liệu người dùng cần cho nghiệp vụ của mình.

---

## Tình huống 5: Một request phải gọi năm Service liên tiếp

**Hỏi:** Có vấn đề gì?

**Trả lời:**

Chuỗi gọi đồng bộ dài gây:

* Tăng độ trễ.
* Tăng nguy cơ timeout.
* Lỗi lan truyền.
* Khó retry.
* Khó debug.

Có thể:

* Tổng hợp dữ liệu qua một Service phù hợp.
* Chuyển một số bước sang bất đồng bộ.
* Cache dữ liệu.
* Xem lại ranh giới Service.
* Tránh chia Service quá nhỏ.

---

## Tình huống 6: Một Service cần dữ liệu từ nhiều Service để hiển thị Dashboard

**Trả lời:**

Có thể dùng:

* API Composition.
* Backend for Frontend.
* Read Model riêng.
* CQRS.
* Event-driven projection.

Không nên để Frontend tự gọi quá nhiều Service nội bộ nếu gây coupling và khó kiểm soát.

---

## Tình huống 7: Một Event bị xử lý hai lần

**Hỏi:** Consumer phải làm gì?

**Trả lời:**

Consumer cần idempotent:

1. Mỗi Event có `event_id`.
2. Consumer lưu những ID đã xử lý.
3. Nếu nhận Event trùng, bỏ qua hoặc trả kết quả cũ.
4. Thiết kế thao tác Database có Unique Constraint nếu phù hợp.

---

## Tình huống 8: Một Microservice có hàng trăm endpoint không liên quan

**Hỏi:** Điều này cho thấy gì?

**Trả lời:**

Có thể Service đang:

* Có quá nhiều trách nhiệm.
* Bao phủ nhiều Bounded Context.
* Trở thành một Monolith nhỏ.
* Có ranh giới nghiệp vụ không rõ.

Nên phân tích nghiệp vụ trước khi tách, không chỉ chia theo số endpoint.

# V. Câu hỏi nâng cao

## 61. Database per Service có bắt buộc mỗi Service dùng một máy Database riêng không?

**Trả lời:**

Không bắt buộc.

Có thể dùng chung một Database Server nhưng mỗi Service sở hữu:

* Schema riêng.
* Database riêng.
* User và quyền riêng.
* Migration riêng.

Quan trọng là không truy cập trực tiếp dữ liệu thuộc Service khác.

---

## 62. API Gateway có chứa Business Logic không?

**Trả lời:**

Không nên chứa Business Logic cốt lõi.

Gateway nên tập trung vào:

* Routing.
* Authentication.
* Rate limiting.
* Logging.
* Chính sách traffic.
* Chuyển đổi giao thức đơn giản.

Nghiệp vụ nên nằm trong Service phù hợp.

---

## 63. Microservice có nên nhỏ nhất có thể không?

**Trả lời:**

Không.

Microservice nên đủ nhỏ để có trách nhiệm rõ và đủ lớn để sở hữu một khả năng nghiệp vụ có ý nghĩa.

Service quá nhỏ tạo nhiều giao tiếp mạng và tăng chi phí vận hành.

---

## 64. MVC và Hexagonal Architecture khác nhau thế nào?

**Trả lời:**

MVC tập trung tách giao diện, điều khiển và dữ liệu.

Hexagonal Architecture tập trung tách nghiệp vụ khỏi các thành phần bên ngoài thông qua Port và Adapter.

Controller trong MVC có thể trở thành một Inbound Adapter trong Hexagonal Architecture.

---

## 65. Có thể kết hợp MVC, DDD và Microservices không?

**Trả lời:**

Có.

Ví dụ:

```text
Microservices Architecture
└── Order Service
    ├── Controller — MVC/Inbound Adapter
    ├── Application Use Cases
    ├── DDD Domain Model
    ├── Repository Port
    └── PostgreSQL Adapter
```

Mỗi khái niệm giải quyết một vấn đề khác nhau.

# VI. Câu trả lời ngắn cần ghi nhớ

**MVC là gì?**

> MVC chia ứng dụng thành Model quản lý dữ liệu và nghiệp vụ, View hiển thị giao diện, Controller nhận request và điều phối xử lý.

**Microservices Architecture là gì?**

> MSA chia hệ thống thành nhiều dịch vụ nhỏ theo nghiệp vụ, có thể triển khai và mở rộng độc lập.

**MVC khác Microservices thế nào?**

> MVC tổ chức bên trong một ứng dụng; Microservices tổ chức toàn hệ thống thành nhiều ứng dụng hoặc dịch vụ.

**Controller nên làm gì?**

> Controller nên nhận request, gọi Use Case hoặc Service và chuyển kết quả thành response, không nên chứa nghiệp vụ phức tạp.

**Khi nào dùng Microservices?**

> Khi hệ thống có miền nghiệp vụ rõ, cần deploy hoặc scale độc lập và đội ngũ có khả năng vận hành hệ thống phân tán.

**Khi nào dùng Monolith?**

> Khi dự án còn nhỏ, nghiệp vụ chưa ổn định, đội ít người hoặc cần phát triển nhanh.

**Kiến trúc kết hợp phổ biến:**

```text
Client
  ↓
API Gateway
  ↓
Microservice
  ├── Controller
  ├── Application Service
  ├── Domain Model
  ├── Repository
  └── Database
```
