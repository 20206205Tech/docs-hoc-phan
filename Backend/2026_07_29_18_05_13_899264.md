Dưới đây là bộ câu hỏi phỏng vấn về **Automation, CI/CD, Jenkins, GitHub Actions và Apache Airflow**, phù hợp với vị trí **Lập trình viên Fresher/Junior Backend, DevOps hoặc AI Automation**.

# I. Automation và CI/CD

## 1. Automation trong phát triển phần mềm là gì?

**Trả lời:**

Automation là việc sử dụng chương trình hoặc công cụ để tự động thực hiện các công việc lặp lại thay vì thao tác thủ công.

Ví dụ:

* Chạy kiểm thử.
* Kiểm tra định dạng mã nguồn.
* Build ứng dụng.
* Build Docker Image.
* Deploy lên Server.
* Backup Database.
* Gửi báo cáo.
* Xử lý dữ liệu theo lịch.

---

## 2. CI là gì?

**Trả lời:**

CI là viết tắt của **Continuous Integration** — tích hợp liên tục.

Khi lập trình viên đẩy mã nguồn lên Git, hệ thống tự động:

1. Checkout source code.
2. Cài đặt dependency.
3. Kiểm tra định dạng.
4. Chạy test.
5. Build ứng dụng.
6. Báo kết quả.

Mục tiêu là phát hiện lỗi sớm trước khi code được merge.

---

## 3. Continuous Delivery là gì?

**Trả lời:**

Continuous Delivery là quá trình tự động chuẩn bị ứng dụng để có thể triển khai bất cứ lúc nào.

Pipeline có thể tự động:

* Test.
* Build.
* Đóng gói artifact.
* Push Docker Image.
* Deploy lên môi trường kiểm thử.

Việc triển khai production thường vẫn cần một bước phê duyệt thủ công.

---

## 4. Continuous Deployment là gì?

**Trả lời:**

Continuous Deployment tự động triển khai mọi thay đổi đã vượt qua pipeline lên production mà không cần phê duyệt thủ công.

Khác biệt chính:

* **Continuous Delivery:** Sẵn sàng deploy, nhưng production có thể cần phê duyệt.
* **Continuous Deployment:** Tự động deploy production.

---

## 5. Pipeline là gì?

**Trả lời:**

Pipeline là chuỗi các bước tự động đưa source code từ lúc commit đến khi được kiểm thử, đóng gói và triển khai.

```text
Commit
  ↓
Lint
  ↓
Unit Test
  ↓
Build
  ↓
Security Scan
  ↓
Push Artifact/Image
  ↓
Deploy
```

---

## 6. Stage và Job khác nhau thế nào?

**Trả lời:**

* **Stage:** Một giai đoạn logic của pipeline, chẳng hạn `Test`, `Build`, `Deploy`.
* **Job:** Một đơn vị công việc cụ thể chạy trên một Runner hoặc Agent.

Một Stage có thể chứa nhiều Job chạy song song.

```text
Test Stage
├── Unit Test Job
├── Integration Test Job
└── Lint Job
```

---

## 7. Artifact trong CI/CD là gì?

**Trả lời:**

Artifact là kết quả được tạo ra trong pipeline và được lưu lại để sử dụng ở bước sau.

Ví dụ:

* File `.jar`.
* File `.zip`.
* Thư mục `dist`.
* Báo cáo kiểm thử.
* Coverage report.
* Docker Image.

---

## 8. Cache khác Artifact thế nào?

**Trả lời:**

**Cache** dùng để tăng tốc pipeline bằng cách tái sử dụng dữ liệu có thể tạo lại, ví dụ:

* `node_modules`.
* Maven dependencies.
* Python package cache.

**Artifact** là kết quả chính cần được chuyển giữa các Job hoặc lưu lại, ví dụ:

* File build.
* Báo cáo test.
* Package triển khai.

Không nên coi cache là nơi lưu artifact quan trọng lâu dài.

---

## 9. Runner hoặc Agent là gì?

**Trả lời:**

Runner hoặc Agent là máy thực thi các Job trong pipeline.

Nó có thể là:

* Máy ảo.
* Server vật lý.
* Docker Container.
* Kubernetes Pod.
* Máy do nền tảng cung cấp.
* Máy tự quản lý.

GitHub Actions thường gọi là **Runner**, Jenkins thường gọi là **Agent**.

---

## 10. Trigger trong CI/CD là gì?

**Trả lời:**

Trigger là sự kiện làm pipeline bắt đầu chạy.

Ví dụ:

* Push code.
* Tạo Pull Request.
* Merge vào `main`.
* Tạo tag.
* Chạy thủ công.
* Theo lịch.
* Gọi API.
* Workflow khác hoàn thành.

---

## 11. Vì sao cần CI/CD?

**Trả lời:**

CI/CD giúp:

* Phát hiện lỗi sớm.
* Giảm thao tác thủ công.
* Deploy nhất quán.
* Tăng tốc phát hành.
* Dễ rollback.
* Có lịch sử triển khai.
* Giảm sai sót do con người.
* Chuẩn hóa quy trình làm việc.

---

## 12. Một pipeline tốt cần đặc điểm gì?

**Trả lời:**

Một pipeline tốt nên:

* Có thể chạy lặp lại với kết quả nhất quán.
* Thất bại sớm khi có lỗi.
* Không để lộ secret.
* Có log rõ ràng.
* Có timeout.
* Có khả năng retry hợp lý.
* Tách rõ test, build và deploy.
* Có cơ chế rollback.
* Không phụ thuộc quá nhiều vào thao tác thủ công.

# II. Jenkins

## 13. Jenkins là gì?

**Trả lời:**

Jenkins là Automation Server thường được sử dụng để xây dựng CI/CD Pipeline.

Jenkins hỗ trợ:

* Build.
* Test.
* Deploy.
* Chạy tác vụ theo lịch.
* Tích hợp Git.
* Docker.
* Kubernetes.
* Hệ thống Plugin lớn.

---

## 14. Jenkins Controller và Agent là gì?

**Trả lời:**

**Controller** quản lý:

* Pipeline.
* Lịch chạy.
* Cấu hình.
* Phân phối công việc.
* Giao diện quản trị.

**Agent** thực thi Job.

```text
Jenkins Controller
     ├── Java Agent
     ├── Node.js Agent
     └── Docker Build Agent
```

Không nên để Controller thực hiện tất cả công việc nặng.

---

## 15. Jenkins Job là gì?

**Trả lời:**

Job là một tác vụ được cấu hình để Jenkins thực hiện.

Ví dụ:

* Build ứng dụng.
* Chạy test.
* Deploy production.
* Backup Database.
* Quét lỗ hổng bảo mật.

---

## 16. Jenkins Pipeline là gì?

**Trả lời:**

Jenkins Pipeline là quy trình CI/CD được mô tả bằng mã nguồn, thường nằm trong file `Jenkinsfile`.

Ví dụ:

```groovy
pipeline {
    agent any

    stages {
        stage('Test') {
            steps {
                sh 'npm ci'
                sh 'npm test'
            }
        }

        stage('Build') {
            steps {
                sh 'npm run build'
            }
        }
    }
}
```

---

## 17. Jenkinsfile là gì?

**Trả lời:**

`Jenkinsfile` là file định nghĩa pipeline Jenkins bằng Groovy DSL.

Nó thường được lưu cùng source code để:

* Theo dõi lịch sử bằng Git.
* Review thay đổi pipeline.
* Đồng bộ pipeline với ứng dụng.
* Khôi phục phiên bản cũ.

Đây là cách tiếp cận **Pipeline as Code**.

---

## 18. Declarative và Scripted Pipeline khác nhau thế nào?

**Trả lời:**

**Declarative Pipeline:**

* Cấu trúc rõ ràng.
* Dễ đọc.
* Có cú pháp chuẩn như `pipeline`, `stages`, `steps`.
* Phù hợp phần lớn dự án.

**Scripted Pipeline:**

* Linh hoạt hơn.
* Dùng cú pháp Groovy tự do.
* Phù hợp luồng rất phức tạp.
* Khó đọc và bảo trì hơn.

---

## 19. `agent any` trong Jenkins nghĩa là gì?

**Trả lời:**

```groovy
agent any
```

nghĩa là pipeline có thể chạy trên bất kỳ Jenkins Agent nào đang phù hợp và khả dụng.

Có thể chỉ định Agent bằng label:

```groovy
agent {
    label 'docker'
}
```

---

## 20. Jenkins Stage dùng để làm gì?

**Trả lời:**

Stage chia pipeline thành các giai đoạn dễ quan sát.

Ví dụ:

```groovy
stages {
    stage('Test') {
        steps {
            sh 'pytest'
        }
    }

    stage('Deploy') {
        steps {
            sh './deploy.sh'
        }
    }
}
```

Nếu pipeline lỗi, có thể nhanh chóng biết lỗi nằm ở giai đoạn nào.

---

## 21. Jenkins Credentials dùng để làm gì?

**Trả lời:**

Jenkins Credentials lưu thông tin nhạy cảm như:

* Username/password.
* SSH private key.
* API token.
* Secret text.
* Certificate.

Pipeline chỉ tham chiếu credential bằng ID, không nên ghi secret trực tiếp trong `Jenkinsfile`.

---

## 22. Làm thế nào dùng secret trong Jenkins Pipeline?

**Trả lời:**

Có thể sử dụng `withCredentials`:

```groovy
withCredentials([
    string(
        credentialsId: 'docker-token',
        variable: 'DOCKER_TOKEN'
    )
]) {
    sh 'docker login -u user -p "$DOCKER_TOKEN"'
}
```

Cần tránh:

* In secret ra log.
* Ghi secret vào artifact.
* Dùng lệnh khiến secret xuất hiện trong process list nếu có lựa chọn an toàn hơn.

---

## 23. Jenkins Plugin là gì?

**Trả lời:**

Plugin mở rộng khả năng của Jenkins.

Ví dụ:

* Git.
* Docker.
* Kubernetes.
* Pipeline.
* Credentials.
* Slack Notification.

Nhược điểm là quá nhiều Plugin có thể gây:

* Xung đột.
* Rủi ro bảo mật.
* Khó nâng cấp.
* Jenkins khởi động chậm.

---

## 24. Multibranch Pipeline là gì?

**Trả lời:**

Multibranch Pipeline tự động phát hiện các branch chứa `Jenkinsfile` và tạo pipeline riêng cho từng branch.

Ví dụ:

```text
main
develop
feature/login
feature/payment
```

Mỗi branch có thể được build và test độc lập.

---

## 25. Jenkins Shared Library là gì?

**Trả lời:**

Shared Library cho phép tái sử dụng logic pipeline giữa nhiều repository.

Ví dụ các dự án đều cần:

* Build Docker Image.
* Push Registry.
* Deploy Kubernetes.
* Gửi thông báo.

Thay vì sao chép code, có thể đặt logic chung trong Shared Library.

---

## 26. Jenkins có thể chạy Agent trên Kubernetes như thế nào?

**Trả lời:**

Jenkins có thể tạo Agent tạm thời dưới dạng Kubernetes Pod.

```text
Jenkins Controller
      ↓
Tạo Agent Pod
      ↓
Chạy Job
      ↓
Xóa Agent Pod
```

Lợi ích:

* Scale linh hoạt.
* Mỗi Job có môi trường cô lập.
* Không cần duy trì nhiều Agent cố định.

---

## 27. Nhược điểm của Jenkins là gì?

**Trả lời:**

* Phải tự cài đặt và vận hành.
* Cần cập nhật Controller và Plugin.
* Cấu hình có thể phức tạp.
* Có thể trở thành điểm lỗi trung tâm.
* Cần quản lý Agent.
* Giao diện và quyền truy cập cần cấu hình cẩn thận.

# III. GitHub Actions

## 28. GitHub Actions là gì?

**Trả lời:**

GitHub Actions là nền tảng Automation và CI/CD tích hợp trực tiếp trong GitHub.

Workflow được định nghĩa bằng YAML trong:

```text
.github/workflows/
```

Ví dụ:

```text
.github/workflows/ci.yml
```

---

## 29. Workflow trong GitHub Actions là gì?

**Trả lời:**

Workflow là một quy trình Automation gồm một hoặc nhiều Job.

Ví dụ:

```yaml
name: CI

on:
  push:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test
```

---

## 30. Event trong GitHub Actions là gì?

**Trả lời:**

Event là sự kiện kích hoạt Workflow.

Ví dụ:

```yaml
on:
  push:
  pull_request:
  workflow_dispatch:
```

Các Event phổ biến:

* `push`.
* `pull_request`.
* `schedule`.
* `workflow_dispatch`.
* `repository_dispatch`.
* `workflow_call`.

---

## 31. Job trong GitHub Actions là gì?

**Trả lời:**

Job là tập hợp các Step chạy trên cùng một Runner.

Mặc định, các Job chạy song song nếu không khai báo phụ thuộc.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest

  build:
    runs-on: ubuntu-latest
```

---

## 32. Step là gì?

**Trả lời:**

Step là một bước trong Job.

Step có thể:

* Chạy shell command bằng `run`.
* Dùng một Action có sẵn bằng `uses`.

```yaml
steps:
  - uses: actions/checkout@v4
  - run: npm ci
  - run: npm test
```

---

## 33. `uses` và `run` khác nhau thế nào?

**Trả lời:**

`uses` gọi một Action có sẵn:

```yaml
- uses: actions/checkout@v4
```

`run` thực thi câu lệnh shell:

```yaml
- run: npm test
```

---

## 34. GitHub-hosted Runner là gì?

**Trả lời:**

GitHub-hosted Runner là máy tạm thời do GitHub cung cấp để chạy Job.

Ví dụ:

```yaml
runs-on: ubuntu-latest
```

Ưu điểm:

* Không cần quản lý Server.
* Môi trường sạch cho mỗi Job.
* Dễ sử dụng.

---

## 35. Self-hosted Runner là gì?

**Trả lời:**

Self-hosted Runner là máy do tổ chức tự quản lý.

Phù hợp khi cần:

* Truy cập mạng nội bộ.
* Phần cứng đặc biệt.
* GPU.
* Cache lớn.
* Môi trường tùy chỉnh.

Cần bảo mật cẩn thận vì Workflow có thể chạy mã trên máy này.

---

## 36. `needs` dùng để làm gì?

**Trả lời:**

`needs` thiết lập thứ tự phụ thuộc giữa các Job.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest

  deploy:
    needs: test
    runs-on: ubuntu-latest
```

Job `deploy` chỉ chạy sau khi `test` thành công.

---

## 37. Matrix Strategy là gì?

**Trả lời:**

Matrix Strategy chạy cùng một Job với nhiều cấu hình.

Ví dụ kiểm thử nhiều phiên bản Python:

```yaml
strategy:
  matrix:
    python-version:
      - "3.11"
      - "3.12"
      - "3.13"
```

Hoặc nhiều hệ điều hành:

```yaml
matrix:
  os:
    - ubuntu-latest
    - windows-latest
```

---

## 38. GitHub Actions Secret dùng để làm gì?

**Trả lời:**

Secret lưu dữ liệu nhạy cảm như:

* API key.
* Registry token.
* Password.
* Cloud credential.

Sử dụng:

```yaml
env:
  API_TOKEN: ${{ secrets.API_TOKEN }}
```

Không nên commit secret trực tiếp vào repository.

---

## 39. Variables và Secrets khác nhau thế nào?

**Trả lời:**

* **Variables:** Dùng cho cấu hình không nhạy cảm.
* **Secrets:** Dùng cho dữ liệu nhạy cảm và được che trong log khi có thể.

Ví dụ Variable:

```text
APP_ENV=production
```

Ví dụ Secret:

```text
DATABASE_PASSWORD
```

---

## 40. Environment trong GitHub Actions là gì?

**Trả lời:**

Environment đại diện cho môi trường triển khai như:

* Development.
* Staging.
* Production.

Environment có thể có:

* Secret riêng.
* Variable riêng.
* Quy tắc phê duyệt.
* Giới hạn branch được phép deploy.

---

## 41. Reusable Workflow là gì?

**Trả lời:**

Reusable Workflow cho phép một Workflow gọi Workflow khác bằng `workflow_call`.

Phù hợp khi nhiều repository dùng chung quy trình:

* Test.
* Build Docker.
* Deploy.
* Security Scan.

Nó giúp tránh sao chép YAML.

---

## 42. Composite Action là gì?

**Trả lời:**

Composite Action đóng gói nhiều Step thành một Action tái sử dụng.

Khác với Reusable Workflow:

* Composite Action tái sử dụng ở cấp Step.
* Reusable Workflow tái sử dụng toàn bộ Workflow hoặc Job.

---

## 43. `workflow_dispatch` dùng để làm gì?

**Trả lời:**

`workflow_dispatch` cho phép chạy Workflow thủ công.

Có thể định nghĩa input:

```yaml
on:
  workflow_dispatch:
    inputs:
      environment:
        required: true
        type: choice
        options:
          - staging
          - production
```

---

## 44. `schedule` trong GitHub Actions hoạt động thế nào?

**Trả lời:**

`schedule` chạy Workflow theo biểu thức cron.

```yaml
on:
  schedule:
    - cron: "0 0 * * *"
```

Ví dụ trên chạy theo lịch hằng ngày.

Cần chú ý cron của GitHub Actions sử dụng múi giờ UTC.

---

## 45. Làm thế nào truyền dữ liệu giữa các Job?

**Trả lời:**

Có thể sử dụng:

* Job outputs cho dữ liệu nhỏ.
* Artifact cho file.
* Registry cho Docker Image.
* External Storage nếu phù hợp.

Ví dụ artifact:

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: build-output
    path: dist/
```

---

## 46. Concurrency trong GitHub Actions là gì?

**Trả lời:**

Concurrency kiểm soát nhiều Workflow hoặc Job chạy đồng thời.

Ví dụ chỉ cho một deployment production chạy tại một thời điểm:

```yaml
concurrency:
  group: production
  cancel-in-progress: false
```

Nó giúp tránh hai pipeline cùng deploy và ghi đè nhau.

---

## 47. Permissions trong GitHub Actions dùng để làm gì?

**Trả lời:**

Permissions giới hạn quyền của `GITHUB_TOKEN`.

Ví dụ:

```yaml
permissions:
  contents: read
  packages: write
```

Nên cấp quyền tối thiểu cần thiết theo nguyên tắc least privilege.

---

## 48. OIDC trong GitHub Actions dùng để làm gì?

**Trả lời:**

OIDC cho phép Workflow nhận credential ngắn hạn từ Cloud Provider thay vì lưu access key dài hạn trong Secret.

Lợi ích:

* Giảm rủi ro lộ key.
* Credential hết hạn nhanh.
* Có thể giới hạn theo repository, branch và environment.

# IV. Apache Airflow

## 49. Apache Airflow là gì?

**Trả lời:**

Apache Airflow là nền tảng điều phối Workflow, thường dùng cho:

* Data Pipeline.
* ETL/ELT.
* Machine Learning Pipeline.
* Báo cáo định kỳ.
* Xử lý dữ liệu theo lịch.
* Điều phối nhiều tác vụ phụ thuộc nhau.

Workflow trong Airflow được định nghĩa bằng Python.

---

## 50. Airflow có phải công cụ CI/CD không?

**Trả lời:**

Airflow không phải công cụ CI/CD chính.

Airflow tập trung vào điều phối Workflow dữ liệu và tác vụ theo lịch.

Jenkins và GitHub Actions tập trung nhiều hơn vào:

* Build.
* Test.
* Đóng gói.
* Deploy phần mềm.

Có thể sử dụng GitHub Actions để triển khai DAG Airflow, nhưng Airflow chịu trách nhiệm chạy Data Workflow.

---

## 51. DAG trong Airflow là gì?

**Trả lời:**

DAG là viết tắt của **Directed Acyclic Graph**.

DAG mô tả các Task và quan hệ phụ thuộc giữa chúng.

```text
Extract
   ↓
Transform
   ↓
Load
```

“Acyclic” nghĩa là không có vòng lặp phụ thuộc.

---

## 52. Task trong Airflow là gì?

**Trả lời:**

Task là một đơn vị công việc trong DAG.

Ví dụ:

* Tải dữ liệu.
* Làm sạch dữ liệu.
* Chạy câu SQL.
* Gọi API.
* Huấn luyện mô hình.
* Gửi báo cáo.

---

## 53. Operator là gì?

**Trả lời:**

Operator là mẫu định nghĩa loại công việc Task sẽ thực hiện.

Ví dụ:

* `PythonOperator`.
* `BashOperator`.
* SQL Operator.
* Docker Operator.
* Kubernetes Pod Operator.

Một Task thường là một instance của Operator.

---

## 54. Ví dụ DAG Airflow đơn giản

```python
from datetime import datetime

from airflow import DAG
from airflow.operators.python import PythonOperator


def extract() -> None:
    print("Extract data")


def transform() -> None:
    print("Transform data")


with DAG(
    dag_id="etl_pipeline",
    start_date=datetime(2026, 1, 1),
    schedule="@daily",
    catchup=False,
) as dag:
    extract_task = PythonOperator(
        task_id="extract",
        python_callable=extract,
    )

    transform_task = PythonOperator(
        task_id="transform",
        python_callable=transform,
    )

    extract_task >> transform_task
```

---

## 55. Scheduler trong Airflow làm gì?

**Trả lời:**

Scheduler:

* Đọc DAG.
* Xác định Task nào đến lịch chạy.
* Kiểm tra dependency.
* Gửi Task cho Executor thực thi.

Scheduler không nhất thiết tự thực hiện toàn bộ công việc của Task.

---

## 56. Executor trong Airflow là gì?

**Trả lời:**

Executor quyết định cách Task được thực thi.

Tùy cấu hình, Task có thể chạy:

* Trong tiến trình cục bộ.
* Qua hàng đợi Worker.
* Trong Kubernetes Pod.
* Trên nhiều Worker phân tán.

---

## 57. Airflow Worker là gì?

**Trả lời:**

Worker là thành phần thực thi Task trong các mô hình Executor phân tán.

Ví dụ:

```text
Airflow Scheduler
      ↓
Message Broker
      ↓
Workers
```

Nhiều Worker giúp tăng khả năng xử lý song song.

---

## 58. Airflow Metadata Database dùng để làm gì?

**Trả lời:**

Metadata Database lưu:

* Trạng thái DAG Run.
* Trạng thái Task Instance.
* Lịch sử chạy.
* Connection.
* Variable.
* Thông tin lập lịch.

Nó không nên được dùng để lưu toàn bộ dữ liệu nghiệp vụ của Data Pipeline.

---

## 59. XCom là gì?

**Trả lời:**

XCom cho phép các Task trao đổi một lượng dữ liệu nhỏ.

Ví dụ:

* ID.
* Đường dẫn file.
* Trạng thái.
* Giá trị tổng hợp nhỏ.

Không nên truyền file lớn hoặc DataFrame lớn qua XCom. Nên lưu dữ liệu lớn trong:

* Object Storage.
* Database.
* Data Warehouse.

Sau đó chỉ truyền đường dẫn hoặc ID qua XCom.

---

## 60. Airflow Variable và Connection khác nhau thế nào?

**Trả lời:**

**Variable** lưu cấu hình chung dạng key-value.

Ví dụ:

```text
output_bucket=data-results
```

**Connection** lưu thông tin kết nối đến hệ thống bên ngoài:

* Database.
* API.
* Cloud.
* Message Broker.

Dữ liệu nhạy cảm nên được quản lý qua Secret Backend phù hợp.

---

## 61. `schedule` trong DAG là gì?

**Trả lời:**

`schedule` xác định lịch chạy DAG.

Ví dụ:

```python
schedule="@daily"
```

hoặc biểu thức cron:

```python
schedule="0 2 * * *"
```

---

## 62. `start_date` trong Airflow là gì?

**Trả lời:**

`start_date` xác định thời điểm bắt đầu lịch của DAG.

Nó không đơn giản chỉ có nghĩa “chạy ngay từ thời điểm này”. Airflow lập lịch theo các khoảng dữ liệu, vì vậy cần hiểu thời điểm logical date và data interval khi debug lịch chạy.

---

## 63. `catchup` là gì?

**Trả lời:**

Nếu `catchup=True`, Airflow có thể tạo các DAG Run cho những khoảng thời gian đã bị bỏ lỡ kể từ `start_date`.

Nếu:

```python
catchup=False
```

Airflow thường chỉ chạy các khoảng mới, không chạy bù toàn bộ lịch sử.

---

## 64. Backfill là gì?

**Trả lời:**

Backfill là chạy lại Workflow cho các khoảng thời gian trong quá khứ.

Ví dụ:

* Chạy lại pipeline từ ngày 1 đến ngày 10.
* Tính lại báo cáo tháng trước.
* Xử lý lại dữ liệu sau khi sửa logic.

Task cần được thiết kế idempotent để backfill an toàn.

---

## 65. Sensor trong Airflow là gì?

**Trả lời:**

Sensor là Task chờ một điều kiện xảy ra.

Ví dụ:

* Chờ file xuất hiện.
* Chờ Task ở DAG khác hoàn thành.
* Chờ dữ liệu có trong Database.
* Chờ API trả trạng thái hoàn tất.

Không nên để Sensor chiếm Worker lâu không cần thiết; có thể dùng chế độ phù hợp như reschedule hoặc deferrable operator khi được hỗ trợ.

---

## 66. Retry trong Airflow được cấu hình thế nào?

**Trả lời:**

Có thể đặt số lần retry và thời gian chờ:

```python
from datetime import timedelta

default_args = {
    "retries": 3,
    "retry_delay": timedelta(minutes=5),
}
```

Chỉ nên retry các lỗi có thể phục hồi, không nên retry vô hạn khi dữ liệu đầu vào sai.

---

## 67. Trigger Rule là gì?

**Trả lời:**

Trigger Rule xác định điều kiện để Task được chạy dựa trên trạng thái của các Task phía trước.

Ví dụ:

* Chỉ chạy nếu tất cả thành công.
* Chạy nếu ít nhất một Task thành công.
* Chạy dù Task trước thành công hay thất bại.

Phù hợp với Task dọn dẹp hoặc gửi thông báo cuối pipeline.

---

## 68. Task idempotent là gì?

**Trả lời:**

Task idempotent có thể chạy lại nhiều lần mà không làm dữ liệu bị trùng hoặc sai.

Ví dụ:

Thay vì luôn `INSERT`, có thể dùng:

* Upsert.
* Ghi đè partition theo ngày.
* Kiểm tra processing ID.
* Xóa dữ liệu của khoảng thời gian trước khi ghi lại.

Đây là đặc điểm rất quan trọng trong Airflow vì Task có thể được retry hoặc backfill.

# V. So sánh Jenkins, GitHub Actions và Airflow

## 69. Jenkins và GitHub Actions khác nhau thế nào?

**Trả lời:**

| Jenkins                          | GitHub Actions                 |
| -------------------------------- | ------------------------------ |
| Thường phải tự vận hành          | Tích hợp trực tiếp GitHub      |
| Pipeline bằng Jenkinsfile/Groovy | Workflow bằng YAML             |
| Plugin rất phong phú             | Marketplace Actions            |
| Kiểm soát hạ tầng cao            | Bắt đầu nhanh                  |
| Cần quản lý Controller/Agent     | Có GitHub-hosted Runner        |
| Phù hợp hệ thống tùy chỉnh       | Phù hợp repository trên GitHub |

---

## 70. GitHub Actions và Airflow khác nhau thế nào?

**Trả lời:**

**GitHub Actions:**

* Kích hoạt chủ yếu bởi sự kiện Git.
* Build, test và deploy ứng dụng.
* Workflow thường gắn với repository.

**Airflow:**

* Điều phối pipeline dữ liệu.
* Chạy theo lịch và data interval.
* Theo dõi dependency giữa các Task.
* Hỗ trợ backfill và retry dữ liệu.

---

## 71. Jenkins và Airflow khác nhau thế nào?

**Trả lời:**

Jenkins tập trung vào Automation chung và CI/CD.

Airflow tập trung vào Workflow có dependency, lịch chạy và xử lý dữ liệu.

Không nên dùng Airflow thay Jenkins để build mọi Pull Request; cũng không nên dùng Jenkins để quản lý Data Pipeline phức tạp hàng ngày nếu Airflow phù hợp hơn.

---

## 72. Khi nào nên chọn Jenkins?

**Trả lời:**

Chọn Jenkins khi:

* Cần tự quản lý hạ tầng CI/CD.
* Có nhiều hệ thống source control.
* Pipeline tùy chỉnh phức tạp.
* Cần Agent đặc biệt.
* Tổ chức đã có hệ sinh thái Jenkins.
* Cần chạy trong mạng nội bộ hoàn toàn.

---

## 73. Khi nào nên chọn GitHub Actions?

**Trả lời:**

Chọn GitHub Actions khi:

* Source code nằm trên GitHub.
* Muốn thiết lập CI/CD nhanh.
* Không muốn vận hành CI Server.
* Cần tích hợp chặt với Pull Request.
* Workflow không yêu cầu hạ tầng quá đặc biệt.
* Muốn tận dụng Marketplace Actions.

---

## 74. Khi nào nên chọn Airflow?

**Trả lời:**

Chọn Airflow khi:

* Có Data Pipeline nhiều bước.
* Cần chạy theo lịch.
* Cần retry và backfill.
* Có dependency giữa các Task.
* Cần theo dõi trạng thái từng lần xử lý.
* Có ETL, ML Pipeline hoặc báo cáo định kỳ.

# VI. Câu hỏi tình huống phỏng vấn

## Tình huống 1: Pipeline test mất quá nhiều thời gian

**Hỏi:** Bạn sẽ tối ưu như thế nào?

**Trả lời:**

Tôi sẽ:

1. Chạy các Job độc lập song song.
2. Cache dependency.
3. Chỉ chạy test bị ảnh hưởng nếu quy trình cho phép.
4. Tách Unit Test và Integration Test.
5. Dùng Image có sẵn dependency.
6. Kiểm tra bước nào là nút thắt.
7. Không tải hoặc build lại artifact không cần thiết.
8. Dùng matrix hợp lý, tránh tạo quá nhiều Job.

---

## Tình huống 2: Hai pipeline cùng deploy production

**Hỏi:** Có rủi ro gì?

**Trả lời:**

Hai pipeline có thể:

* Ghi đè phiên bản của nhau.
* Chạy migration đồng thời.
* Làm trạng thái deployment không xác định.
* Gây rollback nhầm phiên bản.

Cần sử dụng:

* Concurrency lock.
* Deployment queue.
* Environment protection.
* Một pipeline deploy tại một thời điểm.

---

## Tình huống 3: Test thành công nhưng deploy thất bại

**Trả lời:**

Tôi sẽ kiểm tra:

* Credential.
* Network.
* Registry.
* Image tag.
* Cấu hình môi trường.
* Resource limit.
* Health Check.
* Migration Database.
* Log của hệ thống triển khai.

Không nên build lại một artifact khác khi deploy. Nên deploy đúng artifact đã được test.

---

## Tình huống 4: Secret bị ghi ra log

**Hỏi:** Bạn xử lý thế nào?

**Trả lời:**

1. Thu hồi hoặc thay đổi secret ngay.
2. Xóa hoặc hạn chế quyền truy cập log nếu có thể.
3. Kiểm tra secret đã được sử dụng trái phép chưa.
4. Sửa pipeline để không echo secret.
5. Sử dụng secret store.
6. Cấp quyền tối thiểu.
7. Cân nhắc credential ngắn hạn như OIDC.

Chỉ che log không đủ nếu secret đã bị lộ.

---

## Tình huống 5: Deploy thành công nhưng ứng dụng lỗi

**Trả lời:**

Pipeline không nên chỉ kiểm tra lệnh deploy thành công.

Cần thêm:

* Readiness Check.
* Smoke Test.
* Health endpoint.
* Theo dõi error rate.
* Cơ chế rollback.

Ví dụ:

```text
Deploy
→ Chờ ứng dụng Ready
→ Chạy Smoke Test
→ Thành công hoặc Rollback
```

## Tình huống 6: Airflow Task chạy lại tạo dữ liệu trùng

**Hỏi:** Bạn sửa như thế nào?

**Trả lời:**

Thiết kế Task idempotent:

* Upsert theo khóa.
* Dùng Unique Constraint.
* Ghi theo data interval.
* Xóa partition cũ trước khi ghi lại.
* Lưu processing ID.
* Tránh thao tác append không kiểm soát.

---

## Tình huống 7: Airflow DAG không chạy đúng giờ mong muốn

**Trả lời:**

Tôi sẽ kiểm tra:

1. Múi giờ của Airflow.
2. `start_date`.
3. Biểu thức cron.
4. `catchup`.
5. Data interval.
6. Scheduler có hoạt động không.
7. DAG có bị pause không.
8. Có giới hạn concurrency hoặc pool không.

---

## Tình huống 8: Airflow Worker bị lỗi giữa Task

**Trả lời:**

Task có thể được đánh dấu thất bại và chạy lại tùy cấu hình retry.

Vì vậy:

* Task phải idempotent.
* Dữ liệu trung gian nên lưu bền vững.
* Không chỉ lưu trong ổ đĩa tạm của Worker.
* Cần log và checkpoint phù hợp.

---

## Tình huống 9: GitHub Actions cần deploy vào mạng nội bộ

**Trả lời:**

Có thể dùng Self-hosted Runner đặt trong mạng nội bộ.

Cần bảo mật:

* Chỉ chạy Workflow đáng tin cậy.
* Không dùng chung Runner nhạy cảm cho Pull Request không tin cậy.
* Hạn chế quyền hệ điều hành.
* Cô lập Runner.
* Xóa dữ liệu sau mỗi Job nếu cần.

---

## Tình huống 10: Nên dùng Jenkins hay GitHub Actions?

**Trả lời mẫu:**

Nếu source code nằm trên GitHub và pipeline không yêu cầu hạ tầng đặc biệt, tôi ưu tiên GitHub Actions vì thiết lập nhanh và tích hợp Pull Request tốt.

Nếu công ty cần tự quản lý toàn bộ CI/CD, dùng nhiều hệ thống Git hoặc có pipeline và Agent đặc thù trong mạng nội bộ, Jenkins có thể phù hợp hơn.

# VII. Câu hỏi nâng cao

## 75. Pipeline as Code là gì?

**Trả lời:**

Pipeline as Code là việc định nghĩa quy trình CI/CD bằng file mã nguồn.

Ví dụ:

* `Jenkinsfile`.
* `.github/workflows/ci.yml`.

Lợi ích:

* Có version control.
* Code review.
* Dễ rollback.
* Đồng bộ với source code.
* Có thể tái sử dụng.

---

## 76. Immutable Artifact là gì?

**Trả lời:**

Immutable Artifact là artifact đã build thì không bị sửa đổi.

Ví dụ:

```text
user-service:1.4.2
```

Artifact được test ở staging phải là chính artifact được deploy production.

Không nên build lại từ source cho từng môi trường vì có thể tạo ra kết quả khác nhau.

---

## 77. Blue-Green Deployment là gì?

**Trả lời:**

Blue-Green Deployment duy trì hai môi trường:

* Blue: Phiên bản hiện tại.
* Green: Phiên bản mới.

Sau khi kiểm tra Green, hệ thống chuyển traffic sang Green.

Nếu có lỗi, có thể chuyển lại Blue nhanh chóng.

---

## 78. Canary Deployment là gì?

**Trả lời:**

Canary Deployment đưa phiên bản mới đến một phần nhỏ traffic trước.

Ví dụ:

```text
95% → Version cũ
5%  → Version mới
```

Nếu metric ổn định, tăng dần traffic cho phiên bản mới.

---

## 79. Rollback và Roll-forward khác nhau thế nào?

**Trả lời:**

* **Rollback:** Quay về phiên bản trước.
* **Roll-forward:** Sửa lỗi và triển khai phiên bản mới hơn.

Rollback nhanh nhưng có thể khó nếu Database Schema đã thay đổi không tương thích.

---

## 80. Database Migration nên chạy ở đâu trong pipeline?

**Trả lời:**

Migration nên là bước được kiểm soát riêng, có:

* Backup hoặc kế hoạch phục hồi.
* Lock để tránh chạy đồng thời.
* Script tương thích ngược.
* Log rõ ràng.
* Kiểm tra trạng thái.

Nên ưu tiên chiến lược **expand and contract**:

1. Thêm schema mới nhưng vẫn hỗ trợ phiên bản cũ.
2. Deploy code mới.
3. Di chuyển dữ liệu.
4. Chỉ xóa schema cũ khi không còn được sử dụng.

# VIII. Câu trả lời ngắn nên ghi nhớ

**CI là gì?**

> CI tự động kiểm tra và tích hợp code thường xuyên để phát hiện lỗi sớm.

**CD là gì?**

> CD tự động chuẩn bị hoặc triển khai ứng dụng sau khi code vượt qua kiểm thử.

**Jenkins là gì?**

> Jenkins là Automation Server tự quản lý, hỗ trợ xây dựng pipeline CI/CD bằng Jenkinsfile và hệ thống Plugin.

**GitHub Actions là gì?**

> GitHub Actions là nền tảng Automation tích hợp GitHub, định nghĩa Workflow bằng YAML và chạy theo các sự kiện của repository.

**Airflow là gì?**

> Airflow là nền tảng điều phối Data Workflow bằng DAG, hỗ trợ lập lịch, dependency, retry và backfill.

**Jenkins khác Airflow thế nào?**

> Jenkins chủ yếu phục vụ build, test và deploy phần mềm; Airflow chủ yếu điều phối pipeline dữ liệu theo lịch.

**Luồng CI/CD phổ biến:**

```text
Developer Push
      ↓
CI Pipeline
├── Lint
├── Test
├── Build
└── Security Scan
      ↓
Artifact Registry
      ↓
CD Pipeline
├── Deploy Staging
├── Smoke Test
├── Approval
└── Deploy Production
```

**Luồng Airflow phổ biến:**

```text
Schedule
   ↓
Extract
   ↓
Validate
   ↓
Transform
   ↓
Load
   ↓
Report/Notify
```
