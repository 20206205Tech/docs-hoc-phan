Dưới đây là bộ câu hỏi phỏng vấn về **Docker, Kubernetes và Argo CD**, phù hợp với vị trí **Lập trình viên Fresher/Junior Backend, DevOps hoặc Microservices**.

# I. Docker

## 1. Docker là gì?

**Trả lời:**

Docker là nền tảng dùng để đóng gói ứng dụng cùng thư viện, dependency và cấu hình cần thiết vào **Container**.

Nhờ đó, ứng dụng có thể chạy nhất quán trên:

* Máy lập trình viên.
* Máy kiểm thử.
* Server.
* Cloud.
* Kubernetes.

---

## 2. Container là gì?

**Trả lời:**

Container là một tiến trình được cô lập, có đầy đủ môi trường cần thiết để chạy ứng dụng.

Container sử dụng chung Kernel của hệ điều hành Host nhưng có:

* File system riêng.
* Network riêng.
* Process namespace riêng.
* Giới hạn CPU và RAM riêng.

---

## 3. Container khác Virtual Machine như thế nào?

| Container                | Virtual Machine          |
| ------------------------ | ------------------------ |
| Chia sẻ Kernel của Host  | Có hệ điều hành riêng    |
| Nhẹ hơn                  | Nặng hơn                 |
| Khởi động nhanh          | Khởi động chậm hơn       |
| Thường có kích thước nhỏ | Thường có kích thước lớn |
| Cô lập ở mức tiến trình  | Cô lập ở mức máy ảo      |

---

## 4. Docker Image là gì?

**Trả lời:**

Docker Image là mẫu chỉ đọc dùng để tạo Container.

Image chứa:

* Source code hoặc file build.
* Runtime.
* Thư viện.
* Cấu hình mặc định.
* Lệnh khởi động.

Ví dụ:

```text
node:22-alpine
postgres:17
nginx:alpine
```

---

## 5. Docker Container khác Docker Image thế nào?

**Trả lời:**

* **Image:** Bản mẫu để tạo môi trường chạy.
* **Container:** Một instance đang chạy hoặc đã dừng được tạo từ Image.

Một Image có thể tạo ra nhiều Container.

```text
Image: user-service:1.0
   ├── Container 1
   ├── Container 2
   └── Container 3
```

---

## 6. Dockerfile là gì?

**Trả lời:**

Dockerfile là file chứa các chỉ thị dùng để xây dựng Docker Image.

Ví dụ:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY . .

EXPOSE 3000

CMD ["node", "dist/main.js"]
```

---

## 7. `FROM` trong Dockerfile dùng để làm gì?

**Trả lời:**

`FROM` xác định Base Image.

Ví dụ:

```dockerfile
FROM python:3.12-slim
```

Nghĩa là Image mới được xây dựng dựa trên Python 3.12 bản slim.

---

## 8. `RUN` và `CMD` khác nhau như thế nào?

**Trả lời:**

`RUN` được thực thi trong quá trình build Image:

```dockerfile
RUN npm install
```

`CMD` xác định lệnh mặc định khi Container khởi động:

```dockerfile
CMD ["npm", "start"]
```

Một Dockerfile có thể có nhiều `RUN`, nhưng thông thường chỉ có một `CMD` có hiệu lực.

---

## 9. `CMD` và `ENTRYPOINT` khác nhau như thế nào?

**Trả lời:**

`ENTRYPOINT` xác định chương trình chính luôn được chạy.

`CMD` thường cung cấp lệnh hoặc tham số mặc định và dễ bị ghi đè khi chạy Container.

Ví dụ:

```dockerfile
ENTRYPOINT ["python"]
CMD ["main.py"]
```

Container mặc định chạy:

```bash
python main.py
```

---

## 10. `COPY` và `ADD` khác nhau thế nào?

**Trả lời:**

`COPY` chỉ sao chép file hoặc thư mục vào Image.

```dockerfile
COPY . /app
```

`ADD` có thêm một số chức năng như tự giải nén file archive cục bộ.

Thông thường nên ưu tiên `COPY` vì hành vi rõ ràng hơn.

---

## 11. `WORKDIR` dùng để làm gì?

**Trả lời:**

`WORKDIR` đặt thư mục làm việc cho các lệnh tiếp theo.

```dockerfile
WORKDIR /app
```

Sau đó `RUN`, `COPY`, `CMD` và các chỉ thị liên quan sẽ làm việc trong `/app`.

---

## 12. `.dockerignore` dùng để làm gì?

**Trả lời:**

`.dockerignore` loại bỏ những file không cần thiết khỏi Build Context.

Ví dụ:

```text
node_modules
.git
.env
dist
coverage
*.log
```

Lợi ích:

* Build nhanh hơn.
* Image nhỏ hơn.
* Tránh đưa secret vào Image.

---

## 13. Build Context là gì?

**Trả lời:**

Build Context là tập hợp file được gửi cho Docker Engine trong quá trình build.

Ví dụ:

```bash
docker build -t user-service:1.0 .
```

Dấu `.` là Build Context hiện tại.

---

## 14. Các lệnh Docker cơ bản là gì?

**Trả lời:**

```bash
docker build -t my-app:1.0 .
docker images
docker run -d -p 8080:3000 my-app:1.0
docker ps
docker ps -a
docker logs container-name
docker exec -it container-name sh
docker stop container-name
docker rm container-name
docker rmi my-app:1.0
```

---

## 15. `docker run -p 8080:3000` nghĩa là gì?

**Trả lời:**

```bash
docker run -p 8080:3000 my-app
```

Trong đó:

* `8080`: Port trên Host.
* `3000`: Port bên trong Container.

Client truy cập:

```text
localhost:8080
```

Request được chuyển tới port `3000` trong Container.

---

## 16. Docker Volume là gì?

**Trả lời:**

Volume dùng để lưu dữ liệu bên ngoài vòng đời của Container.

Ví dụ, nếu Container PostgreSQL bị xóa nhưng dữ liệu nằm trong Volume thì dữ liệu vẫn còn.

```bash
docker run \
  -v postgres_data:/var/lib/postgresql/data \
  postgres
```

---

## 17. Bind Mount và Volume khác nhau thế nào?

**Trả lời:**

* **Volume:** Do Docker quản lý, phù hợp lưu dữ liệu lâu dài.
* **Bind Mount:** Ánh xạ trực tiếp một thư mục trên Host vào Container.

Ví dụ Bind Mount:

```bash
docker run -v ./src:/app/src my-app
```

Bind Mount thường dùng khi phát triển để thay đổi source code trực tiếp.

---

## 18. Docker Network là gì?

**Trả lời:**

Docker Network cho phép các Container giao tiếp với nhau.

Các Container trong cùng một network có thể gọi nhau bằng tên Container hoặc tên Service.

```text
backend → database:5432
```

Không nên dùng `localhost` để Container này gọi Container khác vì `localhost` chỉ trỏ về chính Container hiện tại.

---

## 19. Docker Compose là gì?

**Trả lời:**

Docker Compose dùng để định nghĩa và chạy nhiều Container bằng một file YAML.

Ví dụ:

```yaml
services:
  api:
    build: .
    ports:
      - "8000:8000"
    depends_on:
      - database

  database:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

Chạy bằng:

```bash
docker compose up -d
```

---

## 20. `depends_on` có đảm bảo Database đã sẵn sàng không?

**Trả lời:**

Không hoàn toàn.

`depends_on` chủ yếu kiểm soát thứ tự khởi động Container. Database có thể đã khởi động Container nhưng chưa sẵn sàng nhận kết nối.

Có thể dùng:

* Health Check.
* Retry trong ứng dụng.
* Script chờ Database.

---

## 21. Multi-stage Build là gì?

**Trả lời:**

Multi-stage Build chia quá trình build thành nhiều giai đoạn.

Ví dụ:

```dockerfile
FROM node:22-alpine AS builder

WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine

WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist

CMD ["node", "dist/main.js"]
```

Lợi ích:

* Image nhỏ hơn.
* Không chứa công cụ build.
* Giảm bề mặt tấn công.

---

## 22. Tại sao không nên chạy Container bằng quyền root?

**Trả lời:**

Nếu ứng dụng bị khai thác, kẻ tấn công có thể có quyền cao bên trong Container.

Nên tạo User riêng:

```dockerfile
RUN addgroup -S app && adduser -S app -G app
USER app
```

---

## 23. Tại sao Container tự dừng ngay sau khi chạy?

**Trả lời:**

Container tồn tại khi tiến trình chính PID 1 còn chạy.

Nếu lệnh chính kết thúc hoặc bị lỗi, Container sẽ dừng.

Kiểm tra bằng:

```bash
docker logs container-name
docker inspect container-name
```

---

## 24. Cách giảm kích thước Docker Image?

**Trả lời:**

* Dùng Base Image nhỏ phù hợp.
* Dùng Multi-stage Build.
* Không copy file không cần thiết.
* Sử dụng `.dockerignore`.
* Không cài dependency development trong Image production.
* Gộp các lệnh `RUN` phù hợp.
* Xóa cache của package manager.

---

# II. Kubernetes

## 25. Kubernetes là gì?

**Trả lời:**

Kubernetes là nền tảng điều phối Container.

Nó hỗ trợ:

* Triển khai ứng dụng.
* Scale Container.
* Self-healing.
* Service discovery.
* Load balancing.
* Rolling update.
* Quản lý cấu hình và secret.

---

## 26. Kubernetes Cluster gồm những thành phần nào?

**Trả lời:**

Một Cluster thường gồm:

```text
Control Plane
  ├── API Server
  ├── Scheduler
  ├── Controller Manager
  └── etcd

Worker Nodes
  ├── kubelet
  ├── Container Runtime
  └── kube-proxy hoặc thành phần mạng tương đương
```

---

## 27. Control Plane là gì?

**Trả lời:**

Control Plane quản lý trạng thái toàn bộ Cluster.

Nó quyết định:

* Pod chạy ở Node nào.
* Khi nào cần tạo hoặc xóa Pod.
* Trạng thái mong muốn của tài nguyên.
* Cách phản ứng khi tài nguyên gặp lỗi.

---

## 28. Kubernetes API Server có vai trò gì?

**Trả lời:**

API Server là cổng giao tiếp trung tâm của Kubernetes.

Các thành phần như:

* `kubectl`.
* Controller.
* Scheduler.
* Argo CD.

đều làm việc với Cluster thông qua API Server.

---

## 29. etcd là gì?

**Trả lời:**

etcd là hệ thống key-value phân tán lưu trạng thái và cấu hình của Kubernetes Cluster.

Ví dụ:

* Deployment.
* Service.
* ConfigMap.
* Secret.
* Trạng thái Node.

etcd là thành phần rất quan trọng và cần được backup.

---

## 30. Scheduler dùng để làm gì?

**Trả lời:**

Scheduler chọn Node phù hợp để chạy Pod dựa trên:

* CPU và RAM.
* Node selector.
* Affinity và anti-affinity.
* Taint và toleration.
* Các ràng buộc tài nguyên khác.

---

## 31. Pod là gì?

**Trả lời:**

Pod là đơn vị triển khai nhỏ nhất trong Kubernetes.

Một Pod có thể chứa một hoặc nhiều Container dùng chung:

* Địa chỉ IP.
* Network namespace.
* Volume.
* Vòng đời.

Thông thường một Pod chứa một Container ứng dụng chính.

---

## 32. Vì sao không nên tạo Pod trực tiếp?

**Trả lời:**

Pod trực tiếp không được tự động tạo lại nếu bị xóa hoặc Node gặp lỗi.

Thường nên tạo Pod thông qua Controller như:

* Deployment.
* StatefulSet.
* DaemonSet.
* Job.

---

## 33. Deployment là gì?

**Trả lời:**

Deployment quản lý các Pod stateless thông qua ReplicaSet.

Nó hỗ trợ:

* Duy trì số lượng Pod.
* Rolling Update.
* Rollback.
* Scale.
* Tự tạo lại Pod bị lỗi.

---

## 34. ReplicaSet là gì?

**Trả lời:**

ReplicaSet đảm bảo luôn có đúng số lượng Pod mong muốn.

Ví dụ:

```yaml
spec:
  replicas: 3
```

Nếu một Pod bị xóa, ReplicaSet tạo Pod mới thay thế.

Thông thường ReplicaSet được quản lý bởi Deployment.

---

## 35. StatefulSet là gì?

**Trả lời:**

StatefulSet phù hợp với ứng dụng cần danh tính và lưu trữ ổn định.

Ví dụ:

* Database.
* Kafka.
* RabbitMQ Cluster.
* Elasticsearch.

Pod của StatefulSet có tên ổn định:

```text
database-0
database-1
database-2
```

---

## 36. DaemonSet là gì?

**Trả lời:**

DaemonSet đảm bảo một Pod chạy trên mỗi Node hoặc một nhóm Node.

Thường dùng cho:

* Log agent.
* Monitoring agent.
* Network plugin.
* Security agent.

---

## 37. Job và CronJob khác nhau thế nào?

**Trả lời:**

`Job` chạy một tác vụ cho đến khi hoàn thành.

Ví dụ:

* Database migration.
* Import dữ liệu.

`CronJob` tạo Job theo lịch.

Ví dụ:

```text
Backup mỗi ngày lúc 00:00
```

---

## 38. Kubernetes Service là gì?

**Trả lời:**

Service cung cấp địa chỉ mạng ổn định để truy cập một nhóm Pod.

Pod có thể bị thay thế và đổi IP, nhưng Service vẫn giữ địa chỉ và DNS ổn định.

---

## 39. Các loại Service phổ biến là gì?

**Trả lời:**

* `ClusterIP`: Chỉ truy cập bên trong Cluster.
* `NodePort`: Mở một port trên mỗi Node.
* `LoadBalancer`: Yêu cầu Cloud Load Balancer.
* `ExternalName`: Ánh xạ đến một DNS bên ngoài.

---

## 40. ClusterIP dùng khi nào?

**Trả lời:**

ClusterIP dùng cho giao tiếp nội bộ.

Ví dụ:

```text
Conversation Service → RabbitMQ
Chatbot Service → Redis
API Service → PostgreSQL
```

Những dịch vụ này không cần public ra Internet.

---

## 41. Ingress là gì?

**Trả lời:**

Ingress định nghĩa quy tắc định tuyến HTTP/HTTPS từ bên ngoài vào các Service.

Ví dụ:

```text
api.example.com/users    → User Service
api.example.com/payments → Payment Service
```

Ingress cần một Ingress Controller như:

* Nginx Ingress.
* Kong Ingress Controller.
* Traefik.

---

## 42. ConfigMap là gì?

**Trả lời:**

ConfigMap lưu cấu hình không nhạy cảm.

Ví dụ:

```text
APP_ENV=production
LOG_LEVEL=info
RABBITMQ_HOST=rabbitmq
```

ConfigMap có thể được đưa vào Pod dưới dạng:

* Environment Variable.
* File được mount.

---

## 43. Secret là gì?

**Trả lời:**

Secret dùng để lưu dữ liệu nhạy cảm như:

* Password.
* Token.
* API key.
* TLS certificate.

Tuy nhiên, Secret trong Kubernetes không mặc định đồng nghĩa với mã hóa an toàn tuyệt đối. Cần kết hợp:

* Encryption at rest.
* RBAC.
* External Secrets Manager.
* Sealed Secrets hoặc giải pháp tương đương.

---

## 44. Liveness Probe là gì?

**Trả lời:**

Liveness Probe kiểm tra Container còn hoạt động đúng hay không.

Nếu Probe thất bại nhiều lần, Kubernetes có thể khởi động lại Container.

Ví dụ:

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 3000
```

---

## 45. Readiness Probe là gì?

**Trả lời:**

Readiness Probe kiểm tra Pod đã sẵn sàng nhận traffic chưa.

Nếu thất bại:

* Pod vẫn có thể tiếp tục chạy.
* Pod bị loại khỏi danh sách Endpoint của Service.
* Request không được chuyển đến Pod đó.

---

## 46. Startup Probe là gì?

**Trả lời:**

Startup Probe dành cho ứng dụng khởi động chậm.

Trong thời gian Startup Probe chưa thành công, Kubernetes chưa thực hiện Liveness Probe, tránh restart ứng dụng quá sớm.

---

## 47. Requests và Limits là gì?

**Trả lời:**

`requests` là tài nguyên tối thiểu Pod yêu cầu để Scheduler chọn Node.

`limits` là giới hạn tối đa Container được sử dụng.

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

---

## 48. Điều gì xảy ra khi Container vượt CPU Limit?

**Trả lời:**

Container có thể bị CPU throttling, nghĩa là bị hạn chế tốc độ sử dụng CPU.

---

## 49. Điều gì xảy ra khi Container vượt Memory Limit?

**Trả lời:**

Container có thể bị hệ thống kết thúc với trạng thái:

```text
OOMKilled
```

Sau đó Kubernetes có thể khởi động lại Container tùy Restart Policy và Controller.

---

## 50. PersistentVolume và PersistentVolumeClaim là gì?

**Trả lời:**

* **PersistentVolume (PV):** Tài nguyên lưu trữ trong Cluster.
* **PersistentVolumeClaim (PVC):** Yêu cầu lưu trữ của ứng dụng.

```text
Pod
 ↓
PVC
 ↓
PV
 ↓
Disk/Storage
```

---

## 51. StorageClass là gì?

**Trả lời:**

StorageClass định nghĩa cách Kubernetes tự động cấp phát storage.

PVC yêu cầu dung lượng, StorageClass tạo PV tương ứng thông qua Storage Provider.

---

## 52. Namespace là gì?

**Trả lời:**

Namespace dùng để phân chia tài nguyên trong một Cluster.

Ví dụ:

```text
development
staging
production
monitoring
argocd
```

Namespace giúp quản lý:

* Quyền truy cập.
* Resource quota.
* Tên tài nguyên.
* Môi trường.

---

## 53. Kubernetes DNS hoạt động thế nào?

**Trả lời:**

Service trong Kubernetes có DNS nội bộ.

Ví dụ Service tên `rabbitmq` trong Namespace `messaging`:

```text
rabbitmq.messaging.svc.cluster.local
```

Trong cùng Namespace có thể gọi ngắn:

```text
rabbitmq
```

---

## 54. Rolling Update là gì?

**Trả lời:**

Rolling Update thay thế Pod cũ bằng Pod mới từng phần, giúp hạn chế downtime.

Ví dụ:

```text
Version 1: 3 Pod
  ↓
Tạo Pod Version 2
  ↓
Pod mới Ready
  ↓
Xóa dần Pod Version 1
```

---

## 55. Rollback Deployment như thế nào?

**Trả lời:**

```bash
kubectl rollout history deployment/user-service
kubectl rollout undo deployment/user-service
```

Có thể rollback về revision cụ thể:

```bash
kubectl rollout undo deployment/user-service --to-revision=2
```

---

## 56. HPA là gì?

**Trả lời:**

Horizontal Pod Autoscaler tự động thay đổi số lượng Pod dựa trên metric.

Ví dụ:

* CPU.
* Memory.
* Request rate.
* Custom metrics.

```text
CPU tăng → tăng số Pod
CPU giảm → giảm số Pod
```

---

## 57. Taint và Toleration dùng để làm gì?

**Trả lời:**

Taint đặt trên Node để ngăn Pod không phù hợp được schedule lên Node đó.

Toleration đặt trên Pod để cho phép Pod chạy trên Node có Taint tương ứng.

Ví dụ dành riêng Node GPU cho AI workload.

---

## 58. Node Affinity và Pod Anti-Affinity là gì?

**Trả lời:**

Node Affinity quy định Pod nên hoặc phải chạy trên loại Node nào.

Pod Anti-Affinity giúp tránh đặt các Pod giống nhau trên cùng một Node.

Ví dụ ba Pod API nên phân tán trên ba Node để tăng tính sẵn sàng.

---

# III. Argo CD và GitOps

## 59. GitOps là gì?

**Trả lời:**

GitOps là phương pháp quản lý hệ thống bằng cách lưu trạng thái mong muốn trong Git.

Luồng tổng quát:

```text
Developer
   ↓ Push manifest
Git Repository
   ↓
Argo CD
   ↓ Synchronize
Kubernetes Cluster
```

Git trở thành nguồn sự thật cho cấu hình triển khai.

---

## 60. Argo CD là gì?

**Trả lời:**

Argo CD là công cụ Continuous Delivery theo mô hình GitOps dành cho Kubernetes.

Argo CD:

* Theo dõi Git Repository.
* So sánh Git với trạng thái Cluster.
* Phát hiện chênh lệch.
* Đồng bộ manifest vào Kubernetes.
* Hỗ trợ rollback và lịch sử triển khai.

---

## 61. Argo CD khác Jenkins hoặc GitHub Actions như thế nào?

**Trả lời:**

Jenkins hoặc GitHub Actions thường thực hiện CI:

* Build source code.
* Chạy test.
* Build Docker Image.
* Push Image lên Registry.

Argo CD thường thực hiện CD:

* Theo dõi manifest trong Git.
* Đồng bộ manifest vào Kubernetes.

```text
GitHub Actions
  → Build Image
  → Push Registry
  → Update Manifest

Argo CD
  → Phát hiện Manifest mới
  → Deploy vào Kubernetes
```

---

## 62. Push-based Deployment và Pull-based Deployment khác nhau thế nào?

**Trả lời:**

Push-based:

```text
CI Pipeline → gọi trực tiếp Kubernetes API
```

Pipeline cần credential của Cluster.

Pull-based với Argo CD:

```text
Argo CD trong Cluster → đọc Git → đồng bộ Cluster
```

Lợi ích:

* Giảm việc cấp Cluster credential cho CI.
* Tự phát hiện cấu hình bị thay đổi ngoài Git.
* Phù hợp GitOps.

---

## 63. Argo CD Application là gì?

**Trả lời:**

Application là tài nguyên mô tả:

* Git Repository nào được theo dõi.
* Thư mục hoặc Helm Chart nào.
* Revision hoặc branch nào.
* Cluster đích.
* Namespace đích.
* Chính sách đồng bộ.

---

## 64. Trạng thái `Synced` và `OutOfSync` là gì?

**Trả lời:**

* `Synced`: Trạng thái trong Cluster giống với cấu hình trong Git.
* `OutOfSync`: Trạng thái Cluster khác Git.

Ví dụ:

* Git yêu cầu 3 replica.
* Cluster đang chạy 2 replica.

Khi đó Application là `OutOfSync`.

---

## 65. Healthy và Synced khác nhau thế nào?

**Trả lời:**

`Synced` nói về sự giống nhau giữa Git và Cluster.

`Healthy` nói về tình trạng hoạt động của tài nguyên.

Một Application có thể:

* `Synced` nhưng `Degraded`: Manifest đúng với Git nhưng Pod bị crash.
* `OutOfSync` nhưng `Healthy`: Ứng dụng vẫn chạy nhưng cấu hình khác Git.

---

## 66. Manual Sync và Automatic Sync khác nhau thế nào?

**Trả lời:**

Manual Sync yêu cầu người dùng bấm Sync hoặc chạy lệnh.

Automatic Sync cho phép Argo CD tự động áp dụng thay đổi khi Git thay đổi.

Ví dụ:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

---

## 67. `selfHeal` trong Argo CD là gì?

**Trả lời:**

`selfHeal` cho phép Argo CD khôi phục tài nguyên nếu có người sửa trực tiếp trong Cluster làm trạng thái khác Git.

Ví dụ:

```bash
kubectl scale deployment user-service --replicas=10
```

Nếu Git ghi `replicas: 3`, Argo CD có thể đưa Deployment trở lại 3 replica.

---

## 68. `prune` là gì?

**Trả lời:**

`prune` cho phép Argo CD xóa tài nguyên khỏi Cluster khi tài nguyên đó đã bị xóa khỏi Git.

Cần sử dụng cẩn thận vì có thể xóa tài nguyên quan trọng nếu cấu hình Git sai.

---

## 69. Vì sao không nên sửa trực tiếp tài nguyên bằng `kubectl edit` khi dùng GitOps?

**Trả lời:**

Thay đổi trực tiếp không được ghi vào Git nên:

* Không có lịch sử rõ ràng.
* Có thể bị Argo CD hoàn tác.
* Gây chênh lệch giữa Git và Cluster.
* Khó audit.

Nên sửa manifest trong Git rồi để Argo CD đồng bộ.

---

## 70. Argo CD hỗ trợ những định dạng triển khai nào?

**Trả lời:**

Argo CD có thể làm việc với:

* Kubernetes YAML.
* Helm.
* Kustomize.
* Jsonnet.
* Các công cụ tạo manifest khác thông qua cơ chế mở rộng phù hợp.

---

## 71. Helm là gì?

**Trả lời:**

Helm là package manager cho Kubernetes.

Helm Chart gồm các template YAML có thể tái sử dụng với nhiều giá trị cấu hình.

Ví dụ:

```text
chart/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    └── service.yaml
```

---

## 72. Kustomize là gì?

**Trả lời:**

Kustomize dùng để tùy chỉnh Kubernetes manifest mà không cần viết template theo cách của Helm.

Ví dụ:

```text
base/
overlays/
  ├── development/
  ├── staging/
  └── production/
```

Mỗi môi trường có thể patch cấu hình từ base.

---

## 73. App of Apps Pattern là gì?

**Trả lời:**

App of Apps là mô hình một Argo CD Application cha quản lý nhiều Application con.

```text
Root Application
  ├── User Service
  ├── Payment Service
  ├── RabbitMQ
  ├── Redis
  └── Monitoring
```

Mô hình này giúp quản lý nhiều ứng dụng theo cấu trúc Git tập trung.

---

## 74. ApplicationSet là gì?

**Trả lời:**

ApplicationSet tự động tạo nhiều Argo CD Application từ một mẫu.

Phù hợp khi:

* Triển khai cùng ứng dụng vào nhiều Cluster.
* Có nhiều môi trường.
* Có nhiều thư mục hoặc Microservice.
* Muốn tự động phát hiện cấu hình từ Git.

---

## 75. Argo CD Rollback hoạt động thế nào?

**Trả lời:**

Có thể chọn revision trước trong lịch sử triển khai.

Tuy nhiên, theo GitOps, cách rõ ràng nhất thường là:

1. Revert commit trong Git.
2. Push commit revert.
3. Để Argo CD đồng bộ trạng thái cũ.

Như vậy Git vẫn phản ánh đúng trạng thái đang chạy.

---

# IV. Câu hỏi tình huống phỏng vấn

## Tình huống 1: Container chạy được ở máy local nhưng lỗi trên Server

**Hỏi:** Bạn kiểm tra gì?

**Trả lời:**

Tôi sẽ kiểm tra:

1. Environment Variable.
2. Architecture của Image.
3. Port ứng dụng.
4. Quyền truy cập file.
5. Log Container.
6. Kết nối Database và dịch vụ phụ thuộc.
7. Image tag có đúng không.
8. Có mount thiếu file hoặc Volume không.

---

## Tình huống 2: Pod có trạng thái `CrashLoopBackOff`

**Hỏi:** Bạn xử lý như thế nào?

**Trả lời:**

Kiểm tra:

```bash
kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>
kubectl logs <pod-name> --previous
```

Các nguyên nhân phổ biến:

* Ứng dụng lỗi khi khởi động.
* Thiếu Environment Variable.
* Không kết nối được Database.
* Liveness Probe sai.
* Command hoặc entrypoint sai.
* Thiếu quyền truy cập.
* OOMKilled.

---

## Tình huống 3: Pod đang `Running` nhưng không nhận request

**Trả lời:**

Tôi kiểm tra:

1. Readiness Probe.
2. Service selector có khớp label Pod không.
3. Service có Endpoint không.
4. Ứng dụng lắng nghe trên `0.0.0.0` hay chỉ `localhost`.
5. `targetPort` có đúng không.
6. Ingress và DNS.
7. NetworkPolicy.
8. Log ứng dụng.

```bash
kubectl get endpoints
kubectl describe service <service-name>
```

---

## Tình huống 4: Pod bị `Pending`

**Trả lời:**

Nguyên nhân có thể là:

* Không đủ CPU hoặc RAM.
* PVC chưa được bind.
* Node selector không khớp.
* Taint chưa có Toleration.
* Affinity quá chặt.
* Không có Node phù hợp.

Kiểm tra:

```bash
kubectl describe pod <pod-name>
```

---

## Tình huống 5: Pod bị `ImagePullBackOff`

**Trả lời:**

Kiểm tra:

* Image name và tag.
* Image có tồn tại trong Registry không.
* Registry có private không.
* `imagePullSecrets`.
* Node có kết nối được Registry không.
* Credential đã hết hạn chưa.

---

## Tình huống 6: Deploy phiên bản mới nhưng Pod mới không Ready

**Trả lời:**

Deployment có thể dừng Rolling Update và giữ lại một số Pod cũ tùy chiến lược.

Tôi sẽ kiểm tra:

* Log Pod mới.
* Readiness Probe.
* Cấu hình mới.
* Secret và ConfigMap.
* Database migration.
* Image tag.
* Resource limit.

Nếu cần, rollback về phiên bản ổn định.

---

## Tình huống 7: Argo CD báo `OutOfSync`

**Trả lời:**

Tôi sẽ:

1. Xem Diff giữa Git và Cluster.
2. Kiểm tra có ai sửa trực tiếp bằng `kubectl` không.
3. Kiểm tra manifest được render bởi Helm/Kustomize.
4. Xác định khác biệt có hợp lệ không.
5. Sửa Git hoặc Sync lại từ Git.

Không nên chỉ bấm Sync mà không hiểu nguyên nhân.

---

## Tình huống 8: Argo CD báo `Synced` nhưng ứng dụng lỗi

**Trả lời:**

`Synced` chỉ có nghĩa là Cluster giống Git, không đảm bảo ứng dụng chạy đúng.

Tôi sẽ kiểm tra:

* Health status.
* Pod status.
* Container log.
* Probe.
* Service Endpoint.
* Dependency.
* Database migration.
* Metric và tracing.

---

## Tình huống 9: Có người xóa Pod thủ công

**Hỏi:** Điều gì xảy ra?

**Trả lời:**

Nếu Pod thuộc Deployment, ReplicaSet sẽ tạo Pod mới để duy trì số replica.

Nếu tạo Pod trực tiếp không có Controller quản lý, Pod sẽ không tự động được tạo lại.

---

## Tình huống 10: Cần lưu dữ liệu PostgreSQL trên Kubernetes

**Trả lời:**

Tôi sẽ cân nhắc:

* StatefulSet.
* PersistentVolumeClaim.
* StorageClass.
* Backup và restore.
* Anti-affinity.
* Pod disruption.
* Replication.

Với hệ thống production quan trọng, có thể ưu tiên dịch vụ Database được quản lý thay vì tự vận hành Database trong Kubernetes.

# V. Câu hỏi nâng cao

## 1. Vì sao không nên dùng tag `latest` trong production?

**Trả lời:**

Tag `latest` không xác định chính xác phiên bản Image.

Nó gây khó:

* Audit.
* Rollback.
* Debug.
* Xác định Image đang chạy.

Nên dùng tag cố định:

```text
user-service:1.4.2
```

hoặc Image digest:

```text
user-service@sha256:...
```

---

## 2. ConfigMap hoặc Secret thay đổi thì Pod có tự khởi động lại không?

**Trả lời:**

Không phải mọi trường hợp.

Nếu truyền qua Environment Variable, Pod thường cần được restart để nhận giá trị mới.

Nếu mount dưới dạng Volume, file có thể được cập nhật sau một khoảng thời gian, nhưng ứng dụng phải hỗ trợ đọc lại cấu hình.

Một cách phổ biến là thay đổi annotation checksum trong Pod Template để Deployment tạo Pod mới.

---

## 3. Argo CD có nên quản lý Secret trực tiếp trong Git không?

**Trả lời:**

Không nên lưu Secret dạng rõ trong Git.

Có thể sử dụng:

* Sealed Secrets.
* External Secrets Operator.
* Vault.
* Cloud Secret Manager.
* SOPS.

Git chỉ nên chứa dữ liệu đã mã hóa hoặc tham chiếu đến hệ thống quản lý Secret.

---

## 4. Kubernetes có đảm bảo Zero Downtime không?

**Trả lời:**

Không tự động trong mọi trường hợp.

Để hạn chế downtime cần:

* Có nhiều replica.
* Readiness Probe chính xác.
* Rolling Update phù hợp.
* Graceful shutdown.
* PodDisruptionBudget.
* Backend tương thích giữa các phiên bản.
* Database migration an toàn.

---

## 5. Vì sao cần Graceful Shutdown?

**Trả lời:**

Khi Pod bị dừng, Kubernetes gửi tín hiệu kết thúc cho Container.

Ứng dụng nên:

1. Ngừng nhận request mới.
2. Hoàn thành request đang xử lý.
3. Đóng kết nối Database và Message Broker.
4. Thoát trong thời gian cho phép.

Nếu không, request hoặc message đang xử lý có thể bị mất.

---

## 6. GitOps có nghĩa là mọi thứ đều phải lưu trong Git không?

**Trả lời:**

Không nhất thiết mọi dữ liệu đều lưu trực tiếp trong Git.

Git nên lưu trạng thái khai báo và tham chiếu cần thiết. Dữ liệu nhạy cảm có thể nằm trong Secret Manager, còn Git lưu tài nguyên External Secret hoặc dữ liệu đã mã hóa.

# VI. Câu trả lời ngắn cần ghi nhớ

**Docker là gì?**

> Docker đóng gói ứng dụng cùng dependency vào Container để chạy nhất quán trên nhiều môi trường.

**Kubernetes là gì?**

> Kubernetes là nền tảng điều phối Container, hỗ trợ triển khai, scale, self-healing và rolling update.

**Argo CD là gì?**

> Argo CD là công cụ Continuous Delivery theo GitOps, tự động đồng bộ trạng thái trong Git vào Kubernetes.

**Pod khác Container thế nào?**

> Container là môi trường chạy ứng dụng, còn Pod là đơn vị triển khai nhỏ nhất của Kubernetes và có thể chứa một hoặc nhiều Container.

**Deployment dùng để làm gì?**

> Deployment quản lý Pod stateless, số replica, rolling update và rollback.

**Service dùng để làm gì?**

> Service cung cấp địa chỉ mạng và DNS ổn định để truy cập một nhóm Pod.

**Liveness khác Readiness thế nào?**

> Liveness kiểm tra có cần restart Container không; Readiness kiểm tra Pod có sẵn sàng nhận traffic không.

**GitOps là gì?**

> GitOps sử dụng Git làm nguồn sự thật cho cấu hình hệ thống và dùng công cụ như Argo CD để đồng bộ Cluster.

**Luồng CI/CD phổ biến:**

```text
Developer
   ↓ Push source code
GitHub Actions
   ├── Test
   ├── Build Docker Image
   ├── Push Image Registry
   └── Update Kubernetes Manifest
                ↓
              GitOps Repository
                ↓
              Argo CD
                ↓
          Kubernetes Cluster
```
