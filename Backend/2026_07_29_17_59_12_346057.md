Dưới đây là bộ câu hỏi phỏng vấn về **Domain-Driven Design (DDD) và Hexagonal Architecture**, phù hợp với vị trí **Lập trình viên Fresher/Junior Backend, Microservices hoặc Software Engineer**.

# I. Tổng quan DDD

## 1. Domain-Driven Design là gì?

**Trả lời:**

Domain-Driven Design, viết tắt là **DDD**, là phương pháp thiết kế phần mềm tập trung vào nghiệp vụ cốt lõi của hệ thống.

DDD giúp:

* Mô hình hóa đúng nghiệp vụ.
* Tạo ngôn ngữ chung giữa kỹ thuật và nghiệp vụ.
* Chia hệ thống thành các ranh giới rõ ràng.
* Giảm phụ thuộc giữa các miền nghiệp vụ.
* Giúp hệ thống lớn dễ bảo trì và mở rộng.

DDD không phải framework hoặc kiến trúc triển khai cụ thể.

---

## 2. Domain là gì?

**Trả lời:**

Domain là lĩnh vực nghiệp vụ mà phần mềm giải quyết.

Ví dụ:

* Thương mại điện tử.
* Ngân hàng.
* Giáo dục.
* Tư vấn pháp luật.
* Quản lý bệnh viện.

Trong hệ thống thương mại điện tử, nghiệp vụ có thể gồm quản lý đơn hàng, thanh toán, sản phẩm và vận chuyển.

---

## 3. Subdomain là gì?

**Trả lời:**

Subdomain là một phần nhỏ hơn của Domain.

Ví dụ Domain thương mại điện tử có:

```text
E-commerce Domain
├── Order
├── Payment
├── Product
├── Inventory
└── Shipping
```

Mỗi Subdomain giải quyết một nhóm vấn đề nghiệp vụ cụ thể.

---

## 4. Core Domain là gì?

**Trả lời:**

Core Domain là phần nghiệp vụ quan trọng nhất, tạo ra lợi thế cạnh tranh hoặc giá trị chính cho doanh nghiệp.

Ví dụ:

* Hệ thống AI pháp luật: xử lý và trả lời câu hỏi pháp lý.
* Sàn thương mại điện tử: quản lý giao dịch và đề xuất sản phẩm.
* Nền tảng học tập: hệ thống đánh giá và cá nhân hóa nội dung.

Core Domain nên nhận nhiều nguồn lực thiết kế nhất.

---

## 5. Supporting Subdomain là gì?

**Trả lời:**

Supporting Subdomain hỗ trợ Core Domain nhưng không trực tiếp tạo lợi thế cạnh tranh.

Ví dụ:

* Quản lý thông báo.
* Quản lý tài liệu.
* Báo cáo nội bộ.
* Quản lý hồ sơ người dùng.

Nó thường cần được phát triển riêng theo yêu cầu của doanh nghiệp.

---

## 6. Generic Subdomain là gì?

**Trả lời:**

Generic Subdomain là chức năng phổ biến, nhiều hệ thống đều cần và thường có thể sử dụng giải pháp sẵn có.

Ví dụ:

* Authentication.
* Gửi email.
* Logging.
* Thanh toán qua nhà cung cấp.
* Lưu trữ file.

Không nhất thiết phải tự phát triển toàn bộ Generic Subdomain.

---

## 7. Ubiquitous Language là gì?

**Trả lời:**

Ubiquitous Language là ngôn ngữ chung được sử dụng thống nhất bởi:

* Lập trình viên.
* Chuyên gia nghiệp vụ.
* Business Analyst.
* Tester.
* Product Owner.

Ngôn ngữ này được sử dụng trong:

* Cuộc họp.
* Tài liệu.
* Tên class.
* Tên method.
* API.
* Event.

Ví dụ, nếu nghiệp vụ gọi là `Order`, mã nguồn không nên lúc dùng `Order`, lúc dùng `Purchase`, lúc dùng `Transaction` cho cùng một khái niệm.

---

## 8. Bounded Context là gì?

**Trả lời:**

Bounded Context là ranh giới mà bên trong đó một Domain Model có ý nghĩa thống nhất.

Một thuật ngữ có thể mang ý nghĩa khác nhau trong các Bounded Context khác nhau.

Ví dụ `Customer`:

* Trong Sales Context: người mua hàng.
* Trong Shipping Context: người nhận hàng.
* Trong Support Context: người gửi yêu cầu hỗ trợ.

Không nên ép toàn bộ hệ thống sử dụng một mô hình `Customer` khổng lồ.

---

## 9. Bounded Context và Subdomain khác nhau thế nào?

**Trả lời:**

* **Subdomain:** Phân chia không gian nghiệp vụ.
* **Bounded Context:** Ranh giới của mô hình phần mềm.

Subdomain thuộc về phân tích nghiệp vụ, còn Bounded Context thuộc về thiết kế giải pháp.

Trong nhiều trường hợp, một Subdomain được triển khai bằng một Bounded Context, nhưng không phải lúc nào cũng tương ứng một-một.

---

## 10. Context Map là gì?

**Trả lời:**

Context Map mô tả quan hệ giữa các Bounded Context.

Ví dụ:

```text
Order Context
     │ OrderCreated
     ▼
Payment Context
     │ PaymentCompleted
     ▼
Shipping Context
```

Context Map giúp thể hiện:

* Context nào cung cấp dữ liệu.
* Context nào phụ thuộc.
* Giao tiếp bằng API hay Event.
* Có cần lớp chuyển đổi dữ liệu không.

# II. Tactical Design trong DDD

## 11. Entity là gì?

**Trả lời:**

Entity là đối tượng được xác định bởi danh tính, không chỉ bởi giá trị thuộc tính.

Ví dụ:

```text
User ID: 100
Order ID: ORD-001
Document ID: DOC-123
```

Dù thuộc tính của `Order` thay đổi, nó vẫn là cùng một Order nếu ID không đổi.

---

## 12. Value Object là gì?

**Trả lời:**

Value Object là đối tượng không có danh tính riêng, được so sánh bằng giá trị.

Ví dụ:

* Money.
* Address.
* Email.
* DateRange.
* Coordinates.

Ví dụ TypeScript:

```typescript
class Money {
  constructor(
    readonly amount: number,
    readonly currency: string,
  ) {
    if (amount < 0) {
      throw new Error("Amount cannot be negative");
    }
  }

  equals(other: Money): boolean {
    return (
      this.amount === other.amount &&
      this.currency === other.currency
    );
  }
}
```

---

## 13. Entity và Value Object khác nhau thế nào?

**Trả lời:**

| Entity                     | Value Object                  |
| -------------------------- | ----------------------------- |
| Có danh tính               | Không có danh tính            |
| So sánh bằng ID            | So sánh bằng giá trị          |
| Có vòng đời riêng          | Thường thuộc về Entity        |
| Có thể thay đổi trạng thái | Thường được thiết kế bất biến |

---

## 14. Vì sao Value Object nên bất biến?

**Trả lời:**

Bất biến giúp:

* Tránh thay đổi ngoài ý muốn.
* Dễ kiểm thử.
* Dễ chia sẻ giữa nhiều thành phần.
* Dễ đảm bảo quy tắc nghiệp vụ.

Thay vì sửa Value Object cũ, hệ thống tạo Value Object mới.

---

## 15. Aggregate là gì?

**Trả lời:**

Aggregate là nhóm Entity và Value Object được quản lý như một đơn vị nhất quán.

Ví dụ:

```text
Order Aggregate
├── Order — Aggregate Root
├── OrderItem
├── ShippingAddress
└── Money
```

Các quy tắc nhất quán của Aggregate phải được đảm bảo trong một transaction.

---

## 16. Aggregate Root là gì?

**Trả lời:**

Aggregate Root là Entity chính và là điểm truy cập duy nhất từ bên ngoài vào Aggregate.

Ví dụ:

```typescript
order.addItem(productId, quantity);
order.cancel();
```

Không nên để bên ngoài cập nhật trực tiếp `OrderItem` mà bỏ qua `Order`, vì có thể vi phạm quy tắc nghiệp vụ.

---

## 17. Vì sao Aggregate không nên quá lớn?

**Trả lời:**

Aggregate quá lớn gây:

* Transaction dài.
* Khóa nhiều dữ liệu.
* Khó xử lý đồng thời.
* Khó scale.
* Tăng nguy cơ conflict.
* Phải tải quá nhiều dữ liệu.

Aggregate chỉ nên chứa những thành phần cần nhất quán tức thời.

---

## 18. Có được tham chiếu trực tiếp Aggregate khác không?

**Trả lời:**

Thông thường nên tham chiếu Aggregate khác bằng ID.

Ví dụ:

```typescript
class Order {
  constructor(
    readonly id: string,
    readonly customerId: string,
  ) {}
}
```

Không nên nhúng toàn bộ `Customer` Aggregate vào `Order`, vì làm tăng coupling và kích thước Aggregate.

---

## 19. Repository trong DDD là gì?

**Trả lời:**

Repository là abstraction dùng để tải và lưu Aggregate.

Ví dụ:

```typescript
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}
```

Domain hoặc Application Layer phụ thuộc vào interface, không phụ thuộc trực tiếp MySQL, PostgreSQL hoặc MongoDB.

---

## 20. Repository khác DAO thế nào?

**Trả lời:**

DAO thường tập trung vào cấu trúc dữ liệu và thao tác Database:

```text
findRow
insertRecord
updateTable
```

Repository tập trung vào Domain:

```text
findOrderById
saveOrder
findActiveSubscriptions
```

Repository thường làm việc với Aggregate hoặc Domain Object thay vì bản ghi Database thuần túy.

---

## 21. Domain Service là gì?

**Trả lời:**

Domain Service chứa nghiệp vụ không phù hợp đặt trong một Entity hoặc Value Object cụ thể.

Ví dụ chuyển tiền giữa hai tài khoản:

```typescript
class TransferService {
  transfer(
    source: Account,
    destination: Account,
    amount: Money,
  ): void {
    source.withdraw(amount);
    destination.deposit(amount);
  }
}
```

Nghiệp vụ liên quan đến nhiều Aggregate nên khó đặt hoàn toàn trong một Entity.

---

## 22. Application Service là gì?

**Trả lời:**

Application Service điều phối một Use Case.

Nó thường:

1. Nhận Command hoặc DTO.
2. Tải Aggregate qua Repository.
3. Gọi phương thức nghiệp vụ.
4. Lưu Aggregate.
5. Publish Event hoặc gọi Port.

Application Service không nên chứa phần lớn Business Logic.

---

## 23. Application Service và Domain Service khác nhau thế nào?

**Trả lời:**

**Application Service:**

* Điều phối Use Case.
* Quản lý transaction.
* Gọi Repository và Port.
* Không chứa quy tắc nghiệp vụ cốt lõi.

**Domain Service:**

* Chứa quy tắc nghiệp vụ.
* Là một phần của Domain Model.
* Không quan tâm HTTP, Database hoặc framework.

---

## 24. Domain Event là gì?

**Trả lời:**

Domain Event mô tả một sự kiện nghiệp vụ đã xảy ra.

Ví dụ:

```text
OrderCreated
PaymentCompleted
DocumentProcessed
SubscriptionExpired
```

Tên Event thường sử dụng thì quá khứ vì nó mô tả sự thật đã xảy ra.

---

## 25. Command và Domain Event khác nhau thế nào?

**Trả lời:**

Command yêu cầu hệ thống thực hiện một hành động:

```text
CreateOrder
CancelOrder
ProcessDocument
```

Domain Event thông báo hành động đã xảy ra:

```text
OrderCreated
OrderCancelled
DocumentProcessed
```

Command có thể bị từ chối. Event là sự thật đã xảy ra.

---

## 26. Factory trong DDD dùng để làm gì?

**Trả lời:**

Factory dùng để tạo Aggregate hoặc Entity phức tạp và bảo đảm đối tượng hợp lệ ngay khi được tạo.

Ví dụ:

```typescript
class OrderFactory {
  static create(
    customerId: string,
    items: OrderItem[],
  ): Order {
    if (items.length === 0) {
      throw new Error("Order must contain at least one item");
    }

    return new Order(
      crypto.randomUUID(),
      customerId,
      items,
      "PENDING",
    );
  }
}
```

# III. Hexagonal Architecture

## 27. Hexagonal Architecture là gì?

**Trả lời:**

Hexagonal Architecture còn được gọi là **Ports and Adapters Architecture**.

Mục tiêu là đặt nghiệp vụ ở trung tâm và cô lập nó khỏi các công nghệ bên ngoài như:

* HTTP.
* Database.
* Message Broker.
* Framework.
* Email Service.
* File Storage.

Luồng phụ thuộc:

```text
External Systems
      ↓
   Adapters
      ↓
    Ports
      ↓
Application + Domain
```

Phần bên trong không phụ thuộc trực tiếp vào phần bên ngoài.

---

## 28. Vì sao gọi là Hexagonal Architecture?

**Trả lời:**

Hình lục giác chỉ mang tính minh họa rằng ứng dụng có thể giao tiếp với nhiều hệ thống bên ngoài qua nhiều cổng.

Nó không có nghĩa kiến trúc bắt buộc phải có sáu thành phần.

---

## 29. Port là gì?

**Trả lời:**

Port là interface xác định cách ứng dụng giao tiếp với bên ngoài hoặc cách bên ngoài gọi vào ứng dụng.

Có hai loại chính:

* Inbound Port.
* Outbound Port.

---

## 30. Inbound Port là gì?

**Trả lời:**

Inbound Port mô tả Use Case mà hệ thống cung cấp cho bên ngoài.

Ví dụ:

```typescript
interface CreateOrderUseCase {
  execute(command: CreateOrderCommand): Promise<string>;
}
```

Các thành phần có thể gọi Inbound Port:

* REST Controller.
* gRPC Handler.
* CLI.
* Message Consumer.
* Unit Test.

---

## 31. Outbound Port là gì?

**Trả lời:**

Outbound Port mô tả những khả năng ứng dụng cần từ hệ thống bên ngoài.

Ví dụ:

```typescript
interface PaymentPort {
  charge(
    customerId: string,
    amount: Money,
  ): Promise<PaymentResult>;
}
```

Implementation có thể là:

* Stripe Adapter.
* MoMo Adapter.
* VNPay Adapter.
* Fake Adapter dùng trong test.

---

## 32. Adapter là gì?

**Trả lời:**

Adapter là implementation kết nối Port với một công nghệ cụ thể.

Ví dụ:

```text
OrderRepository Port
       ↑
PostgresOrderRepository Adapter
```

Hoặc:

```text
PaymentPort
   ├── StripeAdapter
   ├── MomoAdapter
   └── FakePaymentAdapter
```

---

## 33. Inbound Adapter là gì?

**Trả lời:**

Inbound Adapter nhận request từ bên ngoài và gọi Inbound Port.

Ví dụ:

* REST Controller.
* GraphQL Resolver.
* gRPC Handler.
* RabbitMQ Consumer.
* CLI Command.

Ví dụ luồng:

```text
HTTP Request
→ REST Controller
→ CreateOrderUseCase
```

---

## 34. Outbound Adapter là gì?

**Trả lời:**

Outbound Adapter thực hiện Outbound Port bằng công nghệ cụ thể.

Ví dụ:

* PostgreSQL Repository.
* Redis Cache.
* RabbitMQ Publisher.
* Email API Client.
* Object Storage Client.

---

## 35. Primary Adapter và Secondary Adapter là gì?

**Trả lời:**

Primary Adapter, hay Driving Adapter, chủ động gọi vào ứng dụng:

* Controller.
* Message Consumer.
* CLI.
* Test.

Secondary Adapter, hay Driven Adapter, được ứng dụng gọi ra:

* Database.
* Message Broker.
* Email Service.
* External API.

---

## 36. Dependency Rule trong Hexagonal Architecture là gì?

**Trả lời:**

Dependency phải hướng vào trong.

```text
Infrastructure → Application → Domain
```

Domain không được import:

* NestJS.
* FastAPI.
* SQLAlchemy.
* TypeORM.
* RabbitMQ Client.
* HTTP Framework.

Infrastructure có thể phụ thuộc Domain, nhưng Domain không phụ thuộc Infrastructure.

---

## 37. Domain Layer gồm những gì?

**Trả lời:**

Domain Layer thường chứa:

* Entity.
* Value Object.
* Aggregate.
* Domain Service.
* Domain Event.
* Quy tắc nghiệp vụ.
* Domain Exception.

Nó nên độc lập với framework và cơ sở dữ liệu.

---

## 38. Application Layer gồm những gì?

**Trả lời:**

Application Layer thường chứa:

* Use Case.
* Application Service.
* Command và Query.
* Inbound Port.
* Outbound Port.
* Transaction orchestration.
* Điều phối Domain Object.

Application Layer trả lời câu hỏi: hệ thống thực hiện Use Case như thế nào.

---

## 39. Infrastructure Layer gồm những gì?

**Trả lời:**

Infrastructure Layer chứa implementation kỹ thuật:

* ORM Entity.
* Repository Adapter.
* HTTP Client.
* RabbitMQ Producer.
* Kafka Consumer.
* Redis Adapter.
* File Storage.
* Framework configuration.

---

## 40. Controller có thuộc Domain Layer không?

**Trả lời:**

Không.

Controller là Inbound Adapter thuộc lớp ngoài.

Nhiệm vụ:

1. Nhận request.
2. Validate định dạng cơ bản.
3. Chuyển request thành Command.
4. Gọi Use Case.
5. Chuyển kết quả thành response.

Controller không nên chứa Business Logic.

# IV. DDD và Hexagonal Architecture

## 41. DDD và Hexagonal Architecture có giống nhau không?

**Trả lời:**

Không.

* **DDD:** Tập trung mô hình hóa nghiệp vụ.
* **Hexagonal Architecture:** Tập trung quản lý phụ thuộc và cô lập nghiệp vụ khỏi hạ tầng.

Hai phương pháp bổ trợ cho nhau:

```text
DDD
→ Thiết kế Domain Model

Hexagonal Architecture
→ Bảo vệ Domain Model khỏi framework và hạ tầng
```

---

## 42. Có thể dùng DDD mà không dùng Hexagonal Architecture không?

**Trả lời:**

Có.

DDD không yêu cầu một kiến trúc cụ thể. Có thể triển khai DDD với:

* Layered Architecture.
* Hexagonal Architecture.
* Clean Architecture.
* Onion Architecture.
* Modular Monolith.

Tuy nhiên, Hexagonal Architecture thường phù hợp vì giúp Domain độc lập.

---

## 43. Có thể dùng Hexagonal Architecture mà không áp dụng DDD không?

**Trả lời:**

Có.

Một ứng dụng CRUD vẫn có thể sử dụng Ports và Adapters để tách HTTP, Database và logic ứng dụng.

Tuy nhiên, nếu nghiệp vụ đơn giản thì không cần tạo Domain Model quá phức tạp.

---

## 44. Hexagonal Architecture khác Layered Architecture thế nào?

**Trả lời:**

Layered Architecture truyền thống thường có:

```text
Controller
→ Service
→ Repository
→ Database
```

Nếu không thiết kế cẩn thận, Service có thể phụ thuộc trực tiếp Repository cụ thể và ORM.

Hexagonal Architecture sử dụng Port:

```text
Controller Adapter
→ Use Case
→ Repository Port
← PostgreSQL Adapter
```

Business Logic phụ thuộc vào abstraction, không phụ thuộc công nghệ cụ thể.

---

## 45. Hexagonal Architecture khác Clean Architecture thế nào?

**Trả lời:**

Cả hai cùng nhấn mạnh:

* Dependency hướng vào trong.
* Nghiệp vụ độc lập framework.
* Tách Use Case khỏi hạ tầng.
* Dễ kiểm thử.

Khác biệt chủ yếu nằm ở cách gọi và cách trình bày:

* Hexagonal: Ports và Adapters.
* Clean Architecture: Entities, Use Cases, Interface Adapters, Frameworks.
* Onion Architecture: Các vòng tròn Domain ở trung tâm.

Trong thực tế, các ý tưởng có nhiều điểm tương đồng.

---

## 46. Repository Interface nên đặt ở đâu?

**Trả lời:**

Repository Port nên đặt ở phía trong, nơi nó được sử dụng, thường là Application hoặc Domain Layer tùy thiết kế.

Implementation đặt trong Infrastructure Layer.

```text
Application:
OrderRepository interface

Infrastructure:
PostgresOrderRepository implementation
```

Phía trong định nghĩa nhu cầu; phía ngoài triển khai nhu cầu đó.

---

## 47. ORM Model có nên dùng trực tiếp làm Domain Entity không?

**Trả lời:**

Không nên trong hệ thống nghiệp vụ phức tạp.

Nếu dùng chung, Domain Entity sẽ phụ thuộc vào:

* Annotation của ORM.
* Cấu trúc bảng.
* Lazy loading.
* Cơ chế persistence.
* Yêu cầu của framework.

Nên tách:

```text
Order Domain Entity
        ↕ Mapper
Order ORM Model
```

Với CRUD đơn giản, có thể chấp nhận dùng chung để giảm độ phức tạp.

---

## 48. Mapper dùng để làm gì?

**Trả lời:**

Mapper chuyển đổi giữa các mô hình.

Ví dụ:

* HTTP DTO → Command.
* ORM Model → Domain Entity.
* Domain Entity → Persistence Model.
* Domain Result → Response DTO.

```typescript
class OrderMapper {
  static toDomain(model: OrderModel): Order {
    return Order.restore(
      model.id,
      model.customerId,
      model.status,
    );
  }

  static toPersistence(order: Order): OrderModel {
    return {
      id: order.id,
      customerId: order.customerId,
      status: order.status,
    };
  }
}
```

---

## 49. DTO khác Domain Entity thế nào?

**Trả lời:**

DTO dùng để truyền dữ liệu qua ranh giới hệ thống.

Domain Entity chứa hành vi và quy tắc nghiệp vụ.

Ví dụ DTO:

```typescript
interface CreateOrderRequest {
  customerId: string;
  items: Array<{
    productId: string;
    quantity: number;
  }>;
}
```

Domain Entity:

```typescript
order.addItem(productId, quantity);
order.confirm();
order.cancel();
```

Không nên biến Domain Entity thành một object chỉ chứa getter và setter.

---

## 50. Dependency Injection có vai trò gì?

**Trả lời:**

Dependency Injection cung cấp implementation của Port cho Use Case tại thời điểm khởi động ứng dụng.

Ví dụ:

```text
OrderRepository Port
        ↑
PostgresOrderRepository
```

Use Case chỉ biết interface. Module cấu hình quyết định sử dụng Adapter nào.

# VI. Câu hỏi tình huống phỏng vấn

## Tình huống 1: Thay PostgreSQL bằng MongoDB

**Hỏi:** Nếu dùng Hexagonal Architecture, thay PostgreSQL bằng MongoDB ảnh hưởng thế nào?

**Trả lời:**

Nếu Repository Port được thiết kế tốt, Domain và Use Case không cần thay đổi.

Chỉ cần tạo Adapter mới:

```text
OrderRepository
   ├── PostgresOrderRepository
   └── MongoOrderRepository
```

Tuy nhiên, nếu đặc tính transaction hoặc truy vấn thay đổi đáng kể, thiết kế nghiệp vụ có thể vẫn cần xem xét lại.

---

## Tình huống 2: Hỗ trợ cả REST và RabbitMQ

**Hỏi:** Cùng một Use Case được gọi từ REST API và RabbitMQ Consumer, thiết kế thế nào?

**Trả lời:**

Tạo hai Inbound Adapter cùng gọi một Inbound Port:

```text
REST Controller ───────┐
                       ├→ ProcessDocumentUseCase
RabbitMQ Consumer ─────┘
```

Business Logic không bị lặp lại trong Controller và Consumer.

---

## Tình huống 3: Controller chứa quy tắc nghiệp vụ

**Hỏi:** Controller kiểm tra trạng thái Order rồi quyết định có được hủy hay không. Có đúng không?

**Trả lời:**

Không nên.

Quy tắc này phải nằm trong Order Aggregate:

```typescript
order.cancel();
```

Order tự kiểm tra:

* Đã giao hàng chưa.
* Đã hủy chưa.
* Có được hoàn tiền không.

Controller chỉ gọi Use Case và chuyển response.

---

## Tình huống 4: Use Case gọi trực tiếp TypeORM Repository

**Hỏi:** Điều này có phù hợp Hexagonal Architecture không?

**Trả lời:**

Không lý tưởng vì Application Layer phụ thuộc trực tiếp vào TypeORM.

Nên khai báo Repository Port:

```typescript
interface OrderRepository {
  save(order: Order): Promise<void>;
}
```

Sau đó TypeORM Adapter triển khai Port này.

---

## Tình huống 5: Gửi Event và lưu Database

**Hỏi:** Lưu Order thành công nhưng publish `OrderCreated` thất bại thì xử lý thế nào?

**Trả lời:**

Có thể sử dụng Transactional Outbox Pattern:

1. Lưu Order.
2. Lưu Event vào bảng Outbox trong cùng transaction.
3. Worker đọc Outbox.
4. Publish Event lên Broker.
5. Đánh dấu Event đã gửi.

Nhờ đó tránh trường hợp dữ liệu được lưu nhưng Event bị mất.

---

## Tình huống 6: Domain cần gọi API tỷ giá

**Hỏi:** Domain Entity có nên gọi HTTP API trực tiếp không?

**Trả lời:**

Không.

Khai báo Outbound Port:

```typescript
interface ExchangeRatePort {
  getRate(
    sourceCurrency: string,
    targetCurrency: string,
  ): Promise<number>;
}
```

HTTP Adapter thực hiện việc gọi API bên ngoài. Application Service điều phối việc lấy tỷ giá và gọi Domain Logic.

---

## Tình huống 7: Unit test Use Case thế nào?

**Trả lời:**

Dùng Fake Adapter hoặc Mock cho các Outbound Port:

```text
CreateOrderUseCase
├── FakeOrderRepository
└── FakePaymentPort
```

Không cần khởi động:

* HTTP Server.
* PostgreSQL.
* RabbitMQ.
* Framework hoàn chỉnh.

Đây là một lợi ích lớn của Hexagonal Architecture.

---

## Tình huống 8: Một ứng dụng CRUD nhỏ có cần DDD đầy đủ không?

**Trả lời:**

Không nhất thiết.

Với CRUD đơn giản, áp dụng đầy đủ Aggregate, Domain Service, Event và nhiều Mapper có thể gây over-engineering.

Có thể chỉ sử dụng:

* Module rõ ràng.
* Service.
* Repository interface.
* Dependency Injection.
* Một số Value Object quan trọng.

Áp dụng mức độ DDD theo độ phức tạp nghiệp vụ.

# VII. Các lỗi thiết kế thường gặp

## 54. Anemic Domain Model là gì?

**Trả lời:**

Anemic Domain Model là mô hình mà Entity chỉ chứa dữ liệu và getter/setter, còn toàn bộ nghiệp vụ nằm trong Service.

Ví dụ không tốt:

```typescript
order.status = "CANCELLED";
```

Tốt hơn:

```typescript
order.cancel();
```

Method `cancel()` kiểm tra và bảo vệ các quy tắc nghiệp vụ.

---

## 55. Domain Model có được phụ thuộc framework không?

**Trả lời:**

Nên hạn chế tối đa.

Domain Model không nên cần:

* Khởi động NestJS.
* FastAPI.
* ORM.
* Database.
* Message Broker.

Domain nên có thể được kiểm thử bằng unit test thông thường.

---

## 56. Có nên tạo Port cho mọi class không?

**Trả lời:**

Không.

Port nên được tạo tại ranh giới giữa ứng dụng và thế giới bên ngoài, hoặc khi thực sự cần thay thế implementation.

Không cần tạo interface cho mọi Service nội bộ nếu không có giá trị thiết kế rõ ràng.

---

## 57. Có nên tạo một Repository cho mỗi bảng không?

**Trả lời:**

Không nhất thiết.

Trong DDD, Repository thường được tạo cho Aggregate Root, không phải từng bảng.

Ví dụ:

```text
Order Aggregate
├── orders table
└── order_items table
```

Có thể chỉ cần `OrderRepository`, không cần bắt buộc có `OrderItemRepository`.

---

## 58. Có nên để các Bounded Context dùng chung Domain Entity?

**Trả lời:**

Không nên trong đa số trường hợp.

Mỗi Bounded Context có mô hình riêng. Chia sẻ chung Entity sẽ làm tăng coupling và khiến thay đổi của một Context ảnh hưởng Context khác.

Nên giao tiếp bằng:

* API contract.
* Event schema.
* Published Language.
* Anti-Corruption Layer.

# VIII. Câu hỏi nâng cao

## 59. Anti-Corruption Layer là gì?

**Trả lời:**

Anti-Corruption Layer, viết tắt là ACL, chuyển đổi mô hình của hệ thống bên ngoài sang mô hình nội bộ.

Ví dụ:

```text
External Payment Model
        ↓
Payment ACL/Adapter
        ↓
Internal Payment Domain
```

ACL ngăn thuật ngữ và cấu trúc không phù hợp từ hệ thống ngoài xâm nhập Domain Model.

---

## 60. Published Language là gì?

**Trả lời:**

Published Language là ngôn ngữ hoặc schema giao tiếp được công bố giữa các Context.

Ví dụ:

* OpenAPI schema.
* Protobuf.
* JSON Event Schema.
* AsyncAPI.
* Avro Schema.

Nó giúp hai Context giao tiếp mà không chia sẻ trực tiếp Domain Model.

---

## 61. Shared Kernel là gì?

**Trả lời:**

Shared Kernel là một phần nhỏ của Model được hai Bounded Context cùng chia sẻ.

Việc thay đổi Shared Kernel phải được các nhóm liên quan thống nhất.

Pattern này làm tăng coupling nên chỉ nên dùng cho phần thật sự ổn định và nhỏ.

---

## 62. Domain Event nên được publish khi nào?

**Trả lời:**

Domain Event được tạo khi nghiệp vụ xảy ra, nhưng việc publish ra Broker thường nên diễn ra sau khi transaction lưu dữ liệu thành công.

Để bảo đảm độ tin cậy, có thể dùng Outbox Pattern.

---

## 63. Domain Event và Integration Event khác nhau thế nào?

**Trả lời:**

**Domain Event:**

* Có ý nghĩa bên trong Bounded Context.
* Có thể chứa cấu trúc gắn với Domain Model.
* Thường được xử lý nội bộ.

**Integration Event:**

* Được publish cho Context hoặc Service khác.
* Cần contract ổn định.
* Không nên làm lộ chi tiết Domain nội bộ.
* Cần quản lý phiên bản.

Một Domain Event có thể được chuyển thành Integration Event.

---

## 64. Transaction Boundary nên đặt ở đâu?

**Trả lời:**

Transaction thường bao quanh một Use Case và một Aggregate.

Application Service thường chịu trách nhiệm điều phối transaction.

Không nên giữ transaction Database trong khi:

* Gọi API bên ngoài lâu.
* Chờ Message Broker.
* Chờ người dùng.
* Xử lý tác vụ nặng.

---

## 65. Hexagonal Architecture có phù hợp Microservices không?

**Trả lời:**

Có.

Mỗi Microservice có thể được thiết kế như một hình lục giác độc lập:

```text
REST/RabbitMQ
      ↓
Inbound Adapters
      ↓
Application + Domain
      ↓
Outbound Ports
      ↓
Database/External APIs
```

Tuy nhiên, kiến trúc này cũng phù hợp với Modular Monolith, không chỉ Microservices.

# IX. Câu trả lời ngắn cần ghi nhớ

**DDD là gì?**

> DDD là phương pháp thiết kế phần mềm tập trung vào nghiệp vụ, Ubiquitous Language, Bounded Context và Domain Model.

**Hexagonal Architecture là gì?**

> Hexagonal Architecture đặt nghiệp vụ ở trung tâm và giao tiếp với bên ngoài thông qua Ports và Adapters.

**Port là gì?**

> Port là interface định nghĩa cách bên ngoài gọi vào ứng dụng hoặc cách ứng dụng sử dụng dịch vụ bên ngoài.

**Adapter là gì?**

> Adapter là implementation cụ thể kết nối Port với HTTP, Database, Message Broker hoặc dịch vụ bên ngoài.

**Aggregate Root là gì?**

> Aggregate Root là Entity chính kiểm soát mọi thay đổi và bảo vệ tính nhất quán trong Aggregate.

**Application Service khác Domain Service thế nào?**

> Application Service điều phối Use Case; Domain Service chứa quy tắc nghiệp vụ không phù hợp với một Entity cụ thể.

**DDD khác Hexagonal Architecture thế nào?**

> DDD giúp mô hình hóa đúng nghiệp vụ; Hexagonal Architecture giúp bảo vệ nghiệp vụ khỏi phụ thuộc framework và hạ tầng.

**Luồng phụ thuộc đúng:**

```text
Infrastructure
      ↓
Application
      ↓
Domain
```

**Luồng thực thi có thể đi ra ngoài, nhưng phụ thuộc mã nguồn phải hướng vào trong.**
