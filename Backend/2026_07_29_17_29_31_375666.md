Dưới đây là bộ câu hỏi phỏng vấn về **REST và gRPC**, phù hợp với vị trí **Lập trình viên Fresher/Junior Backend, Fullstack hoặc Microservices**.

# I. Kiến thức về REST

## 1. REST là gì?

**Trả lời:**

REST là viết tắt của **Representational State Transfer**, một phong cách kiến trúc dùng để thiết kế hệ thống giao tiếp qua mạng.

REST thường sử dụng:

* HTTP.
* URI để xác định tài nguyên.
* HTTP Method để thể hiện hành động.
* JSON để trao đổi dữ liệu.

Ví dụ:

```http
GET /api/users/10
```

Request trên yêu cầu lấy thông tin người dùng có ID bằng `10`.

---

## 2. REST API là gì?

**Trả lời:**

REST API là API được thiết kế dựa trên các nguyên tắc REST.

Ví dụ:

```http
GET    /users
GET    /users/10
POST   /users
PUT    /users/10
PATCH  /users/10
DELETE /users/10
```

Trong đó, `users` là tài nguyên.

---

## 3. Resource trong REST là gì?

**Trả lời:**

Resource là đối tượng hoặc dữ liệu mà API quản lý.

Ví dụ:

* User.
* Product.
* Order.
* Document.

Mỗi Resource thường được xác định bằng URI:

```text
/users/10
/orders/100
```

---

## 4. URI nên đặt theo danh từ hay động từ?

**Trả lời:**

REST API nên dùng **danh từ** để biểu diễn tài nguyên.

Nên:

```http
GET /users
POST /orders
```

Không nên:

```http
GET /getUsers
POST /createOrder
```

Hành động đã được thể hiện bằng HTTP Method.

---

## 5. Những HTTP Method phổ biến trong REST là gì?

**Trả lời:**

* `GET`: Lấy dữ liệu.
* `POST`: Tạo tài nguyên mới hoặc thực hiện một thao tác không idempotent.
* `PUT`: Thay thế hoặc cập nhật toàn bộ tài nguyên.
* `PATCH`: Cập nhật một phần tài nguyên.
* `DELETE`: Xóa tài nguyên.

---

## 6. GET và POST khác nhau như thế nào?

**Trả lời:**

`GET` dùng để lấy dữ liệu và không nên làm thay đổi trạng thái hệ thống.

`POST` thường dùng để tạo dữ liệu hoặc thực hiện một hành động làm thay đổi trạng thái.

Ví dụ:

```http
GET /products
```

```http
POST /products
Content-Type: application/json

{
  "name": "Laptop"
}
```

---

## 7. PUT và PATCH khác nhau như thế nào?

**Trả lời:**

`PUT` thường thay thế toàn bộ tài nguyên.

```http
PUT /users/10
```

```json
{
  "name": "Nghia",
  "email": "nghia@example.com"
}
```

`PATCH` chỉ cập nhật một phần:

```http
PATCH /users/10
```

```json
{
  "name": "Nguyễn Văn Nghĩa"
}
```

---

## 8. Idempotent là gì?

**Trả lời:**

Một thao tác là idempotent nếu gọi nhiều lần với cùng dữ liệu vẫn tạo ra kết quả cuối giống như gọi một lần.

Ví dụ thường idempotent:

* `GET`
* `PUT`
* `DELETE`

Ví dụ:

```http
DELETE /users/10
```

Gọi lần đầu xóa người dùng. Các lần gọi sau không làm trạng thái hệ thống thay đổi thêm.

`POST` thường không idempotent vì gọi nhiều lần có thể tạo nhiều bản ghi.

---

## 9. Safe Method là gì?

**Trả lời:**

Safe Method là phương thức không nên làm thay đổi trạng thái của tài nguyên trên Server.

Ví dụ:

* `GET`
* `HEAD`
* `OPTIONS`

`Safe` và `idempotent` không hoàn toàn giống nhau. `DELETE` là idempotent nhưng không phải safe vì nó làm thay đổi dữ liệu.

---

## 10. Stateless trong REST là gì?

**Trả lời:**

Stateless nghĩa là Server không phụ thuộc vào trạng thái của request trước đó để xử lý request hiện tại.

Mỗi request phải mang đủ thông tin cần thiết, ví dụ:

```http
Authorization: Bearer <token>
```

Điều này giúp hệ thống dễ mở rộng theo chiều ngang vì bất kỳ Server instance nào cũng có thể xử lý request.

---

## 11. REST API thường dùng định dạng dữ liệu nào?

**Trả lời:**

Phổ biến nhất là JSON:

```json
{
  "id": 10,
  "name": "Nghia"
}
```

REST cũng có thể dùng:

* XML.
* HTML.
* Plain text.
* Binary data.

REST không bắt buộc phải sử dụng JSON.

---

## 12. Status Code 200, 201 và 204 khác nhau thế nào?

**Trả lời:**

* `200 OK`: Request thành công và thường có dữ liệu trả về.
* `201 Created`: Tạo tài nguyên mới thành công.
* `204 No Content`: Xử lý thành công nhưng không có response body.

Ví dụ tạo người dùng thành công nên trả:

```http
HTTP/1.1 201 Created
Location: /users/10
```

---

## 13. Status Code 400, 401 và 403 khác nhau thế nào?

**Trả lời:**

* `400 Bad Request`: Dữ liệu request không hợp lệ.
* `401 Unauthorized`: Chưa xác thực hoặc thông tin xác thực không hợp lệ.
* `403 Forbidden`: Đã xác thực nhưng không có quyền thực hiện hành động.

---

## 14. Status Code 404 và 409 dùng khi nào?

**Trả lời:**

`404 Not Found` dùng khi tài nguyên không tồn tại:

```http
GET /users/999
```

`409 Conflict` dùng khi request xung đột với trạng thái hiện tại.

Ví dụ:

* Email đã tồn tại.
* Cập nhật phiên bản dữ liệu cũ.
* Không thể đặt chỗ vì đã có người đặt trước.

---

## 15. Query Parameter và Path Parameter khác nhau như thế nào?

**Trả lời:**

Path Parameter xác định một tài nguyên cụ thể:

```http
GET /users/10
```

Query Parameter thường dùng để lọc, tìm kiếm, sắp xếp hoặc phân trang:

```http
GET /users?status=active&page=2
```

---

## 16. REST API nên xử lý phân trang như thế nào?

**Trả lời:**

Có thể dùng offset pagination:

```http
GET /users?page=2&size=20
```

Hoặc:

```http
GET /users?limit=20&offset=20
```

Với dữ liệu lớn và thay đổi liên tục, có thể dùng cursor pagination:

```http
GET /users?limit=20&cursor=abc123
```

Cursor pagination thường ổn định và hiệu quả hơn khi dữ liệu lớn.

---

## 17. API Versioning là gì?

**Trả lời:**

API Versioning giúp duy trì nhiều phiên bản API để tránh làm hỏng Client cũ.

Ví dụ:

```http
/api/v1/users
/api/v2/users
```

Ngoài URI, phiên bản cũng có thể được truyền qua header.

---

## 18. Authentication trong REST thường được thực hiện như thế nào?

**Trả lời:**

Các phương pháp phổ biến:

* API Key.
* Session và Cookie.
* JWT Bearer Token.
* OAuth 2.0.

Ví dụ:

```http
Authorization: Bearer <access_token>
```

---

## 19. CORS là gì?

**Trả lời:**

CORS là cơ chế của trình duyệt kiểm soát việc một trang web gọi API thuộc origin khác.

Ví dụ:

```text
Frontend: https://app.example.com
Backend:  https://api.example.com
```

Server cần cấu hình những origin, method và header được phép.

CORS chủ yếu là chính sách của trình duyệt, không phải cơ chế xác thực API.

---

## 20. REST API có hỗ trợ streaming không?

**Trả lời:**

Có thể, thông qua những cơ chế như:

* Server-Sent Events.
* Chunked response.
* Streaming download.
* WebSocket cho giao tiếp hai chiều.

Tuy nhiên, REST thông thường chủ yếu được sử dụng theo mô hình một request và một response.

# II. Kiến thức về gRPC

## 21. gRPC là gì?

**Trả lời:**

gRPC là framework Remote Procedure Call hiệu năng cao.

Nó cho phép một ứng dụng gọi phương thức của Service ở máy khác gần giống như gọi hàm cục bộ.

Ví dụ:

```text
User Service
    ↓ GetUser()
Profile Service
```

gRPC thường sử dụng:

* HTTP/2.
* Protocol Buffers.
* Code generation.
* Hợp đồng API khai báo trong file `.proto`.

---

## 22. RPC là gì?

**Trả lời:**

RPC là viết tắt của **Remote Procedure Call**.

Thay vì tư duy theo tài nguyên như REST:

```http
GET /users/10
```

RPC tư duy theo việc gọi phương thức:

```text
GetUser(userId)
```

Ứng dụng gọi một hàm nằm trên Server từ xa.

---

## 23. Protocol Buffers là gì?

**Trả lời:**

Protocol Buffers, thường gọi là Protobuf, là định dạng tuần tự hóa dữ liệu dạng nhị phân.

Protobuf có đặc điểm:

* Dữ liệu nhỏ.
* Mã hóa và giải mã nhanh.
* Có schema rõ ràng.
* Hỗ trợ sinh code cho nhiều ngôn ngữ.

---

## 24. File `.proto` dùng để làm gì?

**Trả lời:**

File `.proto` định nghĩa:

* Message.
* Trường dữ liệu.
* Service.
* Các RPC method.

Ví dụ:

```proto
syntax = "proto3";

service UserService {
  rpc GetUser(GetUserRequest) returns (UserResponse);
}

message GetUserRequest {
  int64 id = 1;
}

message UserResponse {
  int64 id = 1;
  string name = 2;
}
```

Từ file này, công cụ Protobuf có thể sinh Client Stub và Server Interface.

---

## 25. Các số `= 1`, `= 2` trong Protobuf có ý nghĩa gì?

**Trả lời:**

Đó là số định danh duy nhất của từng field trong message.

Ví dụ:

```proto
message User {
  int64 id = 1;
  string name = 2;
}
```

Các số này được sử dụng trong dữ liệu nhị phân, nên không nên thay đổi hoặc tái sử dụng tùy tiện sau khi API đã được phát hành.

---

## 26. Vì sao không nên thay đổi field number trong Protobuf?

**Trả lời:**

Field number được dùng để nhận dạng trường trong dữ liệu nhị phân.

Nếu thay đổi hoặc dùng lại sai cách, Client và Server ở các phiên bản khác nhau có thể hiểu sai dữ liệu.

Khi xóa field, nên đánh dấu `reserved`:

```proto
message User {
  reserved 2;
  reserved "name";

  int64 id = 1;
}
```

---

## 27. Stub trong gRPC là gì?

**Trả lời:**

Stub là mã Client được sinh tự động từ file `.proto`.

Client gọi Stub như gọi một phương thức bình thường:

```text
userClient.getUser(request)
```

Stub chịu trách nhiệm:

* Tuần tự hóa request.
* Gửi request qua mạng.
* Nhận response.
* Giải mã response.

---

## 28. gRPC sử dụng HTTP phiên bản nào?

**Trả lời:**

gRPC thường sử dụng HTTP/2.

HTTP/2 hỗ trợ:

* Multiplexing.
* Header compression.
* Một kết nối có thể xử lý nhiều stream.
* Giao tiếp streaming hiệu quả.

---

## 29. gRPC có những loại giao tiếp nào?

**Trả lời:**

Có bốn loại chính:

1. Unary RPC.
2. Server Streaming.
3. Client Streaming.
4. Bidirectional Streaming.

---

## 30. Unary RPC là gì?

**Trả lời:**

Client gửi một request và Server trả về một response.

```text
Client ── Request ──> Server
Client <─ Response ── Server
```

Ví dụ:

```proto
rpc GetUser(GetUserRequest) returns (UserResponse);
```

Đây là loại gần giống REST request/response nhất.

---

## 31. Server Streaming là gì?

**Trả lời:**

Client gửi một request, Server trả về một luồng nhiều response.

```proto
rpc ListUsers(ListUsersRequest) returns (stream UserResponse);
```

Ví dụ:

* Stream danh sách kết quả.
* Stream tiến độ xử lý.
* Stream dữ liệu AI.

---

## 32. Client Streaming là gì?

**Trả lời:**

Client gửi nhiều message liên tục, sau đó Server trả về một response.

```proto
rpc UploadChunks(stream FileChunk) returns (UploadResult);
```

Ví dụ:

* Upload file theo từng phần.
* Gửi nhiều bản ghi lên Server.

---

## 33. Bidirectional Streaming là gì?

**Trả lời:**

Client và Server có thể đồng thời gửi nhiều message cho nhau trên cùng một kết nối.

```proto
rpc Chat(stream ChatMessage) returns (stream ChatMessage);
```

Phù hợp với:

* Chat thời gian thực.
* Truyền dữ liệu liên tục.
* Hệ thống điều khiển thời gian thực.

---

## 34. Metadata trong gRPC là gì?

**Trả lời:**

Metadata tương tự HTTP Header, dùng để truyền thông tin bổ sung.

Ví dụ:

* Access token.
* Trace ID.
* Request ID.
* Thông tin phiên bản.

```text
authorization: Bearer <token>
x-request-id: abc123
```

---

## 35. Deadline trong gRPC là gì?

**Trả lời:**

Deadline là thời điểm tối đa mà Client chấp nhận chờ RPC hoàn thành.

Nếu vượt quá thời gian đó, request bị hủy với lỗi deadline exceeded.

Mỗi lời gọi giữa Microservice nên có deadline để tránh chờ vô hạn.

---

## 36. Timeout và Deadline khác nhau thế nào?

**Trả lời:**

Timeout là khoảng thời gian cho phép chờ:

```text
Chờ tối đa 5 giây
```

Deadline là thời điểm cụ thể phải hoàn thành:

```text
Phải hoàn thành trước 10:00:05
```

Trong hệ thống phân tán, deadline có thể được truyền qua nhiều Service để các Service phía sau biết thời gian còn lại.

---

## 37. Interceptor trong gRPC là gì?

**Trả lời:**

Interceptor cho phép chạy logic trước hoặc sau một RPC.

Nó tương tự:

* Middleware trong HTTP.
* Filter trong Java.
* Guard hoặc Interceptor trong NestJS.

Thường dùng cho:

* Authentication.
* Logging.
* Metrics.
* Tracing.
* Error handling.

---

## 38. gRPC xử lý lỗi như thế nào?

**Trả lời:**

gRPC sử dụng status code riêng.

Ví dụ:

* `OK`.
* `INVALID_ARGUMENT`.
* `NOT_FOUND`.
* `ALREADY_EXISTS`.
* `UNAUTHENTICATED`.
* `PERMISSION_DENIED`.
* `INTERNAL`.
* `UNAVAILABLE`.
* `DEADLINE_EXCEEDED`.

Nên trả mã lỗi phù hợp thay vì luôn trả `INTERNAL`.

---

## 39. Health Check trong gRPC là gì?

**Trả lời:**

Health Check cho phép hệ thống kiểm tra một gRPC Service có đang sẵn sàng phục vụ hay không.

Nó thường được dùng bởi:

* Kubernetes.
* Load Balancer.
* Service Discovery.
* Monitoring system.

---

## 40. gRPC có dùng được trực tiếp trong trình duyệt không?

**Trả lời:**

Trình duyệt thường không gọi gRPC chuẩn trực tiếp giống Backend Client vì có một số hạn chế trong việc truy cập đầy đủ các tính năng HTTP/2.

Có thể sử dụng:

* gRPC-Web.
* Proxy như Envoy.
* API Gateway hỗ trợ chuyển đổi giao thức.

Vì vậy, REST thường thuận tiện hơn cho public API dành cho trình duyệt.

# III. So sánh REST và gRPC

## 41. REST và gRPC khác nhau cơ bản như thế nào?

**Trả lời:**

| REST                                   | gRPC                     |
| -------------------------------------- | ------------------------ |
| Kiến trúc hướng tài nguyên             | Gọi phương thức từ xa    |
| Thường dùng HTTP/1.1 hoặc HTTP/2       | Thường dùng HTTP/2       |
| Thường dùng JSON                       | Thường dùng Protobuf     |
| Dữ liệu dễ đọc                         | Dữ liệu nhị phân         |
| Dễ kiểm tra bằng trình duyệt hoặc cURL | Cần công cụ hỗ trợ gRPC  |
| Phù hợp public API                     | Phù hợp giao tiếp nội bộ |
| Streaming không phải mô hình chính     | Hỗ trợ streaming mạnh    |

---

## 42. gRPC có luôn nhanh hơn REST không?

**Trả lời:**

Không nên khẳng định gRPC luôn nhanh hơn trong mọi trường hợp.

gRPC thường có lợi thế vì:

* Protobuf nhỏ hơn JSON.
* Mã hóa và giải mã hiệu quả.
* HTTP/2 hỗ trợ multiplexing.
* Kết nối được tái sử dụng.

Tuy nhiên, hiệu năng thực tế còn phụ thuộc:

* Logic nghiệp vụ.
* Database.
* Network latency.
* Kích thước dữ liệu.
* Cấu hình hệ thống.

Nếu truy vấn Database mất hai giây thì việc đổi JSON sang Protobuf có thể không giải quyết được nút thắt chính.

---

## 43. Khi nào nên dùng REST?

**Trả lời:**

REST phù hợp khi:

* Xây dựng API công khai.
* Client là trình duyệt hoặc mobile.
* Cần dễ kiểm tra và debug.
* Cần tương thích với nhiều hệ thống.
* API chủ yếu là CRUD.
* Đội ngũ muốn phát triển đơn giản.

---

## 44. Khi nào nên dùng gRPC?

**Trả lời:**

gRPC phù hợp khi:

* Giao tiếp nội bộ giữa các Microservice.
* Cần hiệu năng và độ trễ thấp.
* Cần schema và type safety rõ ràng.
* Cần streaming.
* Hệ thống có nhiều ngôn ngữ lập trình.
* Có nhiều lời gọi giữa các Service.

---

## 45. Có thể dùng REST và gRPC trong cùng một hệ thống không?

**Trả lời:**

Có, và đây là thiết kế khá phổ biến.

Ví dụ:

```text
Web/Mobile
    ↓ REST
API Gateway
    ↓ gRPC
Internal Microservices
```

REST được dùng cho Client bên ngoài, còn gRPC được dùng cho giao tiếp nội bộ giữa các Service.

---

## 46. REST và gRPC cái nào dễ debug hơn?

**Trả lời:**

REST thường dễ debug hơn vì:

* JSON dễ đọc.
* Có thể dùng trình duyệt, Postman hoặc cURL.
* HTTP status code quen thuộc.

gRPC cần công cụ như:

* `grpcurl`.
* Postman hỗ trợ gRPC.
* BloomRPC hoặc công cụ tương tự.
* Server Reflection nếu được bật.

---

## 47. REST và gRPC cái nào dễ thay đổi API hơn?

**Trả lời:**

Cả hai đều cần quản lý tương thích ngược.

Với REST:

* Có thể thêm field JSON mới.
* Có thể tạo phiên bản `/v2`.
* Client có thể bỏ qua field không dùng.

Với gRPC:

* Có schema rõ ràng.
* Có thể thêm field mới với field number mới.
* Không nên thay đổi ý nghĩa hoặc tái sử dụng field number cũ.

gRPC có quy tắc schema chặt chẽ hơn, giúp phát hiện lỗi sớm nhưng cũng yêu cầu quản lý `.proto` cẩn thận.

---

## 48. REST hay gRPC phù hợp hơn cho file lớn?

**Trả lời:**

Tùy trường hợp.

REST phù hợp với:

* Upload/download file qua HTTP.
* Object Storage.
* Presigned URL.
* Tương thích với trình duyệt.

gRPC phù hợp khi cần:

* Chia file thành các chunk.
* Client Streaming.
* Truyền dữ liệu giữa các Service nội bộ.

Trong thực tế, file rất lớn thường được upload trực tiếp lên Object Storage thay vì truyền qua nhiều Microservice.

---

## 49. REST hay gRPC phù hợp hơn với Microservices?

**Trả lời:**

Cả hai đều có thể dùng.

REST:

* Đơn giản.
* Dễ debug.
* Phù hợp khi số lượng lời gọi không quá lớn.

gRPC:

* Hợp đồng API rõ ràng.
* Hiệu năng tốt.
* Hỗ trợ streaming.
* Phù hợp giao tiếp nội bộ có tần suất cao.

Không nên chọn gRPC chỉ vì hệ thống sử dụng Microservices. Cần dựa vào yêu cầu thực tế.

---

## 50. Nhược điểm của gRPC là gì?

**Trả lời:**

* Khó đọc dữ liệu trực tiếp vì dùng binary.
* Debug phức tạp hơn REST.
* Client phải sinh code từ `.proto`.
* Browser cần gRPC-Web hoặc Proxy.
* Quản lý schema và tương thích phiên bản phải cẩn thận.
* Không thuận tiện bằng REST cho public API đơn giản.

# IV. Câu hỏi tình huống phỏng vấn

## Tình huống 1: Public API và giao tiếp nội bộ

**Hỏi:** Hệ thống có Web Client và nhiều Microservice. Bạn chọn REST hay gRPC?

**Trả lời:**

Tôi có thể sử dụng REST giữa Web Client và API Gateway vì trình duyệt hỗ trợ tốt và dễ tích hợp. Giữa API Gateway và các Microservice nội bộ, tôi cân nhắc gRPC nếu cần hiệu năng cao, type safety hoặc streaming.

```text
Browser
   ↓ REST/JSON
API Gateway
   ↓ gRPC/Protobuf
Internal Services
```

---

## Tình huống 2: Service gọi nhau bị treo

**Hỏi:** Một gRPC Service gọi Service khác nhưng không nhận được phản hồi. Bạn xử lý thế nào?

**Trả lời:**

Tôi sẽ:

1. Đặt deadline cho mỗi RPC.
2. Kiểm tra log và distributed tracing.
3. Kiểm tra Service Discovery và kết nối mạng.
4. Chỉ retry với lỗi tạm thời và thao tác an toàn.
5. Sử dụng Circuit Breaker nếu phù hợp.
6. Không retry vô hạn.
7. Kiểm tra Backend có quá tải hoặc deadlock không.

---

## Tình huống 3: RPC bị gọi hai lần

**Hỏi:** Client retry khiến một RPC tạo đơn hàng bị xử lý hai lần. Bạn giải quyết thế nào?

**Trả lời:**

Tạo đơn hàng không tự nhiên idempotent. Tôi sẽ sử dụng idempotency key:

```text
idempotency-key: order-request-123
```

Server lưu key đã xử lý. Nếu nhận lại cùng key, Server trả kết quả cũ thay vì tạo đơn hàng mới.

---

## Tình huống 4: Thay đổi file `.proto`

**Hỏi:** Bạn muốn xóa một trường cũ trong Protobuf. Bạn làm gì?

**Trả lời:**

Không nên tái sử dụng field number hoặc tên cũ. Tôi sẽ xóa field và đánh dấu `reserved`:

```proto
message User {
  reserved 3;
  reserved "old_address";

  int64 id = 1;
  string name = 2;
}
```

Điều này tránh phiên bản mới sử dụng lại mã trường mà dữ liệu cũ vẫn có thể chứa.

---

## Tình huống 5: Streaming kết quả AI

**Hỏi:** Một AI Service trả kết quả từng phần. Nên dùng loại RPC nào?

**Trả lời:**

Nếu Client gửi một yêu cầu và Server trả kết quả từng phần, tôi chọn Server Streaming:

```proto
rpc GenerateAnswer(QuestionRequest)
    returns (stream AnswerChunk);
```

Nếu cả Client và Server cần liên tục trao đổi dữ liệu, có thể dùng Bidirectional Streaming.

# V. Câu hỏi nâng cao

## 1. Có nên tự động retry mọi lời gọi gRPC không?

**Trả lời:**

Không.

Chỉ nên retry khi:

* Lỗi có tính tạm thời, chẳng hạn `UNAVAILABLE`.
* Thao tác idempotent.
* Chưa vượt deadline.
* Có giới hạn số lần retry.
* Có exponential backoff và jitter.

Không nên retry tùy tiện thao tác tạo thanh toán hoặc tạo đơn hàng vì có thể tạo dữ liệu trùng.

---

## 2. Tại sao cần truyền deadline giữa các Microservice?

**Trả lời:**

Giả sử Client chỉ chờ tối đa ba giây nhưng Service A gọi Service B mà không truyền deadline. Service B có thể tiếp tục xử lý rất lâu dù Client đã ngắt kết nối.

Truyền deadline giúp:

* Hủy công việc không còn cần thiết.
* Tiết kiệm tài nguyên.
* Tránh request bị treo.
* Kiểm soát tổng thời gian phản hồi.

---

## 3. Có nên chia sẻ một file `.proto` cho tất cả Service không?

**Trả lời:**

Không nên tạo một file khổng lồ dùng chung cho toàn hệ thống.

Nên tổ chức schema theo từng miền hoặc Service:

```text
proto/
├── user/v1/user.proto
├── payment/v1/payment.proto
└── document/v1/document.proto
```

Chỉ chia sẻ những message thực sự là hợp đồng chung.

---

## 4. gRPC có thay thế Message Queue không?

**Trả lời:**

Không.

gRPC phù hợp với giao tiếp trực tiếp, thường cần Service đích đang hoạt động.

Message Queue phù hợp với:

* Giao tiếp bất đồng bộ.
* Lưu message khi Consumer tạm thời không hoạt động.
* Xử lý nền.
* Giảm phụ thuộc giữa các Service.

Một hệ thống có thể sử dụng cả gRPC và RabbitMQ/Kafka.

---

## 5. Làm thế nào bảo mật gRPC?

**Trả lời:**

Có thể sử dụng:

* TLS hoặc mTLS.
* Access token trong Metadata.
* Interceptor để xác thực.
* Phân quyền theo RPC method.
* NetworkPolicy hoặc firewall.
* Không public những Service nội bộ không cần thiết.
* Giới hạn kích thước message và deadline.

# VI. Câu trả lời ngắn nên ghi nhớ

**REST là gì?**

> REST là phong cách kiến trúc hướng tài nguyên, thường sử dụng HTTP Method, URI và JSON để giao tiếp giữa Client và Server.

**gRPC là gì?**

> gRPC là framework gọi hàm từ xa, thường sử dụng HTTP/2 và Protocol Buffers, phù hợp với giao tiếp hiệu năng cao giữa các Microservice.

**REST khác gRPC thế nào?**

> REST hướng tài nguyên và thường dùng JSON, còn gRPC hướng phương thức, sử dụng Protobuf và hỗ trợ streaming mạnh.

**Khi nào dùng REST?**

> Dùng REST cho public API, trình duyệt, CRUD và các hệ thống cần dễ tích hợp, dễ debug.

**Khi nào dùng gRPC?**

> Dùng gRPC cho giao tiếp nội bộ giữa Microservice, cần hiệu năng, type safety hoặc streaming.

**Thiết kế thường gặp:**

```text
Client
  ↓ REST
API Gateway
  ↓ gRPC
Microservices
  ↓ Message Queue
Background Workers
```
